# /feature-verify

Goal-backward verification gate. Reads `tasks.md` `must_haves` blocks and checks the codebase actually delivers each promised truth. Read-only.

## Usage

```
/feature-verify <name>
```

Where `<name>` matches a directory under `.planning/`.

## Procedure

### Step 1: Locate & load

```bash
REPO_ROOT=$(git rev-parse --show-toplevel)
cd "$REPO_ROOT"

FEATURE_NAME="<name>"
TASKS_FILE=".planning/$FEATURE_NAME/tasks.md"
PATTERNS_FILE=".planning/$FEATURE_NAME/PATTERNS.md"   # optional
CONTRACT_FILE=".planning/$FEATURE_NAME/contract.yaml" # optional
```

If `tasks.md` does not exist, stop and tell the user.

**Detect workspace shape:**

```
Read .planning/<name>/tasks.md and look at the first non-blank line.

CASE A — /build workspace (feature):
  tasks.md starts with "# <Feature Name> Tasks" header.
  Parsing: extract every user story's `must_haves` block.

CASE B — /improve workspace (improvement):
  tasks.md starts with "# Improvement: <description>" header.
  Parsing: there's a single top-level `## must_haves` block (not per-story). Use it as the
  sole goal-backward contract. Tasks are flat under ## Tasks sections.

CASE C — Legacy (no must_haves at all):
  tasks.md exists but no must_haves block anywhere. Write a brief verification.md stating
  `status: skipped — no must_haves blocks present` and exit. Do not fabricate truths.
```

For CASE A and CASE B, proceed to Step 2 with the extracted must_haves entries. The verification logic is identical — the only difference is the parser.

### Step 2: Verify each must-have

For each story, for each entry in its `must_haves` block:

**`truths` entries:**
- Translate the truth into a grep-able signal (entry point + expected outcome).
- Run `grep -rn` against the source tree to find evidence the code path exists.
- Classify:
  - **VERIFIED** — found the code path, end-to-end traceable.
  - **FAILED** — no evidence in the codebase. Tag as `BLOCKER`.
  - **UNCERTAIN** — partial evidence; behavior cannot be confirmed without runtime/manual check. Tag as `WARNING`.

**`artifacts` entries:**
- `stat` the path. Missing → **FAILED (BLOCKER)**.
- Read up to 30 lines. Classify as **stub** if any of:
  - File body ≤ 5 lines of substantive content (excluding imports, blank lines).
  - Function returns `null`, `undefined`, `{}` immediately.
  - Contains `TODO` / `FIXME` / `throw new Error('not implemented')` as the primary body.
- Stub → **FAILED (BLOCKER)**. Otherwise → **VERIFIED**.

**`key_links` entries:**
- `grep -rn "<to-symbol>" <from-file-or-dir>` — does the `from` actually reference `to`?
- No match → **FAILED (BLOCKER)**.
- Match but obvious indirection issue (commented out, in a test, in dead code) → **UNCERTAIN (WARNING)**.
- Clean match → **VERIFIED**.

### Step 3: Write `verification.md`

Write `.planning/<name>/verification.md`:

```markdown
# <name> — Verification Report

> Generated by /feature-verify on <ISO date>
> Workspace type: feature (from /build) | improvement (from /improve)

## Summary
- Total must_haves checked: <N>
- VERIFIED: <count>
- FAILED (BLOCKER): <count>
- UNCERTAIN (WARNING): <count>

**Verdict:** SHIP | NEEDS_FIX | UNCERTAIN_NEEDS_HUMAN

## VERIFIED
- **US-01 / truth / "User can submit form"** — handler dispatch chain confirmed:
  `src/features/X/Form.tsx:42` → `dispatch(saveX)` → `src/store/sagas/saveX.ts:18` → API call

## FAILED (BLOCKER)
- **US-03 / key_link / Component → API** — `src/X/Page.tsx` does not import `xApi.fetchY`.
  Fix: wire the fetch call in the page's data-loading effect.

## UNCERTAIN (WARNING)
- **US-02 / truth / "Validation snackbar appears on error"** — handler exists at
  `src/features/X/Form.tsx:55` but cannot confirm visual without runtime.
  Recommend: manual smoke or Playwright e2e.
```

### Step 4: Report & next steps

Print compact summary to stdout:

```
Feature verification: <name>
  VERIFIED: <n>
  FAILED  : <n>  (BLOCKER)
  UNCERTAIN: <n>  (WARNING)

  Report: .planning/<name>/verification.md
```

**Next-steps logic:**

| State | Suggest |
|---|---|
| All VERIFIED, no BLOCKER, no WARNING | `Next: /feature-done <name> — Generate PR summary` |
| BLOCKER count > 0 | `Next: Describe the fixes, then /build <name> to add FIX tasks` |
| WARNING only (no BLOCKER) | `Next: Review UNCERTAIN items manually. If acceptable, /feature-done <name>.` |
| No `must_haves` blocks (legacy) | `Next: This is a legacy feature — /feature-done <name> if work is complete.` |

## Rules

- **READ-ONLY.** Never modify source, never modify tasks.md, never commit.
- **Trust `must_haves`, not status markers.** A `[x]` task can still ship a stub.
- **Do not invent truths.** If the story lacks a `must_haves` block, do not synthesize one — report as legacy-skipped.
- **Cite evidence with `file:line` in every VERIFIED entry.** Anything without a citation is UNCERTAIN.
- Redirect verbose grep output to `/tmp/` — only summaries land in the report.

## Output Management

```bash
grep -rn "<symbol>" src/ > /tmp/verify-<symbol>.txt 2>&1
HITS=$(wc -l < /tmp/verify-<symbol>.txt)
echo "Found $HITS reference(s) to <symbol>"
```

## Notes

- This is the lightweight MACHO counterpart to GSD's `gsd-verifier`. Same methodology, ~60 lines instead of 900.
- The `must_haves` schema is documented in `/build` STEP 3. If a story author forgot the block, `/feature-verify` will skip that story and note it as `no must_haves — story not verifiable`.
- For features with `contract.yaml`, /feature-verify will additionally cross-check that every contract endpoint has a corresponding `truths` entry somewhere in tasks.md (optional v2 check).
