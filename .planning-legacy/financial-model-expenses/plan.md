# Financial Model Redesign — Phase 6: Expense Tracking

> Generated by /prd-refine on 2026-04-05
> Design doc: `hussle-app-dispatch-api/docs/designs/financial-model-redesign.md` (Section 10, Appendix A3, A7, A8)
> Depends on: `financial-model-schema` (Plan 2 complete — tables exist)

## Problem

The app has no individual expense tracking. Only `TruckExpense` exists — monthly aggregates per vehicle used for CPM estimation. Dispatchers and drivers can't log fuel stops, maintenance, tolls, or other costs. Settlements (Phase 7) need real expense data to generate accurate pay statements. IFTA (Phase 8) needs fuel entries with state and gallons. The accounting UI (Phase 9 Part B) needs expense CRUD endpoints to display.

## Solution Overview

Build a new `src/expenses/` module with full CRUD for individual expenses and recurring expense templates. Migrate `TruckExpense` data to `RecurringExpense`. Add driver-portal expense endpoints so drivers can log their own costs. Wire CPM calculation to use new tables.

## Capabilities

### Must Have (P0)

- Expense CRUD (create, list with filters/pagination/sort, get by ID, update, soft delete)
- Fuel entry validation: 2-of-3 rule (amount, gallons, pricePerGallon) with server-side auto-calc of third field
- Fuel entries require `state` (IFTA) and default `fuelType` to DIESEL
- Receipt upload via existing S3 presign/confirm pattern
- RecurringExpense CRUD (create, list, update, deactivate)
- Manual recurring expense generation trigger endpoint
- TruckExpense → RecurringExpense data migration
- Update CPM calculation to query RecurringExpense (estimated) and Expense (actual)
- Driver portal expense access (create own, view own, edit own pre-approved expenses)
- Soft delete with `deletedAt` on Expense model (schema migration)
- Publish domain events on expense changes for CPM invalidation

### Nice to Have (P1)

- Expense summary/aggregation endpoint (totals by category, by period)
- Bulk expense creation (e.g., import from CSV)
- Expense approval workflow (driver submits → dispatcher approves)

## User Flows

### Dispatcher Creates an Expense

1. Dispatcher selects a vehicle from the fleet
2. Opens expense entry form, selects category (e.g., MAINTENANCE)
3. Enters amount, date, vendor, optional notes
4. Optionally uploads receipt photo
5. System creates expense record, publishes `expense.created` event
6. CPM invalidation subscriber marks vehicle CPM as stale

### Dispatcher Logs a Fuel Entry

1. Dispatcher selects category FUEL
2. Enters 2 of 3: amount, gallons, pricePerGallon — third auto-calculated
3. Enters state (required for IFTA), fuelType defaults to DIESEL
4. Optionally enters odometer reading
5. System validates fuel-specific rules and creates expense

### Driver Logs an Expense (Driver Portal)

1. Driver accesses expense entry via driver portal (vehicle-scoped token)
2. Enters expense details (category, amount, date, optional receipt)
3. System creates expense scoped to driver's assigned vehicle
4. Driver can view and edit their own expenses (pre-approved only)
5. Driver cannot delete expenses

### Dispatcher Manages Recurring Expenses

1. Dispatcher sets up recurring expense for a vehicle (e.g., TRUCK_PAYMENT, $2,400/month)
2. Specifies frequency (WEEKLY or MONTHLY) and optional dayOfMonth
3. When ready, triggers generation endpoint to create Expense records from active templates
4. Generated expenses have `source = RECURRING` and `isRecurring = true`
5. Idempotent: skips already-generated entries via `lastGeneratedAt`

### Receipt Upload

1. Client requests presigned URL: `POST /expenses/:id/receipt`
2. Server creates presigned S3 PUT URL, returns { presignedUrl, expiresIn }
3. Client uploads file directly to S3
4. Client confirms: `POST /expenses/:id/receipt/confirm`
5. Server verifies file exists in S3, stores URL in `receiptUrl`

Generates Expense records from all active RecurringExpense entries for the vehicle. Idempotent via `lastGeneratedAt`.

### Key Decisions

- **Soft delete over hard delete** — expenses are referenced by settlements (SettlementLineItem.referenceId) and IFTA reports. Deleting would break data integrity. All queries filter `deletedAt IS NULL`.
- **Manual generation trigger, no cron** — no scheduler infrastructure exists yet. A `POST /recurring-expenses/generate` endpoint lets dispatchers (or a future cron job) trigger generation. Simpler to build, test, and debug.
- **Vehicle-scoped driver token** — current driver portal tokens are load-scoped. Add a `VEHICLE` token type to enable broader driver access for expense logging without granting full org access.
- **Fuel 2-of-3 rule** — server-side validation and auto-calc. If amount + gallons provided, derive pricePerGallon. If amount + pricePerGallon, derive gallons. If gallons + pricePerGallon, derive amount.
- **CPM: estimated vs actual** — `vehicleCpmQueryPrisma` already returns estimated CPM from RecurringExpense. Add an `actualCpmQuery` that sums real Expense records over a period divided by actual miles. Load-level `estimatedCost` prefers actual CPM when sufficient data exists (30+ expenses for the vehicle), falls back to estimated.
- **TruckExpense migration** — data migrated to RecurringExpense, old vehicle expense endpoints deprecated (not removed immediately — removal in Migration B plan).

### Data Migration: TruckExpense → RecurringExpense

1. Create Prisma data migration script
2. For each `TruckExpense` row:
   - Map `expenseKey` → `RecurringExpense.label`
   - Map `monthlyAmount` → `RecurringExpense.amount`
   - Map `category` to nearest granular `ExpenseCategory` (FIXED→INSURANCE, VARIABLE→MAINTENANCE, etc.)
   - Set `frequency = MONTHLY`, `isActive = true`
   - Set `organizationId` from vehicle's organization
3. Skip duplicates (unique constraint on vehicleId + label)
4. Update `calculateCpm` query layer to prefer RecurringExpense over TruckExpense
5. Mark old `/vehicles/:id/expenses` endpoints as deprecated (not removed yet)

## Acceptance Criteria

### Expense CRUD
- [ ] `POST /expenses` creates an expense record linked to organization, vehicle, and optional driver
- [ ] `GET /expenses?vehicleId=X` returns paginated expenses filtered by vehicleId, with support for dateFrom, dateTo, category, hasReceipt, source, sort, order
- [ ] `GET /expenses/:id` returns full expense detail including fuel fields
- [ ] `PATCH /expenses/:id` updates expense fields; returns 404 for soft-deleted expenses
- [ ] `DELETE /expenses/:id` sets `deletedAt` timestamp; does not physically remove the row
- [ ] Soft-deleted expenses are excluded from all list/get queries
- [ ] All endpoints enforce organization scoping via request context

### Fuel Entry Validation
- [ ] When `category = FUEL`, at least 2 of { amount, gallons, pricePerGallon } are required
- [ ] Missing third field is auto-calculated server-side (amount = gallons × pricePerGallon)
- [ ] `state` is required when `category = FUEL`
- [ ] `fuelType` defaults to `DIESEL` when `category = FUEL` and not provided
- [ ] Non-fuel expenses reject fuel-specific fields (gallons, pricePerGallon, fuelType, odometer)

### Receipt Upload
- [ ] `POST /expenses/:id/receipt` returns a presigned S3 PUT URL with configurable expiry
- [ ] `POST /expenses/:id/receipt/confirm` verifies file exists in S3 and stores URL in `receiptUrl`
- [ ] Receipt storage key follows pattern `{orgId}/expenses/{expenseId}/receipt.{ext}`
- [ ] Returns 404 if expense doesn't exist or is soft-deleted

### Recurring Expenses
- [ ] `POST /recurring-expenses` creates a recurring expense template with category, label, amount, frequency, optional dayOfMonth
- [ ] Unique constraint enforced: one label per vehicle (409 Conflict on duplicate)
- [ ] `PATCH /recurring-expenses/:id` updates template fields
- [ ] `DELETE /recurring-expenses/:id` sets `isActive = false` (does not delete)
- [ ] `GET /recurring-expenses?vehicleId=X` returns active recurring expenses for a vehicle
- [ ] `POST /recurring-expenses/generate` creates Expense records from all active RecurringExpense entries for the specified vehicle
- [ ] Generation is idempotent: skips entries where `lastGeneratedAt` is within the current period
- [ ] Generated expenses have `source = RECURRING` and `isRecurring = true`
- [ ] `lastGeneratedAt` is updated on the RecurringExpense after generation

### Driver Portal Access
- [ ] A new `VEHICLE` token type is added to `TrackingToken` for vehicle-scoped driver access
- [ ] `POST /driver-portal/expenses` creates an expense scoped to the driver's assigned vehicle
- [ ] `GET /driver-portal/expenses` returns only expenses for the driver's vehicle
- [ ] `PATCH /driver-portal/expenses/:id` allows editing only the driver's own expenses
- [ ] Driver cannot delete expenses (no DELETE endpoint on driver portal)
- [ ] Driver portal expense endpoints reject requests with invalid or expired tokens

### Data Migration
- [ ] Prisma data migration script converts all `TruckExpense` rows to `RecurringExpense` records
- [ ] Migration maps `expenseKey` → `label`, `monthlyAmount` → `amount`, `category` → nearest granular ExpenseCategory
- [ ] Migration handles duplicates gracefully (skip on unique constraint violation)
- [ ] Old `/vehicles/:id/expenses` endpoints continue to work but are marked deprecated

### CPM Integration
- [ ] `vehicleCpmQueryPrisma` continues to return estimated CPM from RecurringExpense (existing behavior)
- [ ] New `actualCpmQuery` calculates CPM from real Expense records over a configurable period
- [ ] `expense.created`, `expense.updated`, `expense.deleted` events trigger CPM cache invalidation
- [ ] CPM category mapping updated from old meta-categories to granular-to-FIXED/VARIABLE mapping

### Schema Migration
- [ ] Prisma migration adds `deletedAt DateTime?` to the Expense model
- [ ] Migration is non-destructive (no data loss, backward compatible)

### Domain Events
- [ ] `expense.created`, `expense.updated`, `expense.deleted` events published on respective operations
- [ ] `recurring-expense.generated` event published after batch generation
- [ ] Events follow existing event bus pattern (RabbitMQ)
