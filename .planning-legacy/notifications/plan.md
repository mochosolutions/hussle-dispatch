# Track 11 · Notifications

> Generated by /prd-refine on 2026-04-24

## Problem

The notification system has two gaps before MVP verification:

1. **Tenant isolation breach** — `GET /notifications/loads/:loadId/history` and the override repo's `findByLoadId` query by `loadId` alone, allowing any authenticated user to read another org's notification logs and overrides.
2. **Document upload notifications not wired** — the `DOCUMENT_UPLOADED` trigger exists in the enum and customer default settings, but no subscriber handles `document.confirmed` events to actually send email/SMS to the customer.

## Solution Overview

Fix the tenant scoping vulnerability, wire the document-upload notification pipeline end-to-end (event enrichment → subscriber → content builder → email template → SMS template), and verify all three notification triggers (status change, check call, document upload) work with real Twilio + SES, honoring customer opt-out preferences.

## Capabilities

### Must Have (P0)

- Tenant-scoped notification history: `findByLoadId` on both log and override repos requires `organizationId`; controller passes it from `req.scope`
- Tenant-scoped notification overrides: same fix for `LoadNotificationOverrideRepoPort.findByLoadId`
- `document.confirmed` event enriched with `loadId`, `customerId`, `loadNumber`, `contactEmail`, `contactPhone`, `contactCcEmails` at the source (`documentService.confirm()`)
- Notification subscriber handles `document.confirmed` → resolves settings → sends email + SMS
- Document upload email template (React Email in `hussle-emails`)
- Document upload SMS template
- Document upload content builder (`buildDocumentUploadedContent`)
- Customer notification preferences respected (opt-out silences the channel)

### Nice to Have (P1)

- None — all items are P0 for MVP

## User Flows

### Document Upload Notification

1. Driver uploads a document (e.g., BOL) via carrier portal
2. `documentService.confirm()` fires `document.confirmed` with enriched payload including load context
3. Notification subscriber receives event, resolves customer settings + load overrides for `DOCUMENT_UPLOADED` trigger
4. If email enabled: renders `DocumentUploadedEmail` with load#, doc type, tracking link → sends via SES
5. If SMS enabled: renders SMS body with load#, doc type → sends via Twilio
6. Notification log entry created for audit

### Tenant-Scoped Notification History

1. Dispatcher opens load detail → notification history tab
2. `GET /notifications/loads/:loadId/history` passes `organizationId` from `req.scope`
3. Repo queries with `load: { organizationId }` join — only returns logs for loads belonging to that org
4. Same scoping applies to override reads

### Opt-Out Flow

1. Customer has `DOCUMENT_UPLOADED` + `EMAIL` disabled in their settings
2. Document is uploaded for their load
3. `resolveNotificationSettings` returns empty configs for that trigger+channel
4. No email sent; SMS still fires if SMS channel is enabled

## Technical Context

### Existing Code to Reuse

- `resolveNotificationSettings()` (`notifications/services/resolveNotificationSettings.ts`) — already handles merging customer settings + load overrides for any trigger
- `sendNotification()` in `notificationSubscriber.ts` — handles EMAIL/SMS dispatch + log creation; reuse for document upload
- `getOrCreateTrackingUrl()` in `notificationSubscriber.ts` — generates customer tracking links
- `StatusChangeEmail` / `CheckCallEmail` in `hussle-emails` — pattern for new React Email template
- `statusChangeSms.ts` / `checkCallSms.ts` — pattern for new SMS template
- `loadTimestampSubscriber.ts` — existing `document.confirmed` subscriber (shows the event shape and guard pattern)

### Key Decisions

- **Enrich event at source** — `documentService.confirm()` will look up the load record and include `loadId`, `customerId`, `loadNumber`, and contact info in the `document.confirmed` payload. This keeps the notification subscriber simple and consistent with how `load.status.changed` and `load.checkcall.logged` pass data.
- **Notification content** — Document upload notifications show load number, document type, and tracking link. Mirrors the status change pattern.
- **Tenant scoping via load join** — Repos scope `findByLoadId` by joining through `load: { organizationId }` (mirrors `invoiceRepositoryPrisma` pattern). This is a data-level fix, not middleware.
- **No new API endpoints** — Only internal wiring changes. The notification history endpoint already exists.

## Acceptance Criteria

- `GET /notifications/loads/:loadId/history` scoped by `organizationId` — cross-org request returns empty array, not another org's logs
- `GET /notifications/loads/:loadId/overrides` scoped by `organizationId` — cross-org request returns empty array
- Regression tests prove cross-org reads return empty for both endpoints
- When a load document is confirmed and customer has `DOCUMENT_UPLOADED` + `EMAIL` enabled, an email is sent with load number, document type, and tracking link
- When a load document is confirmed and customer has `DOCUMENT_UPLOADED` + `SMS` enabled, an SMS is sent with load number and document type
- When customer has `DOCUMENT_UPLOADED` disabled for a channel, that channel does not fire
- `document.confirmed` event for non-load entity types (e.g., carrier documents) does NOT trigger customer notifications
- Notification log entry created for each sent document upload notification
- SMS delivery verified end-to-end with real Twilio (staging)
- All three triggers (STATUS_CHANGE, CHECK_CALL, DOCUMENT_UPLOADED) verified: enable both channels → confirm both fire → disable one → confirm silenced

- Retry/queue for failed notifications (post-MVP reliability)
- Customer portal notification preferences UI (customer portal is post-MVP)
