# Financial Model — Settlements

> Generated by /prd-refine on 2026-04-05
> Design doc: `hussle-app-dispatch-api/docs/designs/financial-model-redesign.md` (Section 11, Appendix A4, A5, B5)
> Depends on: `financial-model-calculations` (Plan 3) + `financial-model-expenses` (Plan 4)

## Problem

Dispatchers have no way to generate, review, or pay out settlements for company drivers or leased carriers. Loads are delivered and invoiced, but the "money out" side — calculating net earnings, deducting dispatch fees and expenses, and producing a settlement document — is entirely manual. This blocks weekly payroll for company drivers and payout reconciliation for leased carriers.

## Solution Overview

Build a `settlements` module that generates periodic settlement statements, supports a DRAFT → APPROVED → PAID workflow, and produces PDF settlement documents. Settlements aggregate delivered loads for a driver/carrier over a date range, apply dispatch fee and expense deductions, and calculate net earnings.

## Capabilities

### Must Have (P0)

- Manual settlement generation for a carrier/driver + date range
- Auto-draft settlement generation via weekly scheduled job (Sunday 11 PM, configurable)
- Settlement line items: LOAD_REVENUE, DISPATCH_FEE, ACCESSORIAL, EXPENSE, ADJUSTMENT
- Settlement workflow: DRAFT → APPROVED → PAID, with DISPUTED path back to DRAFT
- Idempotent generation (skip if settlement exists for same entity + period)
- Leased carrier expense inclusion toggle (per-carrier `includeExpensesOnSettlement` flag)
- EXTERNAL_CARRIER excluded from settlements (dispatch fee invoice only)
- Settlement PDF generation (React Email template, mirrors invoice PDF pattern)
- Settlement list with filters (status, carrier, driver, date range)
- Settlement detail with line items
- Manual ADJUSTMENT line items on DRAFT settlements (add/edit/delete)

### Nice to Have (P1)

- Email delivery of settlement PDFs to driver/carrier contact email (mirrors `invoiceEmailService` pattern)
- Settlement number sequence (SETT-YYYYMMDD-XXXX)
- Per-mile metrics on PDF (rev/mi, cost/mi, profit/mi)
- Settlement summary totals on list view

## User Flows

### Manual Generation

1. Dispatcher navigates to settlements or a carrier/driver detail
2. Clicks "Generate Settlement" — selects carrier, optionally driver/vehicle, period start/end
3. System validates: carrier is COMPANY_ASSET or LEASED_CARRIER, period has delivered loads
4. System creates DRAFT settlement with computed line items
5. Dispatcher reviews line items, optionally adds ADJUSTMENT line items
6. Dispatcher approves → status moves to APPROVED
7. Dispatcher records payment (method, reference) → status moves to PAID

### Auto-Draft (Weekly)

1. Scheduled job fires Sunday 11 PM (org-configurable)
2. Publishes `settlement.generate` event per eligible driver/carrier with delivered loads in Mon–Sun window
3. Subscriber generates DRAFT settlements with line items
4. Dispatchers see drafts Monday morning on settlement list
5. Same review/approve/pay flow as manual

### Email Delivery

1. Dispatcher opens an APPROVED or PAID settlement
2. Clicks "Send Settlement" — system resolves recipient email from driver/carrier contact
3. System generates settlement PDF, renders email via `@hussle/emails` template, attaches PDF
4. Email sent via shared `notificationService`
5. Settlement records `sentAt` and `sentToEmail`

### Dispute Flow

1. Driver/carrier flags issue with a settlement
2. Dispatcher disputes settlement (requires `disputeReason`) → status returns to DRAFT
3. Dispatcher corrects line items (add/edit/delete ADJUSTMENTs)
4. Re-approves when resolved

## Data Requirements

### Existing Models (already in schema)

**Settlement** — `prisma/schema.prisma:1267`
- `id`, `organizationId`, `settlementNumber`, `carrierId`, `driverId?`, `vehicleId?`
- `periodStart`, `periodEnd`
- `grossRevenue` (Decimal 12,2), `totalMiles` (Int)
- `dispatchFeeTotal` (Decimal 10,2), `expensesTotal` (Decimal 10,2), `netEarnings` (Decimal 12,2)
- `status` (DRAFT | APPROVED | PAID | DISPUTED)
- `approvedAt?`, `approvedByUserId?`, `paidAt?`, `paymentMethod?`, `paymentReference?`, `disputeReason?`

**SettlementLineItem** — `prisma/schema.prisma:1299`
- `id`, `settlementId`, `type` (LOAD_REVENUE | DISPATCH_FEE | EXPENSE | ACCESSORIAL | ADJUSTMENT)
- `referenceId?` (loadId or expenseId), `description`, `miles?`, `amount` (Decimal 10,2), `date`

**Carrier.includeExpensesOnSettlement** — `prisma/schema.prisma:531` (Boolean, default false)

### Schema Addition (migration required)

Add email tracking fields to `Settlement` model:

- `sentAt` (DateTime?) — when settlement email was sent
- `sentToEmail` (String?) — recipient email address

All other models and enums are already created from Phase 2 (financial-model-schema).

## API/Interface Changes

### New Endpoints

| Method | Path | Description | Status |
|--------|------|-------------|--------|
| `GET` | `/api/v1/settlements` | List settlements (filtered by status, carrierId, driverId, periodStart, periodEnd) | 200 |
| `GET` | `/api/v1/settlements/:id` | Get settlement with line items | 200 / 404 |
| `POST` | `/api/v1/settlements/generate` | Manual generation — creates DRAFT | 201 / 400 / 409 |
| `PATCH` | `/api/v1/settlements/:id/approve` | Approve a DRAFT settlement | 200 / 400 / 404 |
| `PATCH` | `/api/v1/settlements/:id/pay` | Record payment on APPROVED settlement | 200 / 400 / 404 |
| `PATCH` | `/api/v1/settlements/:id/dispute` | Dispute APPROVED → DRAFT (requires disputeReason) | 200 / 400 / 404 |
| `GET` | `/api/v1/settlements/:id/pdf` | Download settlement PDF | 200 / 404 |
| `POST` | `/api/v1/settlements/:id/adjustments` | Add ADJUSTMENT line item to DRAFT | 201 / 400 / 404 |
| `PATCH` | `/api/v1/settlements/:id/adjustments/:lineItemId` | Edit ADJUSTMENT line item | 200 / 400 / 404 |
| `DELETE` | `/api/v1/settlements/:id/adjustments/:lineItemId` | Delete ADJUSTMENT line item | 204 / 400 / 404 |
| `POST` | `/api/v1/settlements/:id/send` | Email settlement PDF to driver/carrier contact | 200 / 400 / 404 |

- **`InvoicePdfTemplate.tsx`** + `invoiceTemplateStyles.ts` — pattern for React Email PDF templates
- **`pdfGenerationService.ts`** — shared PDF rendering pipeline (React Email → HTML → PDF via puppeteer/react-pdf)
- **`invoiceEmailService.ts`** — pattern for email delivery with PDF attachment + `@hussle/emails` template rendering
- **`notificationService`** (`src/shared/notifications/`) — shared email sending infrastructure

- **`calculateLoadFinancials()`** (`src/shared/financials.ts`) — already computes `companyMargin`, `carrierPayout`, `driverPay` per load
- **`src/shared/financials.ts` Decimal.js usage** — reuse banker's rounding (ROUND_HALF_EVEN) for settlement totals
- **Event dispatcher pattern** — existing `eventDispatcher` + subscriber model for scheduled generation
- **`node-cron`** — already a dependency for scheduled tasks

### Key Decisions

- **No schema migration needed** — Settlement and SettlementLineItem models exist from Phase 2
- **EXTERNAL_CARRIER excluded** — they receive dispatch fee invoices, not settlements
- **OWNER_OPERATOR excluded** — decision X-001 carries forward (not supported in current release)
- **Expense inclusion is per-carrier** — `Carrier.includeExpensesOnSettlement` boolean drives whether EXPENSE line items appear
- **ADJUSTMENT line items only on DRAFT** — cannot modify approved/paid settlements
- **Idempotency by entity + period overlap** — check for existing settlement covering same carrier/driver and overlapping date range before generating
- **Settlement totals are computed from line items** — `grossRevenue`, `dispatchFeeTotal`, `expensesTotal`, `netEarnings` are derived sums stored on the Settlement record for query performance
- **Fire-and-forget event dispatch** — weekly cron publishes events; subscriber handles generation per driver/carrier independently (one failure doesn't block others)

## Acceptance Criteria

### Generation

- [ ] `POST /api/v1/settlements/generate` with valid carrierId (COMPANY_ASSET) + period creates a DRAFT settlement with LOAD_REVENUE + DISPATCH_FEE + ACCESSORIAL + EXPENSE line items for delivered loads in the period
- [ ] `POST /api/v1/settlements/generate` with LEASED_CARRIER + `includeExpensesOnSettlement: false` creates settlement with LOAD_REVENUE + DISPATCH_FEE + ACCESSORIAL only (no EXPENSE items)
- [ ] `POST /api/v1/settlements/generate` with LEASED_CARRIER + `includeExpensesOnSettlement: true` includes EXPENSE line items
- [ ] `POST /api/v1/settlements/generate` with EXTERNAL_CARRIER returns 400 error
- [ ] Duplicate generation for same carrier/driver + overlapping period returns 409 Conflict
- [ ] Period with no delivered loads returns 400 (no empty settlements created)
- [ ] Settlement `grossRevenue` equals sum of LOAD_REVENUE line item amounts
- [ ] Settlement `dispatchFeeTotal` equals sum of DISPATCH_FEE line item amounts (absolute value)
- [ ] Settlement `expensesTotal` equals sum of EXPENSE line item amounts (absolute value)
- [ ] Settlement `netEarnings` equals `grossRevenue - dispatchFeeTotal - expensesTotal`
- [ ] Settlement `totalMiles` equals sum of loaded miles across settlement loads
- [ ] All Decimal calculations use Decimal.js with banker's rounding (ROUND_HALF_EVEN)

### Workflow

- [ ] `PATCH /:id/approve` on DRAFT settlement transitions to APPROVED, sets `approvedAt` and `approvedByUserId`
- [ ] `PATCH /:id/approve` on non-DRAFT returns 400
- [ ] `PATCH /:id/pay` on APPROVED settlement transitions to PAID, records `paymentMethod`, `paymentReference`, `paidAt`
- [ ] `PATCH /:id/pay` on non-APPROVED returns 400
- [ ] `PATCH /:id/dispute` on APPROVED settlement transitions to DISPUTED, records `disputeReason`
- [ ] `PATCH /:id/dispute` on non-APPROVED returns 400
- [ ] DISPUTED settlement can be re-approved via `PATCH /:id/approve` (only after updating to DRAFT — or DISPUTED acts as reviewable DRAFT)

### Adjustments

- [ ] `POST /:id/adjustments` adds ADJUSTMENT line item to DRAFT settlement and recalculates totals
- [ ] `PATCH /:id/adjustments/:lineItemId` edits ADJUSTMENT description/amount/date and recalculates totals
- [ ] `DELETE /:id/adjustments/:lineItemId` removes ADJUSTMENT and recalculates totals
- [ ] Adjustment operations on non-DRAFT settlements return 400
- [ ] Only ADJUSTMENT-type line items can be edited/deleted (non-ADJUSTMENT returns 400)

### List & Detail

- [ ] `GET /api/v1/settlements` returns paginated list filtered by status, carrierId, driverId, periodStart, periodEnd
- [ ] `GET /api/v1/settlements/:id` returns settlement with all line items
- [ ] All endpoints enforce organizationId scoping
- [ ] All endpoints require authentication via `appAuth` middleware

### PDF

- [ ] `GET /:id/pdf` returns a PDF document for the settlement
- [ ] PDF header shows: settlement number, period dates, driver/carrier name, truck info
- [ ] PDF revenue section lists each load with route, miles, delivery date, amount
- [ ] PDF deductions section lists dispatch fees and expenses by category
- [ ] PDF totals section shows gross revenue, total deductions, net earnings
- [ ] PDF includes per-mile metrics: revenue/mile, cost/mile, net/mile

### Email Delivery

- [ ] `POST /:id/send` on APPROVED or PAID settlement generates PDF, renders email via `@hussle/emails` `renderSettlementEmail`, and sends via `notificationService`
- [ ] Email attaches the settlement PDF as `Settlement_{settlementNumber}.pdf`
- [ ] Recipient email resolved from driver contact (COMPANY_ASSET) or carrier primary contact (LEASED_CARRIER)
- [ ] `POST /:id/send` on DRAFT or DISPUTED settlement returns 400
- [ ] Settlement records `sentAt` and `sentToEmail` after successful send
- [ ] New `settlementEmail` template added to `hussle-emails` package with settlement number, period, carrier/driver name, net earnings amount

### Auto-Draft (Scheduled)

- [ ] Scheduled job publishes `settlement.generate` events for each eligible driver/carrier with delivered loads in the past Mon–Sun
- [ ] Subscriber generates DRAFT settlements from events
- [ ] Already-settled loads are not double-counted (idempotency check)
- [ ] One failed generation does not block others (independent per driver/carrier)
- [ ] Job schedule defaults to Sunday 11 PM, uses org settings if configured

## Out of Scope

- UI for settlements (separate `financial-model-ui` plan)
- Batch payment processing (pay multiple settlements at once)
- OWNER_OPERATOR settlements (excluded per decision X-001)
- Settlement approval permissions beyond `appAuth` (no role-based gating for now)
- Export to accounting systems (QuickBooks, etc.)
- Settlement history/audit log beyond Prisma timestamps
