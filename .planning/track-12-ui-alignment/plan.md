# Track 12 — UI Alignment (Entity Pages)

> Generated by /prd-refine on 2026-04-27
> Source: `docs/tasks/mvp-plan.md` Track 12

## Problem

The `mvp-plan.md` Track 12 spec was written before most of the alignment work landed. An audit on 2026-04-27 (during this refinement) found that all 6 entity list pages already use the canonical `FilterBar + ListKpiBar + NewDataGrid + PageWrapper + ListLayout` pattern with clickable rows; all 6 detail pages already use `DetailLayout`; ~30 of 30 drawers already use `FormDrawer`.

What remains is a small punch-list of stragglers — places where the canonical patterns weren't adopted. This track closes those gaps and verifies consistency.

## Refined Scope (from /prd-refine 2026-04-27)

| Question | Decision |
|---|---|
| Track scope | Audit + targeted fixes only. No rebuilds, no visual polish, no rename. |
| Detail shell name | Keep existing `DetailLayout` — `DetailPageShell` in mvp-plan.md was outdated naming. |
| Inline-autocomplete drawer opens (PlaceTypeahead, CustomerAutocomplete) | Migrate to drawer registry for consistency. |

## Solution Overview

Three small, mostly mechanical migrations:

1. **Drawer-registry adoption** — replace local `useState` drawer-open patterns at three sites with the existing `useDrawerActions` + Redux `uiSlice` registry.
2. **LoadRouteDrawer → FormDrawer** — the only Formik+EditDrawer drawer that hasn't been refactored to use the `FormDrawer` wrapper.
3. **Verification audit** — produce a checklist confirming each entity (Carriers, Drivers, Vehicles, Customers, Contacts, Places) hits the canonical pattern on list, detail, and drawers. Surface any newly-discovered gaps.

### 12.UI.1 — Migrate `NotificationOverrideDrawer` open to drawer registry

**Current:** `hussle-app-dispatch-ui/src/features/load/components/LoadDetailPage/NotificationTab/index.tsx:101` uses `const [drawerOpen, setDrawerOpen] = useState(false);` and renders `<NotificationOverrideDrawer open={drawerOpen} ... />` directly.

**Target:** open via `useDrawerActions().openDrawer({ type: 'notificationOverride', props: { ... } })`. Register the drawer type in the global drawer registry. Remove the `open`/`onClose` props from the consumer; they're handled by the registry.

**Drawer registry pattern reference:** see `hussle-app-dispatch-ui/src/features/ui/hooks/useDrawerActions.ts` and existing registered drawers (look for `registerDrawer` calls). Follow the same registration shape used by, e.g., `LoadCheckCallDrawer`.

### 12.UI.2 — Migrate `PlaceTypeahead` create-drawer open to registry

**Current:** `hussle-app-dispatch-ui/src/features/place/components/PlaceTypeahead/index.tsx:45` uses `const [createDrawerOpen, setCreateDrawerOpen] = useState(false);`.

**Target:** open the create drawer via `useDrawerActions().openDrawer({ type: 'placeCreate', props: { onCreated: (place) => ... } })`. The `onCreated` callback (currently triggered after submit) needs to be supported via the drawer registry's prop-passing mechanism.

**Risk:** the autocomplete is rendered in many places; verify the registered drawer can carry the `onCreated` callback through Redux without serialization issues. If the registry can't serialize callbacks (likely — Redux can't), pass an `onCreatedActionType` enum or use a temporary subscriber pattern. Spell out the chosen approach in the implementation.

### 12.UI.3 — Migrate `CustomerAutocomplete` create-drawer open to registry

**Current:** `hussle-app-dispatch-ui/src/features/customer/components/CustomerAutocomplete/index.tsx:74` — same pattern as 12.UI.2.

**Target:** same approach as 12.UI.2 with `customerCreate` drawer type.

### 12.UI.4 — Migrate `LoadRouteDrawer` to `FormDrawer`

**Current:** `hussle-app-dispatch-ui/src/features/load/components/LoadRouteDrawer/index.tsx` (293 lines) uses `Formik` + `EditDrawer` directly with manual footer/header/dirty handling.

**Target:** wrap in `FormDrawer<RouteFormValues>` from `mocho/components/FormDrawer`. Move the form fields (currently rendered inside `<Formik>{(formik) => ...}`) to the `FormDrawer` render-prop child. Drop manual `EditDrawer` usage, drop manual cancel/submit footer (FormDrawer provides them), drop manual dirty tracking (FormDrawer + EditDrawer pass `isDirty={dirty}` and show ConfirmDialog automatically).

**Watch for:** `FieldArray` usage inside the existing Formik form must continue to work — `FormDrawer` exposes `formikProps` to its children, so `FieldArray` access stays the same. Validation schema, initialValues, onSubmit shape all transfer 1:1.

## Technical Context

### Existing Code to Reuse

- `mocho/components/FormDrawer` (`hussle-app-dispatch-ui/src/mocho/components/FormDrawer/index.tsx`) — Formik+EditDrawer wrapper with built-in cancel/submit footer and `isDirty`-driven discard confirmation. **The migration target for 12.UI.4.**
- `components/EditDrawer` (`hussle-app-dispatch-ui/src/components/EditDrawer/index.tsx`) — drawer chrome with `isDirty` prop wired to `ConfirmDialog`. Used internally by `FormDrawer`; not directly touched by this track.
- `features/ui/hooks/useDrawerActions.ts` — `openDrawer({ type, props })` / `closeDrawer()` over Redux `uiSlice`. **The migration target for 12.UI.1–3.**
- `features/ui/store/reducers/uiSlice.ts` — drawer-state slice; new drawer types registered here.
- Existing canonical references: `LoadCheckCallDrawer` (registry-opened), `CompanyInfoDrawer` / `DispatchTermsDrawer` (FormDrawer adopters).

### Key Decisions

- **No rebuilds.** Every entity already uses the canonical components. `mvp-plan.md` Track 12 spec predates the actual landing.
- **No `DetailPageShell` rename.** `DetailLayout` is the canonical name in this codebase. `mvp-plan.md` will be updated as a doc-only fix in this track.
- **Audit-first for non-FormDrawer drawers.** After reading the four candidate drawers, only `LoadRouteDrawer` is a true Formik form. The other three (`CustomerCompanyInfoDrawer`, `ContactEditDrawer`, `loadintelligence/DetailDrawer`) are wrappers or display-only — explicitly excluded.
- **Drawer-registry callback marshalling** (12.UI.2 / 12.UI.3): Redux can't serialize callbacks. Implementation must choose between (a) registering a temporary action-type subscriber, (b) holding the callback in a non-serializable ref accessible by drawer slug, or (c) routing the success effect through Redux state (e.g. autocomplete listens for the "place created" action). Decision to be made during implementation; flag if the chosen approach leaks into shared code.

6. New audit report `.planning/track-12-ui-alignment/audit-report.md` exists with the 6×4 matrix populated. Any newly-discovered ❌ entries are listed under "Follow-ups (not in this track)".
