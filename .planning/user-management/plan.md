# User Management

> Generated by /prd-refine on 2026-03-25

## Problem

Admins have no way to manage their team from the app. They can't invite users, change roles, or remove members. There are also no guardrails around subscription limits — a TRIAL org can add unlimited users and trucks with no enforcement.

## Solution Overview

Add a Team Management tab to the existing Settings page where admins can invite users, view members, change roles, and deactivate members. Enforce configurable seat and truck limits with a hard stop and upgrade prompt. Build an invite acceptance page so invited users can set their password and join.

## Capabilities

### Must Have (P0)

- Admin can view all members and pending invitations in a Team tab on the Settings page
- Admin can invite a user by providing name, email, and role — sends an invite email
- Admin can change any member's role (admin, dispatcher, viewer, driver)
- Admin can deactivate/remove a member (soft delete)
- Last-admin guard: system prevents removing or demoting the only admin
- Invited user receives an email with a link to `/invite/accept/:token`
- Invite acceptance page: user sets password, account is created, membership is activated
- Subscription enforcement: hard stop when seat limit (3 users for TRIAL) or truck limit (3 trucks for TRIAL) is reached
- Upgrade prompt dialog shown when a limit is hit (invite blocked, vehicle creation blocked)
- Limits defined as constants that can be changed in one place

### Nice to Have (P1)

- Per-tier differentiated limits (different limits for LAUNCH, PRO, ELITE)
- Self-serve upgrade flow from the upgrade prompt
- In-app notification when a user's role is changed

## User Flows

### Invite a Team Member

1. Admin navigates to Settings > Team tab
2. Clicks "Invite Member" button
3. Dialog opens with fields: First Name, Last Name, Email, Role (dropdown)
4. Admin fills in details and submits
5. System checks seat limit — if at limit, shows upgrade prompt dialog instead
6. System creates invitation record (PENDING, 7-day expiry) and sends invite email
7. New invitation appears in the pending invitations list

### Accept an Invitation

1. Invited user receives email with "Accept Invitation" button linking to `/invite/accept/:token`
2. Page loads, verifies token is valid and not expired
3. User sees org name, their assigned role, and a form to set their password
4. User submits — Cognito user is created, membership is activated, invitation status set to ACCEPTED
5. User is redirected to login page with a success message

### Change a Member's Role

1. Admin views member list on Settings > Team tab
2. Clicks role dropdown or edit action on a member row
3. Selects new role from dropdown (admin, dispatcher, viewer, driver)
4. System checks last-admin guard — if this is the only admin and role is being changed away from admin, shows error
5. Role is updated, member list reflects the change

### Remove a Member

1. Admin clicks remove/deactivate action on a member row
2. Confirmation dialog: "Remove [Name] from [Org]? They will lose access immediately."
3. System checks last-admin guard — blocks if this is the only admin
4. Membership is soft-deleted, user's active sessions are revoked
5. Member disappears from active list

### Subscription Limit Hit

1. Admin tries to invite a user (or create a vehicle) when at the limit
2. System returns a limit error
3. Frontend shows upgrade prompt dialog: "You've reached your plan limit of [N] [users/trucks]. Upgrade your plan to add more."
4. Dialog has a dismiss button (no self-serve upgrade yet)

## Data Requirements

### New: Subscription Limits Constants

```typescript
// src/config/subscriptionLimits.ts
const SUBSCRIPTION_LIMITS = {
  maxUsers: 3,
  maxVehicles: 3,
} as const;
```

All tiers share the same config for now. Single constant file, easy to change.

- **Membership** — `id`, `userId`, `organizationId`, `role`, `status`, `invitedById`, `deleted`, `deletedAt`

### Invitation Record Enhancement

The invite service currently accepts `email` and `role`. It needs to also accept `firstName` and `lastName` so these can be passed to the Cognito user creation and the invite email.

## Technical Context

### Existing Code to Reuse

- **Invite service** (`dispatch-api/src/auth/services/invite/`) — create, verify, accept invite logic already built
- **Invite routes** (`dispatch-api/src/auth/routes/invite.ts`) — POST create, GET list, POST verify, POST accept
- **Membership repository** (`dispatch-api/src/auth/repositories/membershipRepositoryPrisma.ts`) — CRUD for memberships with tenant scoping
- **InvitationEmail template** (`hussle-emails/src/invitation/`) — existing email template and render function
- **Settings page** (`dispatch-ui/src/features/settings/`) — existing page with Formik forms, just needs a new tab
- **`authorizeUser` middleware** (`dispatch-api/src/shared/middleware/authorizeUser.ts`) — claim-based route protection
- **Auth provider** (`dispatch-api/src/auth/providers/authProvider.ts`) — Cognito `createUser` method for invite acceptance
- **Roles config** (`dispatch-api/src/config/roles.ts`) — `ADMIN`, `DISPATCHER`, `VIEWER`, `DRIVER`

### Key Decisions

- **Constants over DB config** — Subscription limits are a code constant, not a database setting. Simpler to change and deploy. Can move to DB later if needed.
- **All tiers same limits** — No per-tier differentiation yet. Single `SUBSCRIPTION_LIMITS` object.
- **Hard stop, not soft warning** — When at limit, the action is blocked entirely. No "proceed anyway" option.
- **Existing invite email** — The `InvitationEmail` template already exists. Verify it has the accept link and personalization; update if needed rather than creating a new template.
- **Session revocation on remove** — When a member is removed, their Redis sessions are revoked immediately so they lose access right away.
- **No notification on role change** — Role changes are silent; admin sees the update in the UI but the affected user gets no email or in-app alert.

## Acceptance Criteria

- Admin can view a list of all active members (name, email, role, joined date) on Settings > Team tab
- Admin can view a list of pending invitations (email, role, invited date, expiry) on Settings > Team tab
- Admin can open an invite dialog, fill in first name, last name, email, and role, and submit
- Submitting an invite creates an invitation record and sends an email to the invitee
- Invite is blocked with an upgrade prompt when active member count equals `SUBSCRIPTION_LIMITS.maxUsers`
- Vehicle creation is blocked with an upgrade prompt when active vehicle count equals `SUBSCRIPTION_LIMITS.maxVehicles`
- Invited user can visit `/invite/accept/:token`, see the org name and role, set their password, and join
- Expired or invalid tokens show an appropriate error on the accept page
- Admin can change any member's role via a dropdown/action in the member table
- Changing the last admin's role away from admin is blocked with an error message
- Admin can remove a member via a confirmation dialog; removal soft-deletes the membership and revokes sessions
- Removing the last admin is blocked with an error message
- Admin cannot remove themselves
- `SUBSCRIPTION_LIMITS` is a single constant object in `src/config/subscriptionLimits.ts` that controls both seat and truck limits
- Upgrade prompt dialog is a reusable component that displays the resource type and limit

## Out of Scope

- Per-tier differentiated limits (all tiers use same constants for now)
- Self-serve plan upgrade from the upgrade prompt
- In-app or email notification when a user's role is changed
- Bulk invite (CSV upload or multi-row form)
- Audit log entries for member management actions (audit model exists but wiring is deferred)
- Resend/revoke invitation actions (backend exists but UI is deferred to keep scope tight)
