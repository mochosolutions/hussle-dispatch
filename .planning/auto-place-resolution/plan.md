# Auto-Place Resolution

> Generated by /prd-refine on 2026-05-01
> Updated 2026-05-01 — folded in v1↔v2 comparison findings, UX corrections, and HQ bias position

## Problem

Stops on loads can be saved with no `placeId`, which leaves them with no coordinates because the `Stop` table has no lat/lng columns of its own — coords come from the joined `Place`. Today this happens whenever a dispatcher types a free-text address without picking a saved Place from the typeahead, and the form discards the captured lat/lng on submit. Two visible symptoms:

1. **Map pins missing.** Load detail / dispatch board maps render no pickup or delivery pin for those stops.
2. **Driver location pins never render.** A separate but related defect: `createDriver` doesn't geocode `currentCity`/`currentState` to populate `currentLatitude`/`currentLongitude`, so every newly created driver starts with null coords. (Fix scope: out — see *Out of Scope*. Captured here for context.)

Live verification via `compareGeocoding.ts` against AWS Location v1 vs v2 confirmed three additional issues with today's typeahead:

3. **POI search is broken on v1.** Query `walmart valley stream` returns 4 generic city-level matches with no street addresses. v2 `SearchText` returns 3 specific Walmart store locations with full addresses.
4. **Result `name` field is bloated.** v1 stuffs `"Walmart, Valley Stream, NY, 11581"` into a single string, frontend can't visually separate POI from address.
5. **No match scoring on v1.** Garbage input `"asdfasdf qweqwe"` returns a confident Florida address. v2 `Geocode` returns 0 results — the `MatchScores` field is what gates safe Place creation.

The fix is server-side: on every stop write, look up an existing Place by a normalized dedupe key built from the stop's address fields. If found, link. If not, geocode the address through AWS Location v2 and create a new Place. The Place table doubles as the persistent geocode cache (no Redis layer needed).

A prerequisite phase migrates the AWS Location SDK from the deprecated v1 (`@aws-sdk/client-location`) to the v2 family (`@aws-sdk/client-geo-places`, `-geo-routes`, `-geo-maps`). v2 is required because (a) v1 is marked previous in AWS docs, (b) v2's `Geocode` operation returns `MatchScores` and structured `StreetComponents` that the dedupe key relies on, (c) v2 removes the need for pre-created `PlaceIndex`/`RouteCalculator`/`Map` Terraform resources, and (d) v2's `SearchText` is dramatically better than v1's `SearchPlaceIndexForText` for typeahead because it handles POI/business queries correctly.

## Solution Overview

Two phases shipped as separate PRs.

**Phase 0 — AWS Location v2 SDK migration (PR 1).** Mechanical replacement of v1 SDK calls with v2 equivalents inside the existing `awsLocationProvider`. Typeahead operation switches from `SearchPlaceIndexForText` (v1) to `SearchTextCommand` (v2). Provider response shape cleans up (POI separated from address). Visual diff on map style is the main user-facing risk.

PR 1 cuts over in two stages — a **migration stage** (code switches to v2; v1 SDK package, v1 IAM statements, and v1 Terraform resources stay temporarily as fallback), then a **cleanup stage** (drop v1 SDK, delete v1 Terraform resources, remove v1 IAM statements, remove unused `geo-places:Suggest`, drop env vars). The cleanup stage **must not land** until the verification gates below pass in dev. The two stages are separate commits in the same PR (or two PRs — engineer's call) so reviewer can see them distinctly. The forward-compat IAM update applied 2026-05-01 already pre-positioned v2 permissions, so the migration stage just deploys code.

**Phase 1 — Auto-Place creation on stop write (PR 2).** Add a structured `geocode` method to `GeocodingProviderPort`. Add a `resolveStopToPlace` service that runs on every stop create AND update (symmetric path). Two-tier dedupe: cheap user-input lookup first, AWS geocode + match-or-create on miss. Soft-fill enrichment on match. Auto-created Places flagged as `source: 'AUTO'` and surface a structured warning in the load-create response when a stop fails to resolve. Frontend cleanups remove the now-redundant "Save Place" button, fix the typeahead description rendering, and surface the facility name in the form after selection.

## Capabilities

### Must Have (P0)

**Phase 0 — v2 SDK migration**

- v2 SDK packages installed (`@aws-sdk/client-geo-places`, `@aws-sdk/client-geo-routes`, `@aws-sdk/client-geo-maps`); v1 (`@aws-sdk/client-location`) removed.
- `awsLocationProvider` rewritten to use three v2 clients (places/routes/maps).
- **Typeahead operation switches from v1 `SearchPlaceIndexForText` to v2 `SearchTextCommand`.** Empirical justification: v2 `SearchText` returns POI/business results with full structured addresses (e.g., "walmart valley stream" → 3 specific Walmart store locations). v1 returns city-level fuzzy matches for the same input. `Suggest` was considered and rejected — it returns POI labels without addresses, wrong shape for a typeahead that prepopulates form fields on selection.
- **Provider response separates POI title from address fields.** `GeocodeSuggestion` gains a `name: string | null` field (POI/business name when AWS recognizes one, null otherwise). `address`/`city`/`state`/`zip`/`lat`/`lng` stay as today. Drop the synthetic `label` concatenation.
- **`AddressSearchResult.name` cleanup.** External (typeahead) result `name` field becomes `suggestion.name ?? suggestion.address` — the POI when present, the street address when not. No more bloated full-label dump.
- **ZIP normalization.** v1 returned `"02110 1802"`, v2 returns `"02110-1802"`. Provider strips ZIP+4 to ZIP5 (`zip.replace(/[^0-9]/g, '').slice(0, 5)`) before returning. Format-agnostic.
- **State code normalization.** v1 returned `"New York"`, v2 returns `"NY"`. Existing `normalizeStateCode()` helper still applies for v1 fallback paths but is no-op on v2 inputs.
- Existing port surface (`GeocodingProviderPort.searchAddresses`, `RoutingProviderPort.calculateRoute`, all `MapTileProviderPort` methods) keeps the same signatures so downstream callers don't move.
- `searchAddresses(query, limit)` accepts an optional `BiasPosition: [lng, lat]` parameter so callers can pass a ranking hint. When omitted, defaults to `[-98.5, 39.5]` (US center).
- v1 Terraform resources (`aws_location_place_index`, `aws_location_route_calculator`, `aws_location_map`) deleted; IAM policy migrated to v2 action names. The forward-compat IAM update applied 2026-05-01 added all v2 actions; PR 1 drops the v1 statements **and removes `geo-places:Suggest`** from the v2 set since we're using `SearchText` instead.
- Env vars `AWS_LOCATION_PLACE_INDEX_NAME`, `AWS_LOCATION_ROUTE_CALCULATOR_NAME`, and any map-name-related vars removed from `.env`, deploy configs, and code references.
- Map tile rendering visually equivalent (or close enough for sign-off) to v1 output.
- All existing typeahead, route distance, and map tile flows verified working end-to-end after the cutover.

**Phase 1 — Auto-Place creation: schema + dedupe**

- `Place` table has new column `unit text NULL` (suite/apartment/room indicator from `SecondaryAddressComponents`).
- `Place` table has new column `source text NOT NULL DEFAULT 'USER'` constrained to `'USER' | 'AUTO'` (CHECK constraint).
- `Stop` table has new column `resolutionStatus text NOT NULL DEFAULT 'UNRESOLVED'` constrained to `'RESOLVED' | 'UNRESOLVED' | 'AMBIGUOUS'` (CHECK constraint), btree-indexed.
- `Organization` table has new columns `headquartersLatitude Decimal(9,6) NULL` and `headquartersLongitude Decimal(9,6) NULL` for typeahead bias position. Nullable; existing orgs default to null and fall back to US center.
- New index on `Place(organizationId, source)` for typeahead-side filtering and admin-list filtering.
- New unique index on the canonical dedupe key. `unit` is nullable so use `COALESCE(unit, '')` in an expression index. If Prisma can't model this cleanly, fall back to application-level uniqueness with a non-unique multi-column index for lookup.

**Phase 1 — Auto-Place creation: server logic**

- `GeocodingProviderPort` has a new method `geocode(structured: StructuredAddressInput): Promise<GeocodeResult | null>` that calls v2 `GeocodeCommand` with `IntendedUse: 'Storage'` and `AdditionalFeatures: ['SecondaryAddresses']`.
- `searchAddresses(query, limit, biasPosition?)` reads `Organization.headquartersLat/Lng` for the requesting user's org, passes as `BiasPosition` if set, falls back to US center if null.
- New service `resolveStopToPlace(stop, organizationId)` implementing two-tier dedupe-or-create:
  1. Build dedupe key from raw stop fields → look up Place → hit, link, return.
  2. Miss → call `geocode(structured)` → reject if `MatchScores.Overall < 0.7` **OR** result `type ∉ {PointAddress, PointOfInterest, InterpolatedAddress, InferredSecondaryAddress}` → otherwise build canonical dedupe key from AWS-returned fields → look up Place → hit, link; miss, create Place using `INSERT ... ON CONFLICT DO NOTHING RETURNING *` and re-read by dedupe key if 0 rows returned (race-condition handling).
- **Type gate.** Reject `Locality`, `Region`, `District` even at score=1. These represent city/state-level matches, not addresses, and would pollute the Place table with unmappable rows. Implemented as a constant accept-set in code.
- Place dedupe key composition (in code, not a DB column — it's the lookup signature):
  ```
  (organizationId, normalize(facilityName), awsAddressNumber,
   normalize(awsStreetBaseName), awsStreetType, awsStreetPrefix,
   normalize(unit), awsRegion, awsPostalCode5)
  ```
- Place name fallback: `stop.facilityName ?? awsResult.title ?? [address, city, state, zip].filter(Boolean).join(', ')`. NOT NULL guaranteed.
- Stop-side write-through: when a stop arrives with empty `facilityName` and resolves to a Place, `Stop.facilityName` is populated from `Place.name` before save.
- Soft-fill on Place match: scoped to fields that exist on **both** Stop and Place — `contactName`, `contactPhone`, `notes`. Update only fields that are currently null on the Place; never overwrite a non-null value. Place-only fields (`appointmentRequired`, `lumperRequired`, `ppeRequired`, `is24Hours`, `facilityHours`, `facilityType`) are explicitly out of scope for soft-fill: they have no Stop-side source and are set through the Places admin UI. Verify exact overlap against current `Stop` Prisma model during implementation; widen only if additional fields actually overlap.
- `resolveStopToPlace` runs on every stop write — `createLoad`, `updateLoad`, route/assignment edits — symmetric path.
- Explicit `placeId` from request takes precedence over auto-resolution. Order of precedence: explicit `placeId` from request > auto-resolved `placeId` from address fields > null.
- **`Place.source` mutation rule:** any **user-initiated** update to a Place where `source = 'AUTO'` flips it to `'USER'` unconditionally. The flip is observed (a human touched the row), not field-compared. Enforced in the Place update endpoint (`PATCH /places/:id`) only. Server-internal writes via `resolveStopToPlace` (soft-fill, dedupe-link) explicitly do **not** flip the source — those are not user actions.
- Failure handling:
  - **Geocoder error/down:** load and stop save successfully with `placeId = null` and `resolutionStatus = 'UNRESOLVED'`. Warning logged. Structured warning attached to the load-create response.
  - **Partial address (city/state only, no street) OR result type is `Locality`/`Region`/`District`:** skip Place creation; stop saves with `resolutionStatus = 'UNRESOLVED'`.
  - **Match score below 0.7:** skip Place creation; stop saves with `resolutionStatus = 'AMBIGUOUS'`.
- Load-create and load-update API responses include `warnings: Warning[]` field. Each warning carries `code`, `stopSequence`, `message`. Codes: `STOP_NOT_GEOCODED`, `STOP_AMBIGUOUS_ADDRESS`, `STOP_PARTIAL_ADDRESS`, `GEOCODER_UNAVAILABLE`.
- Backfill script `scripts/backfillPlaces.ts` walks every stop with `placeId IS NULL AND (address IS NOT NULL OR city IS NOT NULL)`, runs `resolveStopToPlace` for each, logs per-stop outcomes (matched / created / skipped-low-confidence / skipped-partial / skipped-bad-type / failed). Idempotent. Reuses production code path.
- Backfill executed against the dev database as part of PR 2 verification.

**Phase 1 — Frontend UX changes**

Make it match saved-result format: `[address, city, state, zip].filter(Boolean).join(', ')`. Symmetric rendering for both groups.

## User Flows

### Flow A — Dispatcher creates a load with a saved-Place pickup, free-text delivery (Phase 1)

1. Dispatcher opens Create Load form.
2. Picks pickup from typeahead — Place is selected, lat/lng captured (UI), `placeId` populated in form state.
3. Types delivery address as free text ("100 Main Street, Tucson, AZ 85705"). Doesn't pick from typeahead.
4. Submits.
5. `createLoad` mapper passes both stops through `resolveStopToPlace`:
   - Pickup: explicit `placeId` present → bypass auto-resolution → link.
   - Delivery: dedupe lookup with `normalize(facilityName)='', addressNumber='100', street='main', ...` → no match → call AWS `Geocode` with structured input → AWS returns canonical `100 Main St` with `MatchScores.Overall = 0.95`, `type = PointAddress` → second dedupe lookup using AWS-canonical fields → no match → `INSERT ... ON CONFLICT DO NOTHING` Place with `source='AUTO'`, `name='100 Main St, Tucson, AZ 85705'`, coords from AWS → link to stop.
6. Both stops save with `resolutionStatus = 'RESOLVED'`. No warnings.
7. Load detail page renders both pins on the map. Dispatcher continues.

### Flow B — Dispatcher creates a load with a typo'd address (Phase 1)

1. Dispatcher types "100 Main Stret, Tucson AZ" (typo).
2. Submits.
3. AWS `Geocode` returns top result with `MatchScores.Overall = 0.62`.
4. Service rejects (below 0.7 threshold). Stop saves with `resolutionStatus = 'AMBIGUOUS'` and `placeId = NULL`.
5. Load-create response includes `warnings: [{ code: 'STOP_AMBIGUOUS_ADDRESS', stopSequence: 1, message: '...' }]`.
6. Load detail map renders the resolved stop and skips the unresolved one. UI surfaces the warning so the dispatcher knows to fix the address.
7. Dispatcher edits the stop, fixes the typo, saves. `updateLoad` runs `resolveStopToPlace` again — now matches confidently — Place created/linked, `resolutionStatus` flips to `'RESOLVED'`.

### Flow C — AWS Location Service is unavailable (Phase 1)

1. Dispatcher submits a load with two free-text stops.
2. `resolveStopToPlace` calls `geocode(...)`; SDK throws.
3. Service catches, logs warning with `code: 'GEOCODER_UNAVAILABLE'`, returns null result.
4. Stop saves with `placeId = NULL` and `resolutionStatus = 'UNRESOLVED'`. Load is created successfully.
5. Response includes `warnings: [{ code: 'GEOCODER_UNAVAILABLE', stopSequence: 0, ... }, { code: 'GEOCODER_UNAVAILABLE', stopSequence: 1, ... }]`.
6. Dispatcher can save and dispatch the load. Map pins are absent until they re-edit the stops once AWS is back.

### Flow D — Soft-fill enrichment (Phase 1)

1. Stop A creates Place P with address "100 Main St, Dallas, TX 75201", facilityName "Walmart DC". Place P has `contactName = NULL`, `notes = NULL`, etc.
2. Some weeks later, Stop B is created with the same address, facilityName "Walmart DC", and additional fields: `contactName = "Jeff Smith"`, `contactPhone = "555-0100"`, `notes = "Use bay 4"`.
3. Dedupe matches Place P. Service runs soft-fill: writes Stop B's `contactName`, `contactPhone`, `notes` into Place P (because P's were null). Does NOT touch Place P's existing non-null fields.
4. Future stops at Walmart DC inherit those filled values for typeahead suggestions and route notes.

### Flow E — Typeahead with HQ bias (Phase 1)

1. Long Island dispatcher's org has `headquartersLat/Lng = (40.73, -73.94)` set in Org settings.
2. Dispatcher types `walmart` in the AddressSearchField.
3. `searchAddresses("walmart", 10, biasPosition=[-73.94, 40.73])` → v2 `SearchText` returns Walmarts ranked by proximity to Long Island.
4. Top results are Walmart-Valley-Stream, Walmart-Uniondale, etc. — a single-word query is enough. Without HQ bias, the dispatcher would have to add `valley stream` to disambiguate.

### Flow F — Concurrent novel-address creates (Phase 1)

1. Dispatcher A and Dispatcher B simultaneously create loads with the same novel pickup address ("500 New Industrial Pkwy, Houston, TX 77001").
2. Both `resolveStopToPlace` calls miss tier-1 (no Place exists yet).
3. Both call AWS Geocode, both get the same canonical fields.
4. Both miss tier-2 dedupe (no Place yet).
5. Both attempt `INSERT ... ON CONFLICT DO NOTHING`.
6. One INSERT succeeds. The other returns 0 rows (lost the race). Service re-reads by dedupe key, finds the winner's Place row, links to it.
7. Both loads save with `resolutionStatus = 'RESOLVED'`, both stops point to the same Place. Single Place row, no constraint violation surfaced to either user.

## Data Requirements

### Schema changes (Phase 1)

**`Place` table**
- `unit text NULL` — suite/apartment/room/floor identifier from `SecondaryAddressComponents`. Normalized lowercase on store.
- `source text NOT NULL DEFAULT 'USER'` — values `'USER' | 'AUTO'`. Add CHECK constraint.

**`Stop` table**
- `resolutionStatus text NOT NULL DEFAULT 'UNRESOLVED'` — values `'RESOLVED' | 'UNRESOLVED' | 'AMBIGUOUS'`. Add CHECK constraint. Add btree index for routing-service consumers.

**`Organization` table**
- `headquartersLatitude Decimal(9,6) NULL` — typeahead bias coord.
- `headquartersLongitude Decimal(9,6) NULL` — typeahead bias coord.

### Index changes (Phase 1)

- New index on `Place(organizationId, source)` — typeahead and admin filtering.
- New unique expression index on `Place(organizationId, normalize_dedupe(facilityName), awsAddressNumber, normalize_dedupe(awsStreetBaseName), awsStreetType, awsStreetPrefix, COALESCE(normalize_dedupe(unit), ''), awsRegion, awsPostalCode5)`.
- New PostgreSQL `IMMUTABLE` function `normalize_dedupe(text) RETURNS text` defined as `lower(regexp_replace(trim($1), '\s+', ' ', 'g'))` — case-fold, strip leading/trailing whitespace, collapse internal whitespace to single space. **No punctuation stripping** (too aggressive; AWS-canonical fields are already clean). Both the SQL expression index and the application-side `normalize()` helper MUST produce identical output for the same input — the function is the single source of truth so they can't drift. Prisma may need a raw SQL migration step; fall back to application-level uniqueness with `INSERT ... ON CONFLICT` swapped for a SELECT-then-INSERT-with-retry pattern only if Prisma can't model the function-based index cleanly.
- New btree index on `Stop(resolutionStatus)`.

### Geocode response shape (used by `resolveStopToPlace`)

```typescript
interface GeocodeResult {
  matchScore: number;                    // MatchScores.Overall, 0..1
  type: 'PointAddress' | 'PointOfInterest' | 'InterpolatedAddress'
      | 'InferredSecondaryAddress' | 'Locality' | 'Region' | 'District' | string;
  title: string | null;                   // POI/business name when present, else null
  addressNumber: string | null;
  streetBaseName: string | null;
  streetType: string | null;              // canonical: "St", "Ave", "Blvd"
  streetPrefix: string | null;            // "N", "W", etc.
  city: string;
  region: string;                         // 2-letter (v2 already canonical)
  postalCode5: string;                    // first 5 digits, format-agnostic
  unit: string | null;                    // from SecondaryAddressComponents
  lat: number;
  lng: number;
}

const ACCEPTED_TYPES = new Set([
  'PointAddress', 'PointOfInterest', 'InterpolatedAddress', 'InferredSecondaryAddress',
]);
```

### Key decisions

- **Server-side geocoding via existing `GeocodingProviderPort`, not UI-supplied coords.** UI-captured lat/lng remain UI-only (typeahead UX). Source of truth is the server. Unifies dispatch-UI, future API/integration callers (load-board ingest, mobile, partner APIs).
- **v2 typeahead op = `SearchText`, not `Suggest`.** Empirically validated 2026-05-01 — `SearchText` returns POI + structured addresses in one call; `Suggest` returns POI labels without addresses. See `.planning/auto-place-resolution/test-scripts/comparison-output.md`.
- **Two-tier dedupe.** First-tier lookup uses raw user input → no AWS call on warm hits (~95% of stops). Miss → AWS Geocode → second-tier lookup using AWS-canonical fields. The Place table doubles as the persistent geocode cache; no Redis layer needed.
- **No abbreviation table needed.** AWS v2 returns canonical street suffixes (`St`, `Ave`, `Blvd`) in `StreetComponents.Type`. The application-side `normalize()` helper does only `lower(trim(s)).replace(/\s+/g, ' ')` — case-fold, edge-trim, collapse internal whitespace. No punctuation stripping (rare in real facility names, and aggressive stripping creates false matches). The SQL expression index uses an `IMMUTABLE` Postgres function `normalize_dedupe(text)` with the equivalent semantics so the two layers can't drift. Punctuation stripping and abbreviation expansion stay deliberately out of scope.
- **`facilityName` IS in the dedupe key.** Multi-tenant addresses are real (Walmart DC and Hub Group 3PL at the same business park). Misspelling cost is acceptable, addressable via Places admin merge UI later.
- **`unit` is a separate nullable column.** Required for any future courier/last-mile workload — wrong-suite delivery is a catastrophic failure mode. Nullable, so trucking-only stops cost nothing.
- **Soft-fill on match.** Update Place fields that are null with values from the new stop; never overwrite a non-null. Audit-trail logged (P1).
- **`Place.source` single mutable enum.** `'USER' | 'AUTO'`. Auto-create sets `'AUTO'`. Any **user-initiated** update through `PATCH /places/:id` against a Place where `source = 'AUTO'` flips it to `'USER'`. Server-internal writes (soft-fill, dedupe-link) do not flip — those aren't user actions.
- **Match score threshold = 0.7.** Validated against real v2 Geocode results — confident matches return 1.0; ambiguous brand queries 0.35–0.67; garbage returns 0 results. 0.7 cuts noise effectively.
- **Type gate alongside score gate.** `MatchScores.Overall` of 1.0 with `type = Locality` is a city-centroid match, not an address — must be rejected too. Accept-set: `{PointAddress, PointOfInterest, InterpolatedAddress, InferredSecondaryAddress}`.
- **Race-condition handling.** Concurrent novel-address creates use `INSERT ... ON CONFLICT DO NOTHING RETURNING *`; loser of the race re-reads by dedupe key. Surfaces no failure to either caller.
- **Load creation never fails because of geocoder issues.** Stop saves coord-less; warnings surface in the response.
- **Symmetric update path.** `resolveStopToPlace` runs on every stop write. Diff-aware short-circuiting deferred — sub-millisecond cost, simpler contract beats marginal optimization.
- **Backfill = production code path.** The script invokes `resolveStopToPlace` per stop. No parallel implementation. Idempotent. Reusable as a per-org admin job in production.
- **`PlaceId` from AWS is NOT the dedupe key.** AWS docs explicitly state PlaceId is not a stable identifier across calls. Key on AWS-returned canonical address fields.
- **HQ bias coords stored on `Organization`.** Two columns (`headquartersLatitude`/`headquartersLongitude`) over a single PostGIS Point because Prisma doesn't model Point natively. Nullable. Falls back to US center `[-98.5, 39.5]` when null.
- **Synchronous geocoding latency on load create.** Worst case ~10 stops × 100ms = 1 second of AWS round-trips inside `POST /loads`. Most loads are 1–2 stops (steady state ≪ 200ms). If complaints surface, parallelize across stops with `Promise.all`. Don't pre-build the optimization.
- **Two PRs, not one.** PR 1 = v2 SDK migration (no behavior change). PR 2 = auto-Place feature on top of stable v2. Smaller blast radius, obvious rollback.

### Explicit exclusions

- **`createDriver` geocoding fix.** Not in this plan. Symptom-related (driver pins also missing) but a separate one-line bug — `createDriver` doesn't run the geocode block that `updateDriver` has. Track as its own ticket.
- **Driver routing/optimization service.** Future work. Will consume `Stop.resolutionStatus` to enforce its own preconditions; this plan only emits the signal.
- **WebSocket migration.** Already planned separately.
- **Address validation API (separate v2 operation).** Not used in this scope.
- **Editable `facilityName` in the stop form post-selection.** Real gap, but affects dedupe semantics and warrants its own design pass. P1.
- **Multi-region geocoding (non-USA).** AWS provider currently filters to `FilterCountries: ['USA']`. Expanding regional coverage is a separate ticket.

### Research findings

- **AWS Location Service v2.** v1 (`@aws-sdk/client-location`) is marked previous in AWS docs (2024 announcement). v2 splits into `geo-places`/`geo-routes`/`geo-maps`, supports structured `QueryComponents` input, returns `MatchScores`, returns parsed `StreetComponents`. v2 removes named-resource requirement (no more pre-created PlaceIndex/RouteCalculator/Map). Pricing equivalent (~$0.50/1k for Geocode under Esri data plan with `IntendedUse: 'Storage'`).
- **Empirical comparison v1 vs v2** (2026-05-01, full output at `.planning/auto-place-resolution/test-scripts/comparison-output.md`):
  - POI brand queries: v2 `SearchText` returns specific store locations with full addresses; v1 returns city-level fuzzy matches. **Decisive — drives the choice of typeahead op.**
  - Match scoring: v2 `Geocode` rejects garbage with 0 results; v1 confidently returns a Florida fuzzy match for `"asdfasdf qweqwe"`. **Validates the 0.7 threshold.**
  - Suite handling: v2 `Geocode` with `AdditionalFeatures: ['SecondaryAddresses']` preserves `Ste 400` in title and labels result `type=InferredSecondaryAddress`; v1 silently drops the suite. **Validates the courier-aware `unit` column.**
  - Type gating: `"Valley Stream NY"` returns `type=Locality, score=1` from v2 `Geocode` — score alone wouldn't reject; type field is the discriminator. **Source of the type-gate addition.**
  - ZIP format: v1 returns `"02110 1802"` (broken), v2 returns `"02110-1802"` (correct US ZIP+4). Provider strips both to ZIP5.
- **`PlaceId` is not stable.** Both v1 and v2 docs explicitly state PlaceId can change between consecutive API calls. Don't use as dedupe key.
- **Address normalization.** AWS v2 Geocode returns canonical street suffix abbreviations in `StreetComponents.Type`. Submitting "Street" returns "St". Eliminates need for our own abbreviation expansion table.
- **Storage rights.** v2 Geocode requires per-request `IntendedUse: 'Storage'`. Esri data plan permits storage; this is the path we're on.
- **`BiasPosition`.** v2 typeahead ops require either `BiasPosition`, `Filter.BoundingBox`, or `Filter.Circle` when `Filter.IncludeCountries` is set. Our default is `[-98.5, 39.5]` (US center) when no org HQ is set. Bias is a ranking hint, not a filter — distant results still appear if no nearby ones match.
