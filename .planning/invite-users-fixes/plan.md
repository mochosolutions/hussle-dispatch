# Invite Users — Settings Page Layout, Table & Editing-Flow Alignment

> Generated by /prd-refine on 2026-05-29
> Updated 2026-05-29: (a) table migration → NewDataGrid; (b) General-tab editing redesigned
> to the app-standard read-only-section + per-section edit-drawer pattern.

## Problem

The Settings page (which hosts the invite-users / Team feature) does not match the
page chrome used everywhere else in the app. Every other top-level page is wrapped in
`ListLayout`, which renders a standard 56px white topbar with a `PageTitle` and an
optional primary action, over a `grey.100` content area. The Settings page instead rolls
its own chrome — `PageWrapper(isLoading)` → a bare `<Box>` with `PageHeader`
(title + subtitle) → `DetailTabBar` → custom content `<Box>`. The result reads as a
different page style: no standard topbar, different title treatment, different spacing.

Notably, `DetailTabBar` is used **only** by this page; every other tabbed surface gets
tabs from `DetailLayout` (entity pages). So Settings is the lone page composing its own
chrome by hand.

## Solution Overview

Two-part alignment:
1. **Chrome:** re-chrome `SettingsPage` with the app-standard `ListLayout` — a `PageTitle`
   topbar reading "Settings", the existing General/Team tabs in the content zone, standard
   `grey.100` content padding.
2. **Tables:** migrate `MemberTable` and `InvitationTable` from raw MUI `<Table>` to the
   app-standard `NewDataGrid` (AG Grid wrapper) with co-located `*CellRenderers.tsx` and
   `ActionsCell`, matching every other list in the app (`rowHeight: 56`, `pagination`,
   `headerHeight: 44`, `EmptyState` empty state).
3. **Editing flow:** redesign the General tab from one always-editable inline form (+ single
   Save) to the app-standard **read-only display sections + per-section edit drawers**. Each
   section renders via `SectionCard` + `SectionHeader` (with an edit pencil, admin-only) +
   `DetailRow` value rows; the pencil opens a section-scoped `EditDrawer` (mirroring carrier
   `CompanyInfoDrawer`) containing just that section's Formik fields, saving via the existing
   `updateSettingsRequest`. This is how every other detail surface in the app edits its data.

## User Flows

### Viewing Settings (admin)
1. User clicks **Settings** in the nav drawer.
2. Page renders with the standard topbar ("Settings") identical in style to other pages.
3. General / Team tabs appear directly under the topbar; selecting a tab swaps content in the
   standard content area.

### Editing a settings section (admin)
1. On the General tab, each section shows current values (read-only `DetailRow` rows) with an
   **Edit** pencil in its `SectionHeader`.
2. Admin clicks Edit → a right-anchored `EditDrawer` opens with that section's fields
   pre-filled from current settings.
3. Admin edits and saves → `updateSettingsRequest` fires with the merged full settings object;
   drawer closes; the section's display rows reflect the new values.
4. Closing the drawer with unsaved changes prompts the `EditDrawer` dirty-form confirmation.

### Viewing Settings (dispatcher)
1. Same chrome; only the **General** tab is present (Team hidden). Sections render read-only
   with **no Edit pencils** — the dispatcher can view settings but cannot open any edit drawer.

### Managing the team (admin, Team tab)
1. Members and Pending Invitations render as `NewDataGrid` grids matching other list pages.
2. Admin changes a member's role inline (role cell) → dispatches `changeMemberRoleRequest`.
3. Admin clicks Remove on a member row (`ActionsCell`) → dispatches `removeMemberRequest`.
4. Admin clicks Resend / Revoke on an invitation row (`ActionsCell`) → dispatches
   `resendInvitationRequest` / `revokeInvitationRequest`; the acted row's actions disable
   while the op is pending.

## Technical Context

### Existing Code to Reuse
- `ListLayout` (`src/components/ListLayout/index.tsx`) — standard page chrome (topbar + content). Already used by `ContactListPage`, `SettlementListPage`, `ExpenseListPage`, `IftaReportPage`, `ratecon IndexPage`.
- `PageWrapper` (`@mocho/ui/components`) — ErrorBoundary + (optional) loading wrapper. Standard composition is `PageWrapper errorContext` → `ListLayout`.
- `PageTitle` (`components/Typography`) — rendered by `ListLayout` topbar; replaces the `PageHeader` title.
- `DetailTabBar` (`components/DetailTabBar`) — keep for the General/Team tab switcher, now placed inside the `ListLayout` content zone.
- `SectionCard` / `SectionTitle` (`components/SectionCard`, `components/Typography`) — already used by the General form; unchanged.
- `NewDataGrid` (`@mocho/ui/components` / `mocho/components/NewDataGrid`) — AG Grid wrapper used by every list. Analog usage: `ContactListPage/index.tsx:222-239`.
- `ActionsCell` (`mocho/components/DataGrid/ActionsCell`) — row actions cell (configurable view/edit/delete + disabled checks). Used for Remove (members) and Resend/Revoke (invitations).
- `EmptyState` (`mocho/components/EmptyState`) — `noDataComponent` for both grids.
- Existing Redux actions reused unchanged: `changeMemberRoleRequest`, `removeMemberRequest`, `resendInvitationRequest`, `revokeInvitationRequest` (the new grids dispatch the same actions the current tables do).
- `SectionHeader` (`components/SectionHeader`) — section title + `onEdit` pencil; renders the Edit affordance only when `onEdit` is passed (admin-only).
- `DetailRow` (`components/Typography`) — key-value read display rows for each section.
- `EditDrawer` (`src/components/EditDrawer/index.tsx`) — standard drawer with built-in dirty-form blocking; the base for all five section drawers.
- Carrier `CompanyInfoDrawer` (`src/features/carrier/components/CompanyInfoDrawer/index.tsx`) — canonical section-edit-drawer analog (`{ entityId, onClose }` → `EditDrawer` + Formik + dispatch update).
- `useDrawerActions` (`features/ui/hooks/useDrawerActions`) — `openDrawer(type, props)`; drawer registry + `popupTypes` `DrawerType`/`DrawerTypeMap`.
- Existing settings fields (`updateSettingsRequest`, `settingsSchema`, the `TextField`/`EmailField` form-fields, `DriverCommunicationsSettings`) reused inside the drawers; the inline General form is replaced by display sections + drawers.

### Key Decisions
- **Target `ListLayout`, not `DetailLayout`.** `DetailLayout` is entity-oriented (requires `id`, `status`, `breadcrumb`, back button) and is wrong for a top-level settings page. `ListLayout` is the generic top-level page chrome and is the correct analog.
- **Keep `DetailTabBar` for tabs.** It already drives the General/Team switch; only its *container* changes (from a hand-rolled `<Box>` stack to the `ListLayout` content zone). No new tab component.
- **Migrate both tables to `NewDataGrid`.** The table standard ("all data tables MUST use `NewDataGrid`") is the main reason the Team tab looks off; raw MUI tables are replaced. Interactive bits (inline role `Select`, expiry/role chips, Resend/Revoke/Remove) move into cell renderers + `ActionsCell`.
- **No behavior/data changes.** Grids dispatch the same existing Redux actions; only the rendering layer changes. Loading uses the grid's own `loading` prop (`loading={!hasLoadedOnce}` pattern), not a page-level overlay.
- **`ActionsCell` for row actions.** If `ActionsCell`'s config doesn't cleanly express Resend/Revoke (non-CRUD verbs), use its custom-action capability or a thin custom actions cell renderer — confirmed during /build against the `ActionsCell` API.
- **Editing flow → read-only sections + per-section edit drawers.** Mirrors carrier/customer/vehicle detail pages (`SectionHeader` edit pencil → `EditDrawer`). Replaces the always-editable inline form + single Save. One drawer per General section (5 total).
- **Drawers save the full settings object.** `PUT /settings` (`updateSettingsSchema`) is a full-object update; each drawer reads current settings from the store, overlays its edited fields, and dispatches `updateSettingsRequest` with the complete merged payload. (If the validator turns out to accept partials during /build, simplify to per-section payloads — confirm against `updateSettingsSchema`.)
- **Dispatcher read-only via absent edit pencils.** `SectionHeader.onEdit` is only wired when `isAdminSelector` is true; non-admins see display-only sections. This supersedes the prior "disabled fields + hidden Save" implementation, which is removed.
- **Preserve role-gating** (`isAdminSelector`, `visibleTabs`) and all Team/invite behavior — only the General-tab rendering/editing model changes.

## Acceptance Criteria
- `SettingsPage` renders inside `PageWrapper` → `ListLayout title="Settings"` (no `PageHeader`, no bare header `<Box>`).
- The Settings topbar is visually identical to other pages' topbars (56px, white, `PageTitle`, bottom border/shadow).
- General and Team tabs render and switch correctly under the new chrome; content sits in the standard `grey.100` content area with `px: { xs: 2, sm: 3 }` padding.
- Dispatcher still sees only the General tab, read-only, with no Save button; admin sees both tabs fully editable — identical behavior to before the refactor.
- `MemberTable` and `InvitationTable` render via `NewDataGrid` with `rowHeight: 56`, `headerHeight: 44`, `pagination: true`, `paginationPageSize: 25`, `EmptyState` empty state, and `ActionsCell` row actions — visually consistent with other list grids.
- Member role change, member remove, invitation resend, and invitation revoke all still work from the grids (same actions/sagas as before); per-row actions disable while their op is pending.
- Cell-rendering logic lives in `MemberCellRenderers.tsx` / `InvitationCellRenderers.tsx`, not inline.
- The General tab shows read-only `DetailRow` sections; each section (admin only) has an Edit pencil that opens its `EditDrawer`. There is no always-editable inline form and no page-level Save button.
- Each section drawer pre-fills from current settings, saves via `updateSettingsRequest`, closes on success, and prompts on dirty-close. Saved values appear immediately in the section's display rows.
- A dispatcher sees the General sections read-only with no Edit pencils and cannot open any drawer.
- All five section drawers are registered in `drawerRegistry` and typed in `popupTypes`.
- `npm run lint` and `npm run check-ts` introduce no new errors in the changed files.
- The page renders without console errors and matches a side-by-side comparison with another `ListLayout` + `NewDataGrid` page (e.g. Contacts).

## Out of Scope
- Any change to the Invite Member dialog, Accept-invite page, or backend.
- Typography/button restyling beyond what adopting `ListLayout` + `PageTitle` + `NewDataGrid` provides.
