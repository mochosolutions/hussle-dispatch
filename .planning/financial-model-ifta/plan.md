# Financial Model — Phase 8: IFTA State Mileage & Reporting

> Generated by /prd-refine on 2026-04-05
> Design doc: `hussle-app-dispatch-api/docs/designs/financial-model-redesign.md` (Section 12, Appendix A9)
> Depends on: `financial-model-expenses` (fuel entries with state/gallons — already implemented)

## Problem

IFTA (International Fuel Tax Agreement) requires trucking companies to report miles driven and fuel purchased per state per quarter. FleetCommand currently has no way to calculate state-by-state mileage for a load's route — the existing distance calculator uses Haversine (straight-line) which doesn't know about state boundaries. Dispatchers have to manually track state miles or use separate tools, then file IFTA reports by hand.

## Solution Overview

Replace the Haversine distance calculator (for loads only) with AWS Location Services to get accurate road distances and route geometry. Intersect the route polyline with US state boundary polygons to derive per-state mileage. Store results in the existing `LoadStateMiles` table. Provide an IFTA report endpoint that combines state mileage with fuel expense data for quarterly filing.

## Capabilities

### Must Have (P0)

- AWS Location Services route calculation via `CalculateRoute` API
- Route polyline intersection with state boundary polygons to derive per-state mileage
- Automatic state mileage calculation triggered by stop changes (when all stops have coordinates)
- `LoadStateMiles` population with calculated state miles
- `totalMiles` on loads updated with accurate AWS road distance (replacing Haversine for loads)
- Redis caching of route results (30-day TTL, keyed by ordered stop coordinates)
- Manual state mileage override endpoint (create/update per-load state miles)
- IFTA report API endpoint — per-vehicle and fleet-wide, returning miles per state + fuel per state
- Haversine retained for non-load uses (scoring, ranking, backhaul feasibility)

### Nice to Have (P1)

- PDF export of IFTA quarterly report
- CSV export of IFTA quarterly report
- `deadheadMiles` recalculation using AWS road distance
- ELD integration for GPS-based mileage source

## User Flows

### Automatic State Mileage Calculation

1. Dispatcher creates/updates stops on a load
2. System emits `STOPS_CHANGED` domain event
3. Event handler checks if all stops have coordinates (via Stop → Place relationship)
4. If yes: resolves coordinates, checks Redis cache for this route
5. Cache miss: calls AWS `CalculateRoute` with stop coordinates as waypoints
6. Intersects route polyline with state boundary GeoJSON using `@turf/turf`
7. Upserts `LoadStateMiles` rows (one per state traversed)
8. Updates `totalMiles` on the Load with the AWS road distance
9. Caches results in Redis (30-day TTL)
10. If any stop lacks coordinates: skips calculation silently (Haversine remains for totalMiles)

### Manual State Mileage Override

1. Dispatcher navigates to load detail and sees state mileage breakdown (or empty state)
2. Dispatcher manually enters miles per state (e.g., from ELD data)
3. System upserts `LoadStateMiles` with `source: MANUAL`
4. Manual entries are not overwritten by automatic recalculation

### IFTA Report Generation

1. User requests IFTA report for a vehicle + quarter (or all vehicles in org)
2. System queries `LoadStateMiles` grouped by state for loads assigned to the vehicle(s) in the date range
3. System queries `Expense` where `category = FUEL`, `fuelType = DIESEL`, grouped by state for the same vehicle(s) and date range
4. Returns combined report: miles driven per state + gallons purchased per state + total fuel cost per state

## Data Requirements

### Existing Models (no schema changes needed)

- **`LoadStateMiles`** — already in schema with `id`, `loadId`, `state` (Char 2), `miles` (Decimal 8,2), `source` (MileageSource enum), `createdAt`. Unique constraint on `[loadId, state]`.
- **`Expense`** — already has `state`, `gallons`, `pricePerGallon`, `fuelType`, `category` fields needed for IFTA fuel queries.
- **`Load`** — `totalMiles` (Int) updated by route calculator. `vehicleId` used for report scoping.
- **`Place`** — `latitude`, `longitude` (Decimal 10,7) used to resolve stop coordinates.
- **`Stop`** — `placeId` FK to Place, `sequence` for ordering.

### MileageSource Enum (already exists)

- `MANUAL` — dispatcher entered
- `GPS` — future ELD integration
- `ELD` — future

**Note:** The design doc mentions `ROUTING_API` as a source value, but the current schema has `MANUAL | GPS | ELD`. A migration will add `ROUTING_API` to the enum.

### New Config (env vars)

- `AWS_LOCATION_ROUTE_CALCULATOR_NAME` — name of the AWS Location route calculator resource
- `AWS_REGION` — AWS region (if not already configured)

## Technical Context

### Existing Code to Reuse

- **`distanceCalculator.ts`** (`src/shared/utils/`) — Haversine calculator, stays as-is for scoring/ranking
- **`LoadStateMiles` model** — already in Prisma schema, ready to use
- **`Expense` model** — fuel entries with `state`, `gallons`, `fuelType` already captured by expense service
- **Domain event system** — existing `EventDispatcherPort` and handler pattern for STOPS_CHANGED trigger
- **Redis infrastructure** — already configured in the stack for caching

### New Dependencies

- `@aws-sdk/client-location` — AWS Location Services SDK for `CalculateRoute` API
- `@turf/turf` (or selective imports: `@turf/line-intersect`, `@turf/line-split`, `@turf/length`, `@turf/boolean-point-in-polygon`) — GeoJSON operations for state boundary intersection

### State Boundary Data

- Source: US Census TIGER/Line simplified state boundary GeoJSON (~2MB)
- Loaded once at startup, cached in-memory as a `FeatureCollection`
- Bundled as a static JSON file in `src/shared/geo/us-states.json`

### Route Caching Strategy

- **Key:** SHA-256 hash of ordered stop coordinates (sorted by sequence, `[lat,lng]` pairs)
- **Value:** `{ totalDistanceKm: number, legs: LegGeometry[], stateMiles: StateMile[] }`
- **TTL:** 30 days
- **Storage:** Redis (existing infrastructure)
- Same route (same stops in same order) returns cached result without AWS call

### AWS Location Services Cost

- Pricing: $0.50 per 1,000 route calculations
- At 100 loads/day with 50% cache hit rate: ~$0.75/month
- Redis caching makes this effectively negligible

### Key Decisions

- **Haversine kept for scoring** — AWS calls add latency and cost; ±10% accuracy is fine for driver ranking, backhaul scoring, and deadhead feasibility checks
- **API-only report format** — PDF and CSV export deferred to follow-up plan
- **Raw data, no tax calculations** — IFTA tax rates change quarterly and vary by fuel type; users file through IFTA software or their accountant
- **Manual override preserved** — State miles with `source: MANUAL` are not overwritten by automatic recalculation; auto-calc only writes `ROUTING_API` rows
- **Coordinates required** — Route calculator requires lat/lng; stops without Place coordinates are skipped (no on-the-fly geocoding)
- **Per-vehicle + fleet-wide reports** — Single endpoint, `vehicleId` param optional
- **DEF excluded from IFTA** — Only `fuelType = DIESEL` expenses count in IFTA fuel reporting

### Error Handling

- **AWS API timeout/failure:** `LoadStateMiles` not created for this load; `totalMiles` falls back to Haversine estimate; logged as warning
- **Missing coordinates:** Calculation skipped silently; load's existing mileage untouched
- **Single-state loads:** One `LoadStateMiles` row with all miles in that state
- **International loads (Canada/Mexico):** State miles only calculated for US segments (future consideration — out of scope for v1)

### STOPS_CHANGED Event Integration

The state mileage calculation is triggered by a domain event handler:

```
src/loads/events/handlers/stateMileageHandler.ts
```

This handler:
1. Listens for `STOPS_CHANGED` events (emitted by stop create/update/reorder/delete services)
2. Loads all stops for the load with their Place coordinates
3. If all stops have coordinates → calls `stateMileageService.calculateAndStore()`
4. If any stop lacks coordinates → skips (logs debug message)

The handler runs fire-and-forget (non-blocking) — stop operations succeed regardless of mileage calculation outcome.

## Acceptance Criteria

### Route Calculator
- [ ] AWS `CalculateRoute` is called with stop coordinates as waypoints when all stops have Place coordinates
- [ ] Route results are cached in Redis keyed by ordered coordinate hash with 30-day TTL
- [ ] Cached results are returned on cache hit without calling AWS
- [ ] AWS API failures are logged as warnings; load mileage falls back to Haversine
- [ ] Route calculator is behind a port interface (`RouteCalculatorPort`) for testability

### State Mileage Calculation
- [ ] Route polyline is intersected with state boundary polygons to derive per-state miles
- [ ] `LoadStateMiles` rows are upserted (one per state traversed) with `source: ROUTING_API`
- [ ] `totalMiles` on the Load is updated with the AWS road distance (sum of leg distances)
- [ ] Single-state loads produce one `LoadStateMiles` row
- [ ] Recalculation replaces existing `ROUTING_API` rows but preserves `MANUAL` rows

### Event-Driven Trigger
- [ ] `STOPS_CHANGED` domain event triggers state mileage calculation
- [ ] Calculation is skipped when any stop lacks a Place with coordinates
- [ ] Calculation runs fire-and-forget (does not block stop operations)
- [ ] Stop create, update, reorder, and delete all emit `STOPS_CHANGED`

### Manual Override
- [ ] `PUT /api/v1/loads/:loadId/state-miles` accepts an array of `{ state, miles }` entries
- [ ] Manual entries are stored with `source: MANUAL`
- [ ] Manual entries are not overwritten by automatic recalculation
- [ ] `GET /api/v1/loads/:loadId/state-miles` returns all state miles for a load with source

### IFTA Report
- [ ] `GET /api/v1/ifta/report?year=Y&quarter=Q` returns fleet-wide report for the authenticated org
- [ ] `GET /api/v1/ifta/report?vehicleId=X&year=Y&quarter=Q` returns single-vehicle report
- [ ] Report includes miles driven per state (from `LoadStateMiles`)
- [ ] Report includes fuel gallons and cost per state (from `Expense` where `category=FUEL`, `fuelType=DIESEL`)
- [ ] DEF expenses are excluded from IFTA fuel data
- [ ] Report includes per-vehicle totals (totalMiles, totalGallons, totalFuelCost, averageMpg)
- [ ] Report includes fleet-wide totals when multiple vehicles are included
- [ ] Date range is correctly derived from year + quarter

### Schema
- [ ] `ROUTING_API` value added to `MileageSource` enum via migration

### Haversine Preservation
- [ ] `distanceCalculator.ts` (Haversine) remains unchanged and continues to be used by scoring, ranking, and backhaul services
- [ ] Only load-level mileage (`totalMiles`) switches to AWS road distance
