## Headline finding (read this first)

**The subscriber is misnamed.** Despite the name `invoiceReadinessSubscriber`, the implementation **does not write the `Load.invoiceReadiness` column at all**. A `grep -rn 'invoiceReadiness:'` across all non-test code in `src/` returns only:

- Two type declarations in `loads/types/loadTypes.ts` (the field's TypeScript shape derived from Prisma).
- Two reads in `loads/controllers/transformers/loadTransformer.ts` (serializing the column to API responses).

There is **no `prisma.load.update({ data: { invoiceReadiness: ... } })` anywhere in the codebase.** The column exists, defaults to `NOT_READY` (from `prisma/schema.prisma:802`), and is **never overwritten**. The transformer always sees `'NOT_READY'`.

The local `readiness` variable inside `evaluateReadiness` (subscriber.ts:149-157) is computed and then **only logged** (`logger.info('Invoice readiness evaluated', { readiness, ... })`, line 252-258). It never reaches the database.

The `deps.loadQuery.updateLoadStatus(loadId, load.status)` call on line 160 passes the **same** status that was just read on line 120, so it is effectively a no-op write of `Load.status` — not a write of `Load.invoiceReadiness`.

The one place `updateLoadStatus` does something meaningful is line 135 — when an existing non-void invoice is found, the load gets force-set to `'INVOICE_PENDING'`. That's a status-machine concern, not a derived-readiness concern.

**Implication for US-13:** This subscriber is not a writer of the derived value being removed. It is a load-state→invoice-creation orchestrator that happens to share a misleading name. The "delete the column writer" portion of US-13 is a **no-op** — the column writer does not exist. The column itself can be dropped from Prisma + the transformer fields removed without touching this subscriber.

The subscriber still has its own future — Phase 2's pure `computeInvoiceReadiness` function will compute the same `readiness` value the subscriber currently computes and logs, but the subscriber's invoice-creation behavior must be preserved.

## Side effects (per handler)

### Shared helper: `evaluateReadiness(loadId, deps)` (subscriber.ts:116-259)

Called by 3 of the 4 handlers. Side effects observable per invocation:

1. **Read load via `loadQuery.findLoadById(loadId)`**
   - Action: Prisma read of load + includes (carrier, customer, contact, accessorialCharges).
   - File:line — `subscriber.ts:120`
   - Idempotent: yes (pure read).
   - Port plan: **KEEP** — needed by the compute path too.
   - Reasoning: Pure read; no derived-column concern.

2. **Early return on non-DELIVERED/INVOICE_PENDING status**
   - Action: `if (!evaluableStatuses.includes(load.status)) return;`
   - File:line — `subscriber.ts:127-130`
   - Port plan: **KEEP** (preserved inside subscriber).
   - Reasoning: Guard, not a writable side effect.

3. **Read existing non-void invoice via `invoiceRepo.findNonVoidByLoadId`**
   - Action: Prisma read.
   - File:line — `subscriber.ts:133`
   - Idempotent: yes.
   - Port plan: **KEEP**.

4. **Force-set load.status → `'INVOICE_PENDING'` when a non-void invoice already exists**
   - Action: `loadQuery.updateLoadStatus(loadId, 'INVOICE_PENDING')` → `prisma.load.update({ data: { status: 'INVOICE_PENDING' } })`.
   - File:line — `subscriber.ts:135` (call) → `invoiceRepositoryPrisma.ts:262-267` (Prisma write).
   - Idempotent: yes (writing the same status twice is benign).
   - Port plan: **KEEP** — this is a load-state-machine effect, unrelated to `invoiceReadiness`.

5. **Read confirmed documents for the load**
   - Action: `documentQuery.findConfirmedByEntity('load', loadId)`

   - **Caveat:** If any database trigger, audit middleware, or Prisma `$extends` middleware piggybacks on the `load.update` call (audit log row, `updatedAt` bump), removing it could be observable. No evidence of such middleware in the codebase, but flagged for human review.

## Open questions / flags for human review

1. **Is the comment "Update load readiness field" (subscriber.ts:159) misleading on purpose, or did a prior attempt to write the column get reverted?** If the latter, there may be product intent the human author should reconcile (e.g., was readiness supposed to land in DB for filtering/searching loads?). For pure compute-on-read this is fine; for "show me all loads with readiness=READY in a list query" we may need an indexable derivation strategy.
2. **Is the no-op `updateLoadStatus(loadId, load.status)` call (line 160) safe to remove?** It looks like dead code, but if any Prisma extension / audit middleware hooks the `load.update` call (e.g. to bump `updatedAt` and trigger cache invalidation), the deletion could be observable. No such middleware was found in `src/shared/middleware/` or `src/shared/prisma/`, but worth a quick confirmation before deleting.
3. **Should the subscriber be renamed during US-13?** It's now misleadingly named — it does invoice creation + email + state-machine flip, not "readiness" writing. Consider `autoInvoiceSubscriber` or `loadDeliveredInvoiceSubscriber`. Cosmetic; can be deferred.
4. **Is anyone outside the API filtering Loads by `invoiceReadiness` (UI list queries, reports)?** Since the column has always been `NOT_READY` in DB, any such filter is broken-by-design today. Worth a quick check before US-13 drops the column.
