# Rate Confirmation Extractor

> Generated by /prd-refine on 2026-05-14

## Problem

Dispatchers create loads in FleetCommand by hand-typing every field off a broker's rate confirmation PDF — broker name, reference numbers, rate, equipment, commodity, every stop's address and appointment time, accessorial line items, detention policy, tracking requirements. A single ratecon takes 5–10 minutes of typing plus a separate trip to attach the PDF as a load document. Errors slip in (transposed addresses, wrong appointment windows), and operationally significant rules buried on page 2+ (detention rates, fees, POD deadlines) get missed entirely.

The carrier already has a working Jupyter notebook (`/Users/jr/Development/Jupyter Notebook/ratecon_extraction.ipynb`) that uses Claude Sonnet vision + a Pydantic schema to extract structured data from real ratecons across multiple broker formats (Scotlynn, MegaCorp, Beemac, Sunteck). That logic needs to ship as a service the dispatch UI can call.

## Solution Overview

A Python FastAPI service (`ratecon-extraction-service/`) packages the notebook's extraction logic behind a single HTTP endpoint. The TypeScript dispatch-api proxies dispatcher uploads to it, applies broker fuzzy-matching against the existing Customer table, and returns a prefill payload the React Create Load page consumes via its existing `intelPrefill` mechanism.

User experience: dispatcher drops a PDF on the Create Load page → blocking spinner (5–30s) → form fields populate with extracted values + a "matched broker?" chip the dispatcher accepts or changes → dispatcher reviews and saves → PDF attaches as a load document on save.

## Capabilities

### Must Have (P0)

- **Dropzone on Create Load page** that accepts a single PDF (≤20MB, application/pdf only) and shows extraction progress.
- **Python FastAPI service** with `POST /extract` endpoint that accepts a PDF and returns the `ExtractionResult` JSON contract from the notebook (broker, carrier, equipment, stops, charges, total_rate, special_instructions, document-level references).
- **Dispatch-api proxy module** at `src/ratecon-extraction/` that:
  - Authenticates the request (`requireAuth`).
  - Streams the PDF body to the Python service via HTTP.
  - Performs broker fuzzy-matching: trigram/Levenshtein search against the org's `Customer` table; returns `{customerId, confidence}` for >=0.8 match, otherwise `{customerId: null, suggestedName}`.
  - Buffers the PDF bytes in Redis under a short-lived key (TTL 30 min) so the UI can attach it on load save without re-uploading.
  - Returns a `RateconExtractionResponse` shaped for the UI prefill.
- **UI saga** that dispatches extraction, prefills the Create Load form via the existing `intelPrefill` path, and surfaces a "broker matched" / "broker detected: X" affordance.
- **PDF attached on save**: when the dispatcher saves the load with a buffered PDF key, dispatch-api fetches the buffered bytes from Redis and creates a load document with category `RATECON`, automatically setting `hasRateCon` / `rateConReceivedAt`.
- **Local dev via docker-compose**: new `ratecon-extraction` service in `docker-compose.yml` runs uvicorn on `:8000`. Dispatch-api reaches it via internal compose hostname.
- **Test fixtures**: the five sample PDFs under `/Users/jr/Development/Jupyter Notebook/ratecon_files/` get copied into `ratecon-extraction-service/tests/fixtures/` so the Python service has integration tests against real broker formats.

### Nice to Have (P1)

- Confidence indicator per extracted field (icon next to prefilled fields the LLM was uncertain about — anything the model returned as null but the dispatcher might want to flag).
- "Re-run extraction" button on the prefill banner if the dispatcher thinks the first pass was wrong.
- Driver-dispatch text message formatter (the notebook's `format_driver_message`) exposed as a second endpoint for use elsewhere in the app later.
- Stop the dispatcher from accidentally creating two loads from the same PDF (hash check on bytes — would block double-extraction within the 30 min Redis window).

## User Flows

### Primary: Extract & Create

1. Dispatcher opens `/loads/new` (Create Load page).
2. A `RateconDropzone` component sits at the top of the form. Empty state reads "Drop a rate confirmation PDF to prefill this form."
3. Dispatcher drops a PDF (or clicks to file-pick).
4. Client-side check: PDF mime, size < 20MB. If fails, snackbar error + abort.
5. UI dispatches `extractRateconRequest({ file })`. Saga POSTs `multipart/form-data` to `/api/v1/ratecon-extraction/extract` on dispatch-api.
6. Dispatch-api streams the PDF body to the Python service. Python service converts pages to base64 PNGs, calls Claude with the tool-use schema, parses the response.
7. Dispatch-api receives the extraction JSON, runs broker fuzzy-match, buffers the PDF in Redis with a key like `ratecon-buffer:<uuid>`, returns response.
8. UI updates form values via Formik `setValues` using the existing `intelPrefill` shape adapter. Dropzone collapses to a "Ratecon extracted — review below" banner showing the buffered key.
9. Dispatcher reviews every field, edits anything wrong, picks the correct broker if fuzzy-match was below threshold.
10. Dispatcher hits **Create**. UI submits `createLoadRequest` with the load fields AND the buffered ratecon key.
11. Dispatch-api save flow: creates the load row, fetches the buffered PDF from Redis, calls existing document service to attach it as a `RATECON` document, sets `hasRateCon` / `rateConReceivedAt`.
12. Success snackbar, redirect to load detail page.

### Failure paths

- **Python service times out (>30s)**: dispatch-api returns 504. UI shows snackbar "Extraction timed out — fill the form manually" and a "Retry" button on the dropzone banner.
- **Claude API error or schema-validation fail**: dispatch-api returns 502. UI shows snackbar with the upstream error, dropzone stays in error state with retry available.
- **No broker matched**: form's customer autocomplete stays empty; banner shows `Detected: "<extracted name>"` as a hint. Dispatcher picks a customer manually.
- **Dispatcher abandons the page after extraction**: Redis TTL (30 min) cleans up the buffered PDF. No orphaned files in S3/local storage.

## Data Requirements

No Prisma schema changes. The feature reuses:

- `Document` rows (created on load-save) for the PDF artifact.
- `Load.hasRateCon` and `Load.rateConReceivedAt` (existing columns flipped by the existing document-confirmation event chain).
- `Customer` rows for broker fuzzy-matching (read-only).

New Redis key namespace: `ratecon-buffer:<uuid>` with 30-minute TTL. Stores `{ pdfBytes: base64, contentType: 'application/pdf', orgId, uploadedBy, uploadedAt }`. Single-use — deleted after document attach.

The Python service is stateless — no database, no Redis. It receives bytes and returns JSON.

## API/Interface Changes

### Dispatch-api (new)

| Endpoint | Method | Purpose |
|---|---|---|
| `/api/v1/ratecon-extraction/extract` | `POST` | Multipart upload of a PDF. Auth required. Returns `RateconExtractionResponse`. |

`RateconExtractionResponse` shape (dispatch-api → UI):

```ts
interface RateconExtractionResponse {
  rateconBufferKey: string;            // Redis key — pass back on load create
  extraction: ExtractionResult;        // mirrors Python ExtractionResult schema
  brokerMatch:
    | { status: 'MATCHED'; customerId: string; confidence: number }
    | { status: 'SUGGESTED'; suggestedCustomerId: string; suggestedName: string; confidence: number }
    | { status: 'NO_MATCH'; extractedName: string | null };
  // Convenience: pre-mapped LoadFormValues partial for direct Formik setValues
  prefill: LoadFormPrefill;
}
```

`createLoadRequest` body gains an optional `rateconBufferKey?: string` field. When present, the load-create handler attaches the buffered PDF as a document and clears the Redis key.

### Python service

`POST /extract`

- Body: `multipart/form-data` with `file` field (PDF). Internal-only — protected by a shared bearer token in the `Authorization` header, set via env var on both services.
- Response: 200 with the Pydantic `ExtractionResult` JSON, or 4xx/5xx with `{ error: { code, message } }`.

`GET /health` — liveness probe returning `{ status: 'ok' }`.

### Dispatch-ui (new + modified)

- New: `features/load/components/CreateLoadPage/RateconDropzone/index.tsx` — drag/drop + state machine (idle / extracting / ready / error).
- New: `features/load/store/sagas/extractRateconSaga.ts` — calls the API, maps to prefill shape.
- New: `features/load/store/reducers/rateconExtractionSlice.ts` — slice tracking `{ status, extraction, brokerMatch, bufferKey, error }`.
- New: `features/load/utils/rateconToFormValues.ts` — pure mapper from `ExtractionResult` → `Partial<LoadFormValues>`.

- Modified: `features/load/components/CreateLoadPage/CreateLoadForm/index.tsx` — accept `rateconPrefill` prop, merge with existing `intelPrefill` logic.
- Modified: `features/load/store/sagas/createLoadSaga.ts` — pass `rateconBufferKey` through to the API.

## Technical Context

### Existing Code to Reuse

- **`CreateLoadForm.intelPrefill`** (`hussle-app-dispatch-ui/src/features/load/components/CreateLoadPage/CreateLoadForm/index.tsx`) — the prefill mechanism for the load form. Ratecon prefill plugs into this same path so we don't fork form-init logic.
- **`documents/compositionRoot.ts`** (`hussle-app-dispatch-api/src/documents/`) — the analog for a feature module that handles file storage + emits events that flip load timestamps. Ratecon extraction follows the same per-module composition-root pattern but is purely an integration module (no Prisma repo of its own; depends on `documentService` and `customerQueryPort`).
- **`shared/redisClient.ts`** (`hussle-app-dispatch-api/src/shared/redisClient.ts`) — for the 30-min PDF buffer.
- **`customers/repositories/customerRepositoryPrisma.ts`** — exposed via a new `CustomerQueryPort.findByNameSimilar(orgId, name)` injected into the ratecon-extraction module.
- **`requireAuth`** middleware and the existing `validateRequest(Yup)` pipeline.
- **`@anthropic-ai/sdk`** is already in the dispatch-api dependencies for other features; the Python side uses the `anthropic` PyPI package per the notebook.
- **Notebook source** (`/Users/jr/Development/Jupyter Notebook/ratecon_extraction.ipynb`) — the locked prompt, the `ExtractionResult` Pydantic schema, the `pdf_pages_to_base64` helper, and `format_driver_message` (P1) port verbatim.

### Key Decisions

- **Python service, not TypeScript port.** Notebook already works; rewriting in TS adds risk and zero value. Locked.
- **dispatch-api proxy, not UI-direct.** Auth + multitenancy + broker matching all live in Node already; Python service stays stateless and provider-agnostic. The dispatch-api is the single browser-facing surface.
- **Single-call extraction with Claude tool-use, all pages as images.** The notebook proves this works for multi-page docs including page-2+ terms. No OCR, no regex per broker.
- **Reuse `intelPrefill` mechanism, don't fork it.** Cheaper to add a second prefill source than parallel form-init paths.
- **Redis buffer + attach-on-save, not commit-on-extract.** Avoids orphaned S3 objects if the dispatcher abandons. 30-min TTL is generous for human review.
- **Internal bearer token between dispatch-api and Python.** Python service trusts dispatch-api; it never sees user JWTs. Token rotated like any infra secret.
- **Sample PDFs go into the Python service's git tree as test fixtures.** They're real but already in the developer's local notebook directory — internal-dev visibility only, no production PII concerns. Confirm before committing if any contain sensitive carrier data.
- **No new Prisma schema.** Existing `Document` + `Load.hasRateCon`/`rateConReceivedAt` cover it.
- **Sync UX with 30s hard timeout.** Async/queue is over-engineering for V1; dispatcher waiting on the page is fine for 5–30s. Retry button covers the timeout case.
- **V1 ships dev-only.** No staging/prod Dokploy config in this feature. Staging/prod deployment is a follow-up.
- **Pyproject + uv for the Python service.** Modern toolchain; lock with `uv.lock`.
- **Ruff for lint, mypy strict for types, pytest for tests** — Python equivalents of the project's TS validate pipeline.

### Explicit Exclusions

- No email-inbox ingest. PDF upload only.
- No bulk import from the loads list page. One PDF at a time on Create Load.
- No auto-create of new Customer records on no-match. Dispatcher picks manually.
- No background extraction / job queue. Sync only.
- No staging or production deployment of the Python service in V1.
- No support for image rate confirmations (PNG/JPG); PDF only. (Easy follow-up if needed.)
- No persistent storage of extraction results; only the final load + attached PDF persist.

## Acceptance Criteria

1. `POST /extract` on the Python service, given any of the 5 sample PDFs in `tests/fixtures/`, returns HTTP 200 with a JSON body that validates against the `ExtractionResult` Pydantic schema and contains at least one stop with a non-null address.
2. `docker compose up` brings up `ratecon-extraction-service` on port 8000 alongside dispatch-api (3001) and dispatch-ui (5173); dispatch-api's `/api/health` and the Python `/health` both return 200.
3. Hitting `POST /api/v1/ratecon-extraction/extract` from the dispatch UI with the Sunteck `CARRCONFIRM.pdf` test fixture returns a `RateconExtractionResponse` whose `prefill.equipmentType`, `prefill.customerRate`, and `prefill.stops` are populated.
4. On the Create Load page, dropping a sample PDF prefills the Load Details, Equipment, and at least one row in the Stops section without manual typing. Form remains editable.
5. Saving the load after an extraction creates exactly one new `Document` row of category `RATECON` attached to the load, with `hasRateCon = true` and `rateConReceivedAt` populated.
6. Saving the load clears the Redis key `ratecon-buffer:<uuid>`.
7. Abandoning the page after extraction leaves no orphaned S3/local-storage objects; the Redis key expires after 30 minutes.
8. Broker fuzzy-match: when extraction returns a broker name that case-insensitively matches an existing Customer name in the org with similarity ≥ 0.8, the `customerId` is pre-selected in the form. Below 0.8, the form leaves customerId empty and the dropzone banner reads `Detected: "<name>"`.
9. Hard 30s timeout: requests exceeding 30s return HTTP 504 from dispatch-api with `{ error: { code: 'EXTRACTION_TIMEOUT' } }`. UI shows a snackbar and a Retry button.
10. PDFs over 20MB or non-`application/pdf` mime are rejected client-side with no network call, and rejected server-side with HTTP 400 if bypassed.
11. Python service unit/integration tests under `pytest` pass; the `ratecon-extraction` module in dispatch-api passes `npm run validate`.
12. New env vars `RATECON_EXTRACTION_SERVICE_URL`, `RATECON_INTERNAL_TOKEN`, and (Python-side) `ANTHROPIC_API_KEY` are documented in `.env.example` and `docs/RUNBOOK.md`.

## Out of Scope

- Email-inbox ingest of broker emails / PDF attachments.
- Bulk ratecon import from the loads list page.
- Auto-creation of new Customer records on no-match.
- Background job / async extraction queue.
- Staging or production deployment of the Python service.
- Image-only (PNG/JPG) rate confirmations.
- A separate "Ratecon History" page or audit trail beyond the Document attachment.
- Reconciliation of extracted values against a previously-saved load (the "attach + verify" mode discussed and rejected).
- The driver-dispatch text-message formatter (notebook section 4b) — deferred to a follow-up; the schema is preserved so the formatter ports trivially.
- DAT-load-scraper integration (scraper still feeds loads its own way).
