# UI Consistency & Component Standardization

> Generated by /prd-refine on 2026-04-15

## Problem

The dispatch app has 11 feature modules that each build the same UI patterns differently. List pages construct filter bars, KPI cards, search inputs, and tables from raw MUI primitives with inconsistent layouts, row heights, pagination, and cell renderer placement. Detail pages vary in how they compose summaries, tabs, sidebars, edit buttons, and content cards. Six features manage drawer/modal state with local `useState` instead of the centralized Redux system. The result is an app that feels inconsistent to users and is hard for developers to extend — there's no single pattern to copy when building a new feature.

## Solution Overview

Create missing shared components (FilterBar, ListKpiBar, DocumentsTab), establish binding standards in CLAUDE.md, then refactor each feature to use the shared components and centralized drawer/modal system. Each feature gets a single story covering its list page, detail page, and drawer/modal migration. Bugs found in the audit are fixed during the feature's refactor.

## Capabilities

### Must Have (P0)

- Composable `FilterBar` component supporting select, multi-select chips, date-range, toggle, and debounced search
- `ListKpiBar` component for standardized summary metric rows on list pages
- Shared `DocumentsTab` component replacing duplicate inline implementations
- All drawer/modal state migrated from local `useState` to centralized Redux (`useDrawerActions` / `useModalActions`)
- All unregistered drawers/modals added to `drawerRegistry.ts` / `modalRegistry.ts` with type-safe entries in `popupTypes.ts`
- Drawer vs modal reclassification per the context-driven decision framework
- Carrier saga watcher fix (uncomment update/delete registrations)
- CLAUDE.md updated with component selection rules and page structure standards
- All pages and shared components use semantic Typography helpers (`EntityId`, `PageTitle`, `SectionTitle`, `Body`, `BodyStrong`, `BodyMuted`, `Amount`, `AmountDisplay`, etc.) instead of raw `<Typography variant="...">`
- All list pages use `NewDataGrid` (AG Grid wrapper) — no custom table implementations. Dispatch Board's `LoadTable` must be migrated to `NewDataGrid`.

### Nice to Have (P1)

- Standardize all AG Grid row heights to 56px
- Enable pagination (`paginationPageSize: 25`) on all tables
- Replace inline empty states with shared `EmptyState` component
- Extract inline cell renderers to `<Feature>CellRenderers.tsx` files
- Add `ActionsCell` to tables that currently lack it (Invoices, Settlement, Expenses)
- Standardize detail page sidebar to `Grid md={8} / md={4}` where sidebar is used
- Extract inline summary KPIs to `<Feature>SummaryBar` components (Customer, Place, Contact)
- Extract inline tab content to tab component files (Place, Contact)

## User Flows

### List Page (standardized)

1. User navigates to a list page (e.g., /carriers)
2. Page renders: ListLayout title bar with Export + Create buttons
3. Optional ListKpiBar shows summary metrics above table
4. FilterBar renders with feature-specific filter configuration (selects, search, chips, toggles)
5. NewDataGrid renders with consistent 56px rows, pagination, ActionsCell
6. User types in search — DebouncedInput fires after 300ms, filters update via Redux
7. User clicks a row — navigates to detail page
8. Empty state shows EmptyState component with "Create" action if no data

### Detail Page (standardized)

1. User navigates to a detail page (e.g., /carriers/:id)
2. Page renders: PageWrapper → DataGuard → DetailLayout
3. DetailLayout shows: back button + entity name + status badge + action buttons
4. FeatureSummaryBar renders KPI metrics below header
5. Tabs render below summary; tab components live in `pages/<Page>/components/`
6. Content sections use SectionCard with SectionHeader (built-in edit button)
7. Optional right sidebar (md={4}) for secondary context — decision per feature
8. User clicks Edit on a card → `dispatch(openDrawer('featureInfo', { entityId }))` → DrawerManager renders drawer
9. User clicks a destructive action → `dispatch(openModal('confirmDelete', { ... }))` → ModalManager renders modal

### Drawer/Modal Interaction (standardized)

1. Page calls `useDrawerActions().openDrawer(type, { entityId })` — passes ID, not object
2. Redux uiSlice stores `{ drawerType, drawerProps }`
3. DrawerManager in App.tsx looks up component in drawerRegistry, renders it
4. Drawer reads entity data from Redux store via selector (always current)
5. On submit: drawer dispatches saga request action → saga handles API call → saga dispatches `closeDrawer()` + refresh
6. On close with dirty form: EditDrawer shows nested ConfirmDialog (local to drawer, not Redux modal)

## API/Interface Changes

### New Shared Components

- `FilterBar` — composable filter bar with declarative config
  - Props: `filters[]` (type: 'select' | 'multiSelectChip' | 'dateRange' | 'toggle'), `search?` config, `values`, `onChange`
  - Each filter type is a composable sub-component that FilterBar orchestrates
- `ListKpiBar` — summary metric row for list pages
  - Props: `items[]` ({ label, value, subtitle?, icon? })
- `DocumentsTab` — shared tab for document management
  - Props: `entityType`, `entityId`, `canUpload?`

### Modified Components

- `popupTypes.ts` — add type entries for all unregistered drawers/modals
- `drawerRegistry.ts` — register ~8 missing drawer components
- `modalRegistry.ts` — register ~5 missing modal components

Per the context-driven decision framework ("Does the user need to see the parent page?"):

| PaySettlementDrawer | Drawer | **Modal** | Confirming payment details — self-contained decision |

| Invoice Mark Paid dialog | Inline dialog | **Modal** (registered) | Confirming amount, self-contained |

## Technical Context

### Existing Code to Reuse

- `NewDataGrid` (mocho/components) — AG Grid wrapper, already used by all list pages. Standardize props.
- `ActionsCell` (mocho/components/DataGrid) — row actions with view/edit/delete. Extend to all tables.
- `DebouncedInput` (mocho/components) — debounced search input. Replace 9 custom implementations.
- `EmptyState` (mocho/components) — empty state with icon/title/action. Replace inline "No X found" text.
- `SectionCard` (components/) — card with grey header and actions. Use for all detail page content sections.
- `SectionHeader` (components/) — uppercase title with Edit button. Use for consistent edit actions.
- `DetailRow` (components/) — key-value display. Already used by Place/Contact, extend to other detail pages.
- `EditableSection` (mocho/components) — view/edit toggle. Available but unused — evaluate for detail pages.
- `ConfirmDialog` (mocho/components) — confirmation modal. Use for all registered confirmation modals.
- `useDrawerActions` / `useModalActions` hooks — type-safe dispatch. Already used by 5 features.
- `createCrudSlice` factory (utils/redux/) — standardized page slice creation.
- `createEntityModule` factory (utils/redux/) — standardized entity adapter creation.

### Key Decisions

- **FilterBar is composable** — each filter type (select, chips, dateRange, toggle) is a discrete sub-component. FilterBar orchestrates layout. Features can mix and match filter types.
- **Pass IDs to drawers, not objects** — drawers read entity data from Redux store by ID. Prevents stale data when entity updates while drawer is open.
- **One drawer + one modal simultaneously** — no stacking. A drawer can open a confirmation modal on top. This is the right constraint.
- **Sidebar is optional per feature** — DetailLayout accepts an optional `sidebar` prop. Features that don't need secondary context use full-width layout.
- **Reclassify during migration** — when moving a feature's drawer state to Redux, also apply the decision framework to determine if it should be a drawer or modal. One pass.
- **Bug fixes included in feature refactors** — vehicle UUID display, contact UUID display, and place escape char fixed during their respective feature stories.
- **Row height standardized to 56px** — compromise between current 52px and 62px values. 64px for tables with avatars/two-line cells.

### Drawer vs Modal Decision Framework

```
Does the user need to see the parent page while doing this?
  YES → DRAWER (480px standard, 640px wide)
  NO →
    Is this a complex, multi-section primary task?
      YES → FULL PAGE (own route)
      NO → MODAL (sm for confirms, md for forms)
```
