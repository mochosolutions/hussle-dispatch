## Problem

The current carrier onboarding portal (`hussle-app-dispatch-ui/src/features/carrier-portal/`) is structurally broken at the schema/validation layer:

- **Silent address-typeahead failures** — AWS Location errors are swallowed; carriers see an empty dropdown with no recourse.
- **Strict TIN regex in `validators/buildPhaseSchema.ts`** — rejects valid EIN and SSN formats; blocks Phase 1 completion.
- **No engine, no schema, no mid-flow signing** — each phase is a bespoke page component; visibility/branching rules are coded ad-hoc; the dispatch agreement is requested out-of-band, not embedded.
- **Field locking after signing is impossible** — without an engine to track which fields back the signed agreement, post-sign edits cannot be prevented.

Carrier traffic is weeks away. Patching the current portal won't fix the architectural gap — the v1 tech spec (`docs/onboarding-example-tech-spec/`) defines the right shape (declarative schema + pure-function engine + embedded mid-flow signing), and Features 1 + 2 already shipped the FMCSA and DocuSeal pipes the portal will consume.

## Solution Overview

Replace `features/carrier-portal/` in-place with a v2 rebuild that introduces:

1. **A declarative schema as TypeScript code** — phases / steps / questions / predicates / prefill bindings, composed from per-phase files.
2. **A UI-only pure-function engine** — `getVisibleSteps`, `getNextStepId`, `getPrevStepId`, `evaluatePredicate`, `resolveContext`, `computeInvalidations`. No I/O, no persistence, fully testable.
3. **Generic step-type renderers** — one component per step type (`segmentation`, `input`, `verification`, `signing`, `upload`, `review`, `checkpoint`, `complete`). Knows nothing about specific phases; consumes schema + session.
4. **Embedded DocuSeal signing** — `<AgreementSigningStep />` renders `<DocusealForm src={embedUrl} onComplete={...} />` from `@docuseal/react`. Carrier signs *inside* the portal, not redirected away.
5. **Post-sign field locking** — fields used in the agreement template render read-only with a lock icon after `agreement.status === SIGNED`. Back-navigation still works; locked fields just refuse edits.
6. **Root-cause fixes for the two known UX bugs** — address typeahead surfaces errors visibly with a manual-entry fallback; TIN field accepts EIN or SSN formats and validates at the field, not in the schema.
7. **Session model migration** — `OnboardingSession` adopts `currentStepId: string` + `completedStepIds: string[]` (Prisma migration); existing rows backfill by mapping `currentPhase` → first stepId of that phase.

The 9-stage flow: **Welcome → Company → Equipment → Drivers → Cost Analysis → Lane Preferences → Sign → Documents → Complete.**

## Capabilities

### Must Have (P0)

#### Engine + schema (UI-only, pure-function)

- **Engine module** at `features/carrier-portal-v2/engine/`:
  - `evaluatePredicate(predicate, session) → boolean` — supports `eq`, `in`, `and`, `or`, `not` operators on dot-paths.
  - `resolveContext(session, dotPath) → unknown` — resolves `answers.<stepId>.<questionId>`, `fmcsa.<field>`, `invitation.<field>`, `agreement.<field>` against the session context.
  - `getVisibleSteps(schema, session) → Step[]` — flattens phases × steps and filters by phase + step predicates.
  - `getNextStepId(schema, session, currentStepId) → string | null` — linear walk over visible steps.
  - `getPrevStepId(schema, session, currentStepId) → string | null` — linear walk backwards.
  - `computeInvalidations(schema, session, trialAnswers) → string[]` — returns ids of completed steps that flip to hidden under the trial state. Locked steps' fields throw a `LockViolationError` instead of being added to the invalidation list.
- **Schema module** at `features/carrier-portal-v2/schema/` — one TS file per phase (`welcomePhase.ts`, `companyPhase.ts`, `equipmentPhase.ts`, `driversPhase.ts`, `costAnalysisPhase.ts`, `lanePreferencesPhase.ts`, `signingPhase.ts`, `documentsPhase.ts`, `completePhase.ts`), composed by `onboardingSchema.ts`. Question definitions retain the existing question content with these v2 corrections:
  - **`company.legalName` is the primary required identity field** — what's shown on the tax return; always collected. Persisted to new `Carrier.legalName String?` column on save; locked after signing.
  - **`company.dbaName`** (renamed from `company.name`) **is conditional** — gated by a Yes/No `company.hasDba` toggle: "Do you operate under a different name (DBA)?". Only visible + required when `hasDba === 'yes'`. Default visible state: hidden. Persisted to new `Carrier.dbaName String?` column on save; **not** in the lock list (DBAs can change without re-signing). On every Carrier write, `portalCompanyService` recomputes `Carrier.name = dbaName ?? legalName` so the existing `Carrier.name` display column stays correct without touching any downstream reader.
  - **`company.signatoryName` and `company.signatoryTitle` are new Company-phase questions** — added so the lock-after-signing contract has a real Company surface to lock against (today signatory data is captured only at signing time). Both are simple text inputs; both land in the lock list.
  - **`company.taxClassification`, `company.tinType`, `company.tin` are persisted to new Carrier columns** — `Carrier.taxClassification String?`, `Carrier.tinType String?`, `Carrier.tin String?`. TIN stored as **plaintext** for now (matches the existing `Carrier.ein` precedent; see Risks for the PII follow-up). All three land in the lock list.
  - **`company.mcNumber` is conditional, gated by `company.hasMcAuthority`** — the first step in the Company phase is `company-authority-question` ("Do you have MC authority?" Yes/No). MC# entry and (for the No path) the entire business-details form fold into **this same step** via progressive disclosure, NOT separate sub-steps. Path branches:
    - **Yes** → MC# input reveals inline beneath the Yes toggle (left-bordered conditional reveal). CTA: "Look up my authority". Submitting advances to `company-fmcsa-verification` (side-effect FMCSA lookup), then `company-confirm` (review FMCSA-prefilled fields).
    - **No** → amber callout + the full business-details form (legalName, hasDba/dbaName toggle, taxClassification, tinType, tin, dotNumber optional, phone, email, address) reveals inline beneath the No toggle. CTA: "Continue". Submitting persists directly and advances to the next phase (Equipment). **No `company-mc-entry`, `company-fmcsa-verification`, or `company-confirm` step exists on the No path.**
    - DOT# remains always collected (intrastate carriers still need it; the GVWR-driven DOT-required callout is an Equipment-phase concern). On the No path it's optional with a "if you have one" hint; on the Yes path it's prefilled by FMCSA.
    - **Rationale** — collapsing 3 plan-spec steps into one screen via disclosure reduces the click-through depth, eliminates a useless "verification" loading screen for intrastate carriers, and matches the progressive-disclosure principle established for the rest of the schema.
  - **`drivers.entries` is conditional, gated by `drivers.hasEmployeeDrivers`** — first step in Drivers phase asks "Do you have employee drivers?" Yes/No:
    - **Yes** → render the driver-list builder.
    - **No** → render a single confirmation screen ("Got it — you're the only driver running loads.") with Continue. The phase completes; `drivers.entries` is persisted as `[]`. Owner-operators don't see the driver-list builder.
  - **General UX principle: progressive disclosure** — for any optional/conditional field, prefer a Yes/No toggle that reveals the follow-up over showing an optional input by default. The engine's `visibility` predicate supports this declaratively in the schema; no special component logic needed.
- **Schema types** — `Schema`, `Phase`, `Step`, `Question`, `Predicate`, `PrefillBinding`, `SideEffect`, `Session`, `Answers` — exported from `engine/types.ts`. Step types: `segmentation`, `input`, `verification`, `signing`, `upload`, `review`, `checkpoint`, `complete`, plus the two phase-specific renderers `costAnalysis` and `lanePreferences` (see Step-type renderers below).
- **`SigningStepDef.locksFields: string[]`** — declarative list of 8 dot-paths that become read-only after the signing step completes:
  ```ts
  locksFields: [
    'company.legalName',
    'company.mcNumber',           // Yes path only — gated by visibility
    'company.dotNumber',
    'company.signatoryName',
    'company.signatoryTitle',
    'company.taxClassification',
    'company.tinType',
    'company.tin',
  ]
  ```
  Lock enforcement runs at **two layers** for v2: (1) UI — `<LockableField />` renders read-only with the lock icon; (2) server — `portalCompanyService` rejects POSTs mutating any locked dot-path with HTTP 422 when `Carrier.dispatchAgreementSignedAt IS NOT NULL`. The list of locked paths is shared between client and server via a single source-of-truth export from `signingPhase.ts`.
- **Engine purity guarded by ESLint** — `features/carrier-portal-v2/engine/**/*.ts` MUST NOT import from any file outside `engine/` except `engine/types.ts`. Enforced via `dependency-cruiser` rule `no-impure-engine-imports`.

#### Step-type renderers

- **`<SegmentationStep />`** — card-grid question renderer for the Welcome step. Single question: `carrier_type` (owner-operator / small-fleet / dispatcher-carrier). **Welcome eyebrow rule**: render `"Invited by {Organization.name}"` when the carrier reached the portal via a `CarrierInviteToken` (the inviting org resolves from `token → organizationId → Organization`; org is guaranteed non-deleted because token validation rejects tokens whose org is soft-deleted — see Backend changes); fall back to `"Invited to {config.appName}"` for self-registration. The app-name comes from `hussle-app-dispatch-ui/src/config.ts` — never hardcoded.
- **`<InputStep />`** — generic Formik+Yup form renderer. Reads `step.questions[]` and renders each via the right `@mocho/ui/components/form-fields` component based on `question.fieldType`. Validates via a Yup schema *built from the question definitions* (not the broken `buildPhaseSchema.ts` approach — see Key Decisions). Supports `prefillFrom` bindings that auto-fill empty fields from `resolveContext`.
- **`<CostAnalysisStep />`** — dedicated step renderer for the Cost Analysis phase (the cost UX is a structured fleet P&L ledger, not a flat form). Reads the cost schema and composes already-shipped primitives:
  - `<LedgerSection>` × 3 (Fixed costs / Variable costs per mile / Operating assumptions)
  - `<LedgerGroup>` for sub-totals within each section
  - `<AssetPaymentRow>` for per-asset equipment payments. Each row corresponds to a real `Vehicle` row created in the Equipment phase (keyed by stable `Vehicle.id` — see Equipment-service upsert refactor in Backend changes). Ownership toggle (owned/financed) writes through to `Vehicle.ownership`; amount writes through to `Vehicle.loanPayment`; insurance row writes through to `Vehicle.insuranceMonthlyCost`. **Hybrid storage**: per-vehicle facts go to `Vehicle` columns (single source of truth for settlements/expenses); everything else lives in `OnboardingSession.answers.costAnalysis` JSON.
  - `<EditableExpenseRow>` for dynamic `policies[]` + `subscriptions[]` arrays (JSON only).
  - `<ExpenseRow>` for fixed-key cost fields (overhead, fuel inputs, operating assumptions — all JSON).
  - `<ComputedLine>` for derived values (fuel/mi, owner-pay monthly).
  - `<RateCard>` with primary (min book rate) + secondary (break-even CPM) blocks. **Break-even is computed on read** from stored inputs — no `Carrier.breakEvenCpm` column. `Carrier.minimumRatePerMile` is the only persisted output.
  - Step is `dirty`-aware: empty state disables Continue + renders `RateCard` with the `emptyState` prop.
  - Save writes happen in a single transaction: N `Vehicle` row updates + 1 `OnboardingSession.answers` merge + 1 `Carrier.minimumRatePerMile` update.
- **`<LanePreferencesStep />`** — dedicated step renderer for the Lane Preferences phase (two scopes × three sections × per-driver inheritance). Composes:
  - `<ScopeBar>` to switch between `Fleet default` and `Per-driver overrides`.
  - Driver chip row (`<DriverChip>` × N) with `<ToggleButtonGroup>` filter (All / Customized only), header showing "**N** of M customized", and edge-fade scroll masks. Supports 10+ drivers. Empty state when no overrides exist. Each chip keys on stable `Driver.id` (see Drivers-service upsert refactor in Backend changes).
  - `<EditingCallout>` shown in per-driver scope above sections.
  - **Section 1 — Lanes**: `<LaneStateMap>` (US state grid; click cycles neutral → preferred → avoid; region presets).
  - **Section 2 — Schedule**: `<ScheduleGrid>` (7-day tri-state on/flex/off) + `<SchedulePresetGroup>` (5 presets) + 2× `<OptCard>` (max miles from home, max days out).
  - **Section 3 — Freight types**: 10× `<FreightChip>` (tri-state neutral/on/avoid; multi-select). Freight enum extended from 8 → 10 values (adds `containers`, `hazmat`, `oversize`, `auto_haul`, `tanker`).
  - Each section renders `<SectionHead>` with optional `<OverrideBadge>` + reset link in per-driver scope. Inherited sections render at `opacity: 0.65` with "Override for &lt;driver&gt;" link.
  - **Hybrid storage**: writes go to per-driver `Driver` columns (`Driver.preferredLanes Json?`, `Driver.maxDaysOut`, `Driver.homeBaseCity/State`, new `Driver.weeklySchedule Json?`, new `Driver.freightPreferences Json?`) where columns exist; fleet defaults write to new `Carrier` columns (`Carrier.preferredLanes Json?`, `Carrier.weeklySchedule Json?`, `Carrier.homeBaseCity/State`, `Carrier.freightPreferences Json?`, `Carrier.maxDaysOut`); everything also mirrored in `OnboardingSession.answers.lanePreferences` as a parallel ledger during transition. `DriverAvailability` table is **untouched** — the on/flex/off pattern is a *preference* with its own column, not a *schedule* with time windows.
- **`<VerificationStep />`** — "Looking up your authority..." waiting UI. Subscribes to a session-state field (`session.fmcsaSnapshot`) and advances when it lands. **Multi-state degraded path** (renders distinct UI per state, not one generic error):
  - **Found** → advance to `company-confirm` automatically.
  - **Not found** (MC# returned no match) → Callout asks the carrier to check the number; CTA: "Try a different number" + secondary "Continue without FMCSA".
  - **Service problem** (network/timeout/provider-stubbed) → Callout explains the lookup is temporarily unavailable; CTA: "Retry" + secondary "Skip and enter manually".
  - Multi-match / ambiguous-data states inherit the "skip and enter manually" fallback for v2.
- **`<AgreementSigningStep />`** — the MUST-INCLUDE piece. **Single-document UX for v2** (Dispatch Agreement only); the shipped focus-mode primitives (`DocumentRow`, `FocusHeader`, `DotTrail`, `DocuSealStage`, `FocusFooter`) support N documents — see "Out of Scope (deferred) — Multi-document signing UX" for future expansion.
  - On mount: `GET /api/v1/agreements?carrierId={carrierId}&templateKey=DISPATCH_AGREEMENT` (extends existing endpoint).
  - If agreement is `SIGNED` → auto-advance via `engine.getNextStepId` (no embed render).
  - If agreement is `PENDING` and `embedUrl` is fresh → render `<DocusealForm src={embedUrl} onComplete={handleSigned} />`.
  - If no agreement exists → `POST /api/v1/agreements { carrierId, templateKey }` to create it, then render the embed with the returned `embedUrl`.
  - `handleSigned` does NOT persist signing — webhook owns persistence. It only dispatches `advanceToNextStep` to navigate.
  - On *every* mount (including back-from-Documents): re-fetch agreement status. If the carrier closed the tab mid-sign and the webhook fired, this surfaces the SIGNED state and auto-advances.
- **`<UploadStep />`** — document upload UI. **Required documents in v2: COI only** (Certificate of Insurance). W-9 removed — structured TIN/legalName/taxClassification data captured in Company phase is now authoritative; the gate reads `Carrier.tin IS NOT NULL` instead of the legacy `Carrier.w9OnFile` boolean (see Backend changes). Carrier Packet also dropped (replaced by structured Company-phase data). `documentsPhase.ts` schema declares: `documents: [{ id: 'coi', label: 'Certificate of Insurance', required: true }]`. Presigned-S3 upload via existing portal endpoints. Auto-advances when COI reaches `Pending` or `Verified`. The `<UploadZone>` primitive supports N zones if W-9 / Carrier Packet are ever needed back for non-MC carriers — schema-only change.
- **`<ReviewStep />`** — read-only summary with inline edit links per displayed field. Clicking edit dispatches back-nav to the originating step (respecting lock rules).
- **`<CheckpointStep />`** — celebratory milestone screen between phases. Acknowledged by carrier click.
- **`<CompleteStep />`** — terminal "all done" screen. Layout per `docs/screenshots/onboarding/carrier_complete.png`:
  - All-green stepper (every phase ✓).
  - Centered green check circle, **personalized headline** (`"You're submitted, {signatoryFirstName}."`).
  - Body copy referencing the assigned dispatcher by name (`"{dispatcherName} will review your application and activate your account — usually within a few hours. You'll get a text when you're live."`) — resolved from `session.invitation.dispatcher` context.
  - **"WHAT YOU COMPLETED" summary card** — checklist rendered from the engine's `completedStepIds`. Each row pulls a short summary from the schema's `completeSummary?: (answers) => string` field per step. Examples: "Company info — {legalName} · MC-{mcNumber}", "2 trucks added and configured", "Dispatch Agreement signed", "COI uploaded · Pending dispatcher review".
  - "⚡ One thing to do after activation" info callout (static copy from `completePhase.ts`).
  - No "next steps" button — terminal state. Magic link remains valid; if the carrier returns, the engine routes them back here.

#### Portal shell + navigation

- **`<PortalShell />`** — layout wrapper, three regions:
  - **Header** (dark navy bar + white sub-bar): brand mark left (`FleetCommand / Carrier onboarding`), 6-phase stepper centered, **🔒 Secure** indicator right. Header is sticky.
  - **Content slot** (light-gray page background): renders the active step component, centered with max-width.
  - **`<PortalFooterBar />`** sticky bottom: "✓ Progress saved" indicator left · current location label (e.g., "Equipment · Q2") · **Save & Exit** button right.
  - Routes to the right step renderer based on `session.currentStepId`.
- **`<PortalStepper />`** — horizontal stepper visualizing the **6 carrier-facing phases** (Company / Equipment / Drivers / Costs / Preferences / Documents) — *not* the underlying engine steps. The Welcome and Signing steps are intentionally *not* shown in the stepper (Welcome is a pre-stepper landing; Signing folds visually into Documents). Each phase shows a numbered badge that swaps to a green checkmark when `getVisibleSteps(schema, session)` reports all steps in that phase are in `completedStepIds`. Active phase's badge is filled blue with the phase label colored blue. Replaces the existing broken stepper.
- **`<PortalFooterBar />`** — three-column footer. The "Progress saved" pill is bound to a `lastSavedAt` selector; shows a brief loading spinner during in-flight saves. The center label resolves the current step's phase label + question number (1-indexed within visible phase steps). The Save & Exit button dispatches `saveAndExitRequest` → persists current answers → navigates to a "We saved your progress" intermediate screen with the magic-link reminder + invite-email's resend option, then closes the tab if launched from SMS.
- **Save & Exit** — implemented as a saga that calls the existing `submitStep` endpoint with the current draft state, then routes to a `<SavedAndExitView />` confirmation screen (still inside the portal, no auth change). The invite token remains valid; the carrier can return via the same magic link.
- **Back navigation** — clicking "Back" dispatches a `navigateBack` action that:
  1. Computes `getPrevStepId(schema, session, currentStepId)`.
  2. If the target step has its `currentAnswers` (carrier visiting a completed step), renders read-only with edit affordance.
  3. If the carrier edits and submits, `computeInvalidations` runs on the trial state; any non-locked invalidations are shown in a confirmation modal listing what will reset. Locked fields refuse edits with the lock-icon tooltip.

#### Lockable form field

- **`<LockableField />`** — a wrapper around `@mocho/ui` form fields. When `locked=true`, renders the underlying value as read-only with a MUI lock badge and a tooltip: *"Locked after agreement signed. Contact your dispatcher to amend."* Receives lock state via a selector derived from `agreement.status === 'SIGNED'`.
- All Company-phase fields whose question IDs match a `SigningStepDef.locksFields` entry render via `<LockableField />` instead of the base field.

#### Bug-fix components

- **`<AddressTypeaheadField />`** — AWS Location-backed autocomplete:
  - Surfaces network errors with a visible inline error message + "Retry" button.
  - On 3 consecutive failures or explicit "Skip lookup" click, falls back to a manual-entry mode rendering address line 1 / line 2 / city / state / zip / country as plain text fields.
  - Never swallows errors. All API failures logged via `enqueueSnackbar` at most once per session (deduplicated).
  - Replaces the existing silent-fail typeahead.
- **`<TinField />`** — TIN/EIN field:
  - Accepts EIN format (`XX-XXXXXXX`) or SSN format (`XXX-XX-XXXX`).
  - Normalizes input on blur (strips non-digits, re-inserts hyphens in the canonical position based on length: 9 digits → `XX-XXXXXXX` by default; if the carrier explicitly toggled "I'm an individual", `XXX-XX-XXXX`).
  - Validates at the field level via a Yup schema fragment. **Not** in `buildPhaseSchema.ts` — that file is deleted as part of this PR; per-question Yup schemas are derived inside `<InputStep />`.

#### Backend changes (dispatch-api)

- **Prisma migration `AddOnboardingStepIdsToSession`**:
  - Adds `currentStepId: String?` to `OnboardingSession`.
  - Adds `completedStepIds: String[]` (Postgres `text[]`) with default `[]`.
  - Backfill DDL: for existing rows, sets `currentStepId` to the first stepId of the schema phase matching `currentPhase` (mapping table inlined in the migration), and `completedStepIds` to the union of stepIds for all phases ≤ `currentPhase - 1`.
  - Keeps `currentPhase` and `currentQuestionIndex` columns for one release as derived/legacy; drops them in a follow-on once nothing reads them.

- **Prisma migration `PromoteCompanyFieldsToCarrierColumns`** (new):
  - Adds `Carrier.legalName String?`, `Carrier.dbaName String?`, `Carrier.taxClassification String?`, `Carrier.tin String?`, `Carrier.tinType String?`.
  - Backfill: `Carrier.legalName = Carrier.name` for existing rows (legacy rows had `name` holding the legal name); `dbaName / taxClassification / tin / tinType = NULL` (data only exists in `OnboardingSession.answers` for completed onboardings and is left as-is).
  - `Carrier.ein` left in place — overlaps with `Carrier.tin` when `tinType=EIN`, but referenced by existing admin flows; consolidation/deprecation is a future cleanup, not part of this milestone.

- **Prisma migration `AddLanePreferenceColumns`** (new):
  - Adds Carrier fleet-default columns: `Carrier.homeBaseCity String?`, `Carrier.homeBaseState String?`, `Carrier.preferredLanes Json?`, `Carrier.weeklySchedule Json?`, `Carrier.freightPreferences Json?`, `Carrier.maxDaysOut Int?`.
  - Adds Driver per-driver-override columns where missing: `Driver.weeklySchedule Json?`, `Driver.freightPreferences Json?`. (Existing `Driver.preferredLanes Json?`, `Driver.maxDaysOut Int?`, `Driver.homeBaseCity/State String?` are reused.)
  - No backfill — NULLs are interpreted as "inherit fleet default" per the engine's `effective(driverId, section)` resolver (lives in dispatch's load-matching service, not in the engine module).

- **Prisma migration `DropLegacyComplianceFlags`** (new):
  - Drops `Carrier.w9OnFile` and `Carrier.carrierPacketOnFile`.
  - Runs **after** the reader-side coordinated edit (see `onboardingGate` change below) so no live code path reads a column that no longer exists.
  - `DocumentType.W9` enum value left in place — historical Document rows of that type must still validate.

- **`portalService` accepts stepId-keyed save**:
  - `saveAnswer({ stepId, questionId, value })` and `submitStep({ stepId, answers })` endpoints.
  - The old phase-keyed save endpoints (`saveCompany`, `saveEquipment`, …) remain functional for one release (mapped internally to stepId-keyed shape) so any half-completed in-flight session continues to save.
  - Computes and persists `agreementLocked: boolean` on the session-summary response by checking the carrier's latest `DISPATCH_AGREEMENT` status.

- **`portalCompanyService` rewrite**:
  - On save, writes `legalName / dbaName / taxClassification / tin / tinType / signatoryName / signatoryTitle` to the corresponding new `Carrier` columns.
  - Recomputes `Carrier.name = dbaName ?? legalName` on every write so the display-name column stays consistent without touching downstream readers.
  - Enforces the **server-side lock** — rejects updates to any dot-path in the shared `LOCKS_FIELDS` constant (imported from `signingPhase.ts`-equivalent on the server side, or duplicated as a tested constant) with HTTP 422 `{ code: 'FIELD_LOCKED', field }` when `Carrier.dispatchAgreementSignedAt IS NOT NULL`. Locked field changes never silently succeed.

- **`portalEquipmentService` upsert-by-id refactor** (prereq for Cost Analysis per-asset rows):
  - Drops the current wipe-and-recreate behavior (`deleteVehiclesByCarrierId` + `createVehicles` from scratch).
  - `SaveEquipmentInput.vehicles[]` gains an **optional `id` field**. Service diffs the incoming list against existing rows: rows with a matching `id` are updated, rows without an `id` are created, existing rows whose `id` is missing from the incoming list are deleted.
  - Returned shape still includes `id` for each row so the UI can round-trip IDs on subsequent saves.
  - `Vehicle.id` becomes **stable across re-saves**, which Cost Analysis and (later) Drivers-to-Vehicle assignment both depend on.

- **`portalDriversService` upsert-by-id refactor** (prereq for Lane Preferences per-driver overrides):
  - Same shape change as Equipment — `SaveDriversInput.drivers[]` gains an optional `id`; service does upsert-by-id; returned shape includes `id`.
  - `Driver.id` becomes stable across re-saves, which Lane Preferences per-driver chip keys depend on.

- **`onboardingGate.checkCarrierOnboarding` reader migration**:
  - Stops reading `Carrier.w9OnFile`. Reads `Carrier.tin IS NOT NULL` as the equivalent signal (structured TIN data captured in Company phase replaces the W-9 file upload).
  - Coordinated edit across all current `w9OnFile` readers: `src/shared/onboardingGate.ts`, `src/loads/services/loadService.ts`, `src/loads/repositories/loadRepositoryPrisma.ts`, `src/carriers/jobs/documentCheckJob.ts`, `src/carriers/services/carrierComplianceSubscriber.ts`, `src/carriers/compositionRoot.ts`, `src/carriers/validators/carrierValidators.ts`, `src/carriers/types/*.ts`. Same edit for `carrierPacketOnFile` readers.
  - `portalDocumentsService.COMPLIANCE_FLAG_MAP` keeps the `W9` entry as a no-op (defense in depth — if any legacy upload route still fires, the flag write is harmless and not read); drops the `CARRIER_PACKET` entry.

- **`carrierInviteTokenRepoPrisma.findByToken` hardening** (security correctness):
  - Existing filters (`revokedAt: null`, `expiresAt: { gt: now }`) extended with `organization: { is: { deleted: false } }` and `carrier: { is: { deletedAt: null } }`. Tokens for soft-deleted orgs or carriers no longer validate.
  - Returns null on rejection — existing middleware handles null as a 401/403.

- **Cascade token revocation on soft-delete** (defense in depth):
  - When an `Organization` is soft-deleted (`deleted: true`), revoke all related `CarrierInviteToken` rows (set `revokedAt: now`). New helper `revokeByOrganizationId` added.

## User Flows

### Flow 1 — Happy path, end-to-end

1. Dispatcher creates a carrier invitation (existing dispatcher UI, unchanged). `CarrierInviteToken` row created.
2. Carrier receives SMS with magic link, taps it, lands on the portal. Token validates (revoked / expired / org-deleted / carrier-deleted all reject).
3. **Welcome** — eyebrow renders "Invited by {Organization.name}". Selects `carrier_type` (owner-operator / small-fleet / dispatcher-carrier). Submit.
4. **Company** — first step asks "Do you have MC authority?" (Yes/No):
   - **Yes path**: enters MC#; `VerificationStep` loads (FMCSA lookup fires); FMCSA snapshot lands (or the multi-state degraded path resolves); `company-confirm` renders FMCSA-prefilled fields. Carrier reviews/edits `legalName`, `hasDba`/`dbaName`, address, `taxClassification`, `tinType`, `tin`, `signatoryName`, `signatoryTitle`, phone, email. Submit writes to new `Carrier` columns + computes `Carrier.name = dbaName ?? legalName`.
   - **No path**: the full business-details form reveals inline; same field set; same write semantics. No FMCSA step.
5. **Equipment** — adds/edits vehicles via the list-builder. Each save round-trips stable `Vehicle.id`s (upsert-by-id; no wipe-and-recreate). Submit.
6. **Drivers** — gated by "Do you have employee drivers?" Yes/No. Yes → list-builder with stable `Driver.id`s. No → confirmation screen + persist `drivers.entries = []`. Submit.
7. **Cost Analysis** — `<CostAnalysisStep />` renders the fleet P&L ledger. Per-asset payment rows reference the stable `Vehicle.id`s from step 5; ownership + payment amount + insurance write through to `Vehicle.loanPayment / ownership / insuranceMonthlyCost`. Policies, subscriptions, overhead, owner pay basis, fuel, wear/ops per-mile, operating assumptions land in `OnboardingSession.answers.costAnalysis`. Live `RateCard` shows break-even CPM + min book rate. Submit transactionally writes Vehicle updates + answers merge + `Carrier.minimumRatePerMile`.
8. **Lane Preferences** — `<LanePreferencesStep />` renders `Fleet default` scope by default. Three sections: state map, weekly schedule (on/flex/off), freight types (10 chips). Carrier can toggle to `Per-driver overrides` and customize per-driver via the chip bar. Submit writes fleet defaults to new `Carrier` columns + per-driver overrides to `Driver` columns (where present) + mirrors everything in `answers.lanePreferences`.
9. **Sign** — `AgreementSigningStep` mounts:
   - Checks for existing agreement → none → POSTs `/api/v1/agreements`, gets `embedUrl`.
   - Renders `<DocusealForm src={embedUrl} onComplete={...} />`.
   - Carrier signs inside the iframe; DocuSeal fires `onComplete`; portal navigates to Documents.
   - Webhook fires server-side, finalizes the agreement, locks the 8 listed fields client-side **and** server-side.
10. **Documents** — carrier uploads **COI only** (one required document). When COI reaches `Pending` → step auto-completes.
11. **Complete** — terminal screen. Session marked complete.

### Flow 2 — Resume after browser close mid-sign

1. Carrier is at the Sign step; clicks into the DocuSeal iframe; completes signature; closes browser before `onComplete` fires (or before the portal-side navigation resolves).
2. DocuSeal still posts the webhook → API `finalizeAgreement` runs → agreement is `SIGNED` server-side.
3. Carrier opens the magic link later. Portal loads, fetches session, resolves `currentStepId` to the Sign step.
4. `AgreementSigningStep` mounts → fetches agreement → `status === SIGNED` → dispatches `advanceToNextStep` → portal navigates to Documents.
5. Carrier never sees the signing screen again.

### Flow 3 — Carrier back-navigates after signing

1. Carrier completes Sign + Documents but realizes they want to update the cost numbers.
2. Clicks the Cost Analysis label in the stepper.
3. Cost Analysis fields are editable (not in `locksFields`). Carrier updates a number and submits.
4. `computeInvalidations` returns empty (no downstream phases depend on cost numbers). Submit goes through; no modal.
5. Carrier navigates further back to Company.
6. All 8 lock-list fields (`legalName`, `mcNumber`, `dotNumber`, `signatoryName`, `signatoryTitle`, `taxClassification`, `tinType`, `tin`) render via `<LockableField />` — read-only with lock icon. Other Company fields (address, phone, email, `dbaName`) remain editable.
7. Carrier tries to click into `legalName` → tooltip: *"Locked after agreement signed. Contact your dispatcher to amend."* If a forged POST attempts to mutate a locked field, the server rejects with HTTP 422 `{ code: 'FIELD_LOCKED', field: 'company.legalName' }`.

### Flow 4 — Address typeahead degraded mode

1. Carrier types into the address field. AWS Location returns a 5xx.
2. Inline error: *"Address lookup is temporarily unavailable. Retry?"* with a Retry button.
3. Carrier retries twice; both fail. Component switches to manual-entry mode automatically (or carrier clicks "Skip lookup").
4. Manual entry shows address line 1 / line 2 / city / state / zip / country as plain text fields. Carrier completes, submits.

### Key Decisions

- **UI-only engine for v2** — engine + schema live in dispatch-ui under `features/carrier-portal-v2/engine/`. API-side engine deferred. Smallest blast radius; reuses existing portal session endpoints with one new stepId-keyed action. PROJECT.md's "Engine is an interface, not a rewrite" supports this.
- **Schema as TypeScript code, not JSON in DB** — schemas live in source under `schema/` and ship via PR. Per-session schema version pinning isn't a real concern when there's one active schema and deployments are coordinated. PROJECT.md's "Schema is data, stored as code first" locks this.
- **Welcome step asks `carrier_type` only** — `service_tier` is a dispatcher decision, not a carrier self-select. One segmentation question keeps the welcome screen frictionless.
- **Signing lands between Lane Preferences and Documents** — late mid-flow. Pre-Documents placement preserves the "signed-but-incomplete" state (carriers can abandon after signing without completing uploads) but keeps the full operational profile captured before legal binding.
- **`@docuseal/react` embed, not redirect** — carrier signs inside the portal. Webhook owns persistence; `onComplete` is for client-side navigation only.
- **Auto-advance on SIGNED at every signing-step mount** — covers the close-mid-sign race. Webhook is the source of truth; UI re-checks on every load.
- **Field locking via `SigningStepDef.locksFields` + `<LockableField />`** — declarative. The list of locked dot-paths lives in the schema (`signingPhase.ts`), not scattered in component code. Lock state derived from `agreement.status === SIGNED`. Back-nav allowed; lock just refuses edits.
- **Address typeahead surfaces errors, falls back to manual entry** — root-cause fix for the silent-fail bug. AWS Location errors visible to the carrier with retry; auto-fallback after 3 failures or explicit "Skip lookup".
- **TIN validation at field level, not schema level** — `<TinField />` accepts EIN (`XX-XXXXXXX`) or SSN (`XXX-XX-XXXX`), normalizes on blur. `buildPhaseSchema.ts` (the source of the strict-regex bug) is deleted; per-question Yup fragments derived inside `<InputStep />` instead.
- **Session model migration: `currentStepId` + `completedStepIds`** — DB aligns with engine vocabulary. `currentPhase` + `currentQuestionIndex` retained for one release as legacy; dropped in a follow-on. Backfill maps existing rows by phase number.
- **`features/carrier-portal/` deleted in same PR as v2 ships** — no `-legacy` keepalive, no parallel route. Single replacement, clean tree.
- **No event-sourced ledger, no outbox** — session state stays a single Prisma row. Engine purity gives us testability; event-sourcing's full benefits aren't needed at this scale.
- **Eligibility sidebar / dispatcher real-time / co-pilot / OCR all deferred** — out of scope for v2 first cut. Confirmed by user.
- **Schemas remain TS files** — `schema/*Phase.ts`. Question content (labels, options, validation) preserved from the current `features/carrier-portal/questions/*.ts` files where it was correct.

- **Cost analysis storage: hybrid (Vehicle columns + answers JSON)** (Delta 1). Per-vehicle facts go to existing `Vehicle.loanPayment / ownership / insuranceMonthlyCost` columns — single source of truth for settlements/expenses, which already read those columns. Everything else lives in `OnboardingSession.answers.costAnalysis` JSON. Break-even CPM is computed on read (no `Carrier.breakEvenCpm` column). Equipment service rewrite to upsert-by-id (the per-asset references demand stable `Vehicle.id`s) is a coupled prereq.

- **Lane preferences storage: hybrid + new Carrier columns + mirror in answers JSON** (Delta 2). Per-driver overrides write to existing/new `Driver` columns. Fleet defaults write to new `Carrier` columns. Everything mirrored in `answers.lanePreferences` as a parallel ledger during the transition (drop the JSON mirror in a future cleanup once column readers are exercised in production). Drivers-service upsert-by-id refactor is a coupled prereq for stable `Driver.id` references.

- **Schedule mismatch resolved via new `weeklySchedule` columns** (Delta 2). On/flex/off is a *preference* (do you want to work weekends), not a *schedule* (when can you be reached). `Driver.weeklySchedule Json?` + `Carrier.weeklySchedule Json?` hold the preference; `DriverAvailability` stays for real time-window scheduling. Avoids overloading `DriverAvailability` with two different semantics.

- **Documents = COI only** (Delta 3). Dispatch Agreement moves to mid-flow `<AgreementSigningStep />`. W-9 removed — structured TIN/legalName/taxClassification captured in Company phase is now the authoritative signal. Carrier Packet also dropped (replaced by structured Company-phase data). `Carrier.w9OnFile` + `carrierPacketOnFile` columns are dropped in this milestone; `onboardingGate` reader migrates to `Carrier.tin IS NOT NULL`. `DocumentType.W9` enum value left in place (historical document rows still need to validate).

- **Carrier column promotions for the lock-after-signing set** (Delta 4 expanded). `legalName / dbaName / taxClassification / tin / tinType` get real Carrier columns. `Carrier.name` becomes the display column computed as `dbaName ?? legalName` on every write — keeps all existing readers working. TIN stored as **plaintext** for now (matches existing `ein` precedent; PII follow-up tracked in Risks).

- **Lock enforcement runs UI + server-side** (Delta 4 follow-up #2). UI uses `<LockableField />`; server-side `portalCompanyService` rejects locked-field mutations with HTTP 422 when `Carrier.dispatchAgreementSignedAt IS NOT NULL`. The shared `LOCKS_FIELDS` constant is the single source of truth across client and server.

- **Color-blind safety as a cross-cutting design rule** (Delta 5). Every component using color to convey state pairs it with a shape glyph; `aria-label` encodes the state when the visual signal is iconographic. Rule documented here AND appended to `.claude/skills/design-principles/SKILL.md` so future features inherit it. Pre-execution spot-check audits the 30+ shipped primitives.

- **Welcome eyebrow = "Invited by {Organization.name}"** (Delta 7). Personalized when the carrier reached the portal via an invite token; `config.appName` in the generic fallback (self-registration). `Organization.name` is already a column (no schema change); `CarrierInviteToken.organizationId` already FKs to it. No per-user-name attribution — orgs are the durable identity from the carrier's perspective; users change between invite and signing.

- **Carrier invite token validation hardening** (Delta 7). `findByToken` adds `organization: { is: { deleted: false } }` and `carrier: { is: { deletedAt: null } }` filters. Cascade revocation on org/carrier soft-delete is the belt-and-suspenders companion. Closes a real security gap (current validation only checks revoked/expired), not just a UX concern.

- **No mockup pass on `<VerificationStep />` or `<company-confirm>`** (Delta 8). Built from text spec using the established component palette. The verification step explicitly handles 3 distinct degraded states (found / not-found / service-problem) so executors don't ship only the happy path.

- **Multi-document signing UX over-built; stays deferred** (Delta 9). `<AgreementSigningStep />` ships single-doc only in v2. The focus-mode primitives are ready for D&A consent / Broker-Carrier Master / Factoring NOA expansion when product wants it — schema-only change.

- **Equipment + Drivers services move to upsert-by-id** (Delta 1 + 2 prereqs). Current wipe-and-recreate makes `Vehicle.id` / `Driver.id` unstable across re-saves, breaking any downstream reference. The refactor is the architectural standard going forward — id-stable list updates instead of "set the whole list."

- **App-name constant sweep** (follow-up #4). `config.appName` becomes the single source of truth across UI surfaces; API gets a parallel `APP_NAME` env var. Hardcoded `"FleetCommand"` strings replaced. Prepares the codebase for the upcoming brand rename without making the rename itself part of this milestone.

- **Stale-onboarding reaper is its own story, not part of this milestone**. Mid-flow row creation (Vehicle, Driver, Document, OnboardingSession with partial answers, Agreement) creates orphan data when carriers abandon. The reaper job — reminder at day 14, dispatcher visibility at day 30, automated cleanup transaction at day 60 — is scoped and designed but tracked as a discrete follow-up so it doesn't bloat this milestone's blocking scope. Until the reaper ships, orphan data accumulates; volume is low enough at current scale that this is acceptable for a 6-week window.

| `@docuseal/react` version pinning surprises with our DocuSeal OSS version | Pin `@docuseal/react` to a version verified compatible with the staging DocuSeal container; smoke-test in dev before staging deploy. |

## Companion Story (separate deliverable — not blocking this milestone)

### Stale-onboarding reaper

**Problem.** Mid-flow row creation (`Vehicle`, `Driver`, `Document` + S3 object, `OnboardingSession` with partial `answers`, `Agreement` if signing was reached) creates orphan data when carriers abandon onboarding. Today's wipe-and-recreate masks part of the problem; the v2 upsert-by-id refactor removes that accidental mitigation. PII (driver names, license info, TIN/SSN in `answers.company.tin`) accumulates without an aging policy.

**Solution.** A scheduled `node-cron` job in dispatch-api with a three-stage cadence:

| Day | Signal | Action |
|---|---|---|
| 14 | `OnboardingSession.lastActiveAt < now - 14d` AND `completedAt IS NULL` AND `Carrier.status = INVITED` | Send carrier reminder via existing notification subscriber (email + SMS where phone is on file). |
| 30 | Same predicate, age ≥ 30 days | Dispatcher dashboard surfaces a "stale invite" badge for manual cancel/extend. |
| 60 | Same predicate, age ≥ `ORPHAN_REAP_DAYS` env (default 60) | **Cleanup transaction** — see below. |

**Cleanup transaction** (`carrierReaperService.reapCarrier(carrierId)`):
1. Soft-delete `Carrier` (`deletedAt = now`, `status = 'ABANDONED'` — new enum value).
2. Soft-delete all `Driver[]` and `Vehicle[]` rows for the carrier.
3. Archive `Document[]` (`isArchived = true`) and delete corresponding S3 objects.
4. Delete `OnboardingSession`.
5. Revoke all `CarrierInviteToken[]` for the carrier via `revokeByCarrierId`.
6. Audit-log entry with carrier identity + last phase reached + reap reason.
7. Emit `carrier.abandoned.reaped` event for any downstream observability.

**Acceptance criteria**:
- New `CarrierStatus.ABANDONED` enum value added (Prisma migration).
- `node-cron` job registered; runs once daily; idempotent (re-running the same day for the same carrier is a no-op).
- Unit test: cleanup transaction is atomic — partial failure leaves no half-deleted state.
- Integration test: stale fixture (`lastActiveAt = 65 days ago`) gets reaped; non-stale fixture (`lastActiveAt = 45 days ago`) does not.
- Reminder + dispatcher-badge wired via existing notification + dispatcher dashboard surfaces.
- `ORPHAN_REAP_DAYS` and reminder/badge thresholds configurable via env.

**Why separate**: scope contains a new cron, two notification touchpoints, a dispatcher UI surface, an S3 cleanup pathway, and a destructive transaction — meaningful enough to ship/test independently. Data-hygiene risk is acceptable for the carrier-portal-v2 milestone window given low onboarding traffic; reaper lands in the next cycle.
