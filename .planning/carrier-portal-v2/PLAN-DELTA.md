## Delta 1 — Cost analysis needs its own step renderer + richer schema

**Plan section**: Step-type renderers (line 63 — `<InputStep />`), Schema module (line 44), User Flows / Flow 1 step 7 (line 178: "Cost Analysis — enters cost numbers")

**Plan currently implies**: Cost analysis is a generic `<InputStep />` reading question definitions and rendering form fields. The schema's `costAnalysisPhase.ts` declares a flat list of cost-number questions.

**Reality** (Rounds 4 + 4.5):
The cost analysis screen is a structured **fleet P&L ledger**, not a flat form:
- **Three `LedgerSection`s** — Fixed costs (monthly) / Variable costs (per mile) / Operating assumptions
- **Per-asset equipment payments** — each truck/trailer rendered as an `AssetPaymentRow` with an Owned/Financed pill toggle and a per-asset amount input
- **Dynamic insurance policies array** — user adds N policies via `EditableExpenseRow` (name + amount + remove)
- **Dynamic subscriptions array** — same pattern, with one fixed "Dispatch / TMS software · included" row pinned at top
- **Owner pay redesign** — per-truck weekly target + Gross/Net pill toggle; computed monthly shown via `ComputedLine` (`× N trucks × 52/12 wk/mo`)
- **Fuel cost computed** — diesel ÷ MPG, rendered as a `ComputedLine`
- **Output** — break-even **cost per mile** AND minimum book rate, both displayed in `RateCard`'s primary + secondary block
- **Empty-form state** — `RateCard` renders em-dash placeholders + "fill in your fleet P&L to see your rate" footer text; Continue disabled

**Proposed plan amendments**:

1. Under **Step-type renderers**, add a new entry between `<InputStep />` and `<VerificationStep />`:

   > **`<CostAnalysisStep />`** — dedicated step renderer for the cost-analysis phase. Reads cost schema and composes already-shipped primitives:
   > - `<LedgerSection>` × 3 (Fixed / Variable / Operating assumptions)
   > - `<LedgerGroup>` for sub-totals within each section
   > - `<AssetPaymentRow>` for per-asset equipment payments (driven by `equipment.assets` from the Equipment phase via `prefillFrom`)
   > - `<EditableExpenseRow>` for dynamic insurance + subscriptions arrays
   > - `<ExpenseRow>` for fixed-key cost fields (overhead, fuel inputs, operating assumptions)
   > - `<ComputedLine>` for derived values (fuel/mi, owner-pay monthly)
   > - `<RateCard>` with primary (min book rate) + secondary (break-even CPM) blocks
   > - Step is `dirty`-aware: empty state disables Continue + renders RateCard with `emptyState` prop

2. Under **Engine + schema / Schema module**, extend `costAnalysisPhase.ts` shape:

   ```typescript
   // costAnalysisPhase.ts answers shape
   interface CostAnalysisAnswers {
     equipmentPayments: Array<{
       assetId: string;           // FK to equipment.assets[].id
       ownership: 'owned' | 'financed';
       monthlyAmount: string;     // "0" when owned
     }>;
     policies: Array<{ id: string; name: string; monthlyAmount: string }>;
     subscriptions: Array<{ id: string; name: string; monthlyAmount: string }>;
     overhead: {
       officeUtilities: string;
       accountingLegal: string;
       bankFeesCardsFactoring: string;
     };
     ownerPay: {
       perTruckWeekly: string;
       payBasis: 'gross' | 'net';
     };
     fuel: { dieselPrice: string; mpg: string };  // fuel/mi derived
     wearOps: { maintenance: string; tires: string; def: string; tolls: string };
     operating: {
       loadedMilesPerMonth: string;
       deadheadPct: string;
       marginPct: string;
     };
     // Computed outputs (not persisted; derived in step renderer):
     // - fixedTotal, variablePerMile, fuelCostPerMile
     // - fixedPerLoadedMile, deadheadAdj, breakEvenCpm, minBookRate
   }
   ```

3. Under **Existing Code to Reuse**, add:

   > **`features/carrier-portal-v2/components/`** — `LedgerSection`, `LedgerGroup`, `ExpenseRow`, `EditableExpenseRow`, `AssetPaymentRow`, `LedgerAddRow`, `ComputedLine`, `RateCard` all shipped and visible at `/dev/onboarding-preview/cost-analysis`. `<CostAnalysisStep />` composes these; no new component work needed.

## Delta 2 — Lane preferences needs its own step renderer + richer schema with per-driver inheritance

**Plan section**: Step-type renderers (line 63 — `<InputStep />` implied), Schema (line 44), User Flows / Flow 1 step 8 (line 179: "Lane Preferences — enters home base, lane preferences, freight preferences")

**Plan currently implies**: Lane preferences is a generic `<InputStep />` with flat questions for lanes + home base + freight preferences.

**Reality** (Rounds 3 + 7 + 7.5):
The lane preferences screen has **two scopes × three sections × per-driver inheritance**:
- **Two scopes**: `Fleet default` and `Per-driver overrides`, switched via `<ScopeBar>` (segmented control with count pill)
- **Per-driver chip bar** in the override scope — supports 10+ drivers with All/Customized-only filter (`ToggleButtonGroup`) and edge-fade gradient masks on horizontal scroll
- **Three sections** per scope (numbered via `<SectionHead>`):
  1. **Lanes** — `<LaneStateMap>` (US state grid; click cycles neutral → preferred → avoid; region presets)
  2. **Weekly schedule** — `<ScheduleGrid>` (7-day tri-state on/flex/off) + `<SchedulePresetGroup>` (5 presets) + 2× `<OptCard>` (max miles from home, max days out)
  3. **Freight types** — 10× `<FreightChip>` (tri-state neutral/on/avoid; multi-select)
- **Inheritance pattern**: per-driver sections show `<OverrideBadge>` + reset link when they diverge from fleet; inherited sections render dimmed (opacity 0.65) with "Override for &lt;driver&gt;" link
- **`<EditingCallout>`** banner shown above sections in per-driver scope

**Proposed plan amendments**:

1. Under **Step-type renderers**, add another new entry:

   > **`<LanePreferencesStep />`** — dedicated step renderer for the lane preferences phase. Composes:
   > - `<ScopeBar>` to switch between `Fleet default` and `Per-driver overrides`
   > - Driver chip row (`<DriverChip>` × N) with `<ToggleButtonGroup>` filter (All / Customized only) and edge-fade scroll masks; supports 10+ drivers
   > - `<EditingCallout>` shown in per-driver scope above sections
   > - Section 1: `<LaneStateMap>` (already built, supports presets + region shortcuts)
   > - Section 2: `<ScheduleGrid>` + `<SchedulePresetGroup>` + 2× `<OptCard>`
   > - Section 3: `<FreightChip>` × 10 in `chip-group` layout
   > - Each section renders `<SectionHead>` with optional `<OverrideBadge>` + reset link in per-driver scope
   > - Inherited sections render at `opacity: 0.65` with "Override for &lt;driver&gt;" link

2. Under **Engine + schema / Schema module**, extend `lanePreferencesPhase.ts` shape:

   ```typescript
   // lanePreferencesPhase.ts answers shape
   type LaneState = 'preferred' | 'avoid';      // neutral = key absent
   type ScheduleState = 'on' | 'flex' | 'off';
   type DayKey = 'mon' | 'tue' | 'wed' | 'thu' | 'fri' | 'sat' | 'sun';
   type SchedulePreset =
     | 'weekdays' | 'weekdays_flex_fri'
     | 'long_haul' | 'regional_61' | 'custom';
   type FreightTypeId =
     | 'dry_van' | 'reefer' | 'flatbed' | 'step_deck' | 'power_only'
     | 'containers' | 'hazmat' | 'oversize' | 'auto_haul' | 'tanker';
   type FreightState = 'on' | 'avoid';          // neutral = key absent

   interface FleetLanePreferences {
     lanes: Record<string /* state code */, LaneState>;
     schedule: Record<DayKey, ScheduleState>;
     schedulePreset: SchedulePreset;
     maxMilesFromHome: number | 'no_limit';
     maxDaysOut: number;
     freightTypes: Record<FreightTypeId, FreightState>;
   }

   interface LanePreferencesAnswers {
     fleet: FleetLanePreferences;
     // Per-driver overrides: each driver may override any subset of sections.
     // A section is "overridden" iff its key is present in this record;
     // absence = inherits fleet default.
     overrides: Record<string /* driverId */, Partial<FleetLanePreferences>>;
   }
   ```

3. **Inheritance check at runtime** (engine concern): For load matching, dispatch looks up `effective(driverId, section) = overrides[driverId][section] ?? fleet[section]`. This logic lives outside the engine module (in dispatch's load-matching service) but the schema shape must enable it.

## Delta 5 — Color-blind safety as a cross-cutting design pattern

**Plan section**: Add to Technical Context / Key Decisions

**Plan currently says**: Nothing about accessibility or colorblind-safety.

**Reality** (Round 7.5): The locked design rule is —
> **Every place where color is the sole signal pairs color with a shape glyph.**

Specific applications in shipped primitives:
- `LaneStateMap` cells: ✓ corner glyph for preferred, ✕ for avoid (matched in legend swatches)
- `DriverChip` status: `LinkOutlined` icon (default = inherits) vs `EditOutlined` (overridden) — shape carries the meaning; tooltip carries the label
- `FreightChip` state: ✓ prefix for on, ⊘ prefix for avoid; strikethrough text on avoid; `aria-label` includes state ("Hazmat — avoided")

Places already color-safe (no change needed): stepper checkmarks, doc tags with text labels, `ScheduleGrid` On/Flex/Off labels, `OverrideBadge` text.

**Proposed plan amendment**: Add to **Key Decisions** (after the existing decisions block, before Risks):

> **Color-blind safety pattern** — every component shipped pre-execution that uses color to convey state pairs it with a shape glyph or text. `LaneStateMap` cells carry ✓/✕ corner badges; `DriverChip` status uses `LinkOutlined`/`EditOutlined` icons; `FreightChip` carries ✓/⊘ prefix glyphs + strikethrough text on avoid. New components introduced during execution must follow the same rule — color is allowed, but never as the sole signal. `aria-label` should encode state when the visual signal is iconographic.
