# Track 4 — Driver Portal Audit & Fixes

> Generated by /prd-refine on 2026-04-23

## Problem

The driver portal is the primary interface for drivers during active loads — they receive an SMS with a magic link, check in, advance load status, and upload documents (BOL/POD). Track 3 (SMS prompts with deep-links) and Track 5 (document upload flow) are now implemented but the portal has never been systematically audited. There are zero frontend tests and zero service/controller tests beyond the auth middleware. Before MVP staging, every driver-facing flow must be verified to work end-to-end across mobile and desktop viewports, and any bugs found must be fixed.

## Solution Overview

Structured audit organized by user flow. Each flow gets a reusable Playwright spec (contributing to V.E2E.1) that exercises the happy path and key error paths at both mobile (375px) and desktop (1280px) viewports. Bugs discovered during each flow's spec are fixed inline as part of that task. A final verification pass re-runs all specs clean.

## Capabilities

### Must Have (P0)
- Playwright specs covering every driver-facing flow, runnable at mobile + desktop
- All bugs found during audit are fixed
- Second full pass confirms all specs pass clean
- Screenshots captured at critical assertions (for V.E2E.2)

### Nice to Have (P1)
- Accessibility audit (color contrast, touch targets, screen reader labels) at mobile viewport
- Performance check (page load time under 3s on throttled 3G)

## User Flows

### Flow 1: Token Authentication (Magic Link)
1. Driver receives SMS with portal URL containing token
2. Driver opens link in mobile browser
3. Portal validates token, shows load summary
4. **Error paths:** expired token (>7 days), revoked token, invalid/malformed token, missing token

### Flow 2: Load Summary View
1. Driver sees load number, status, equipment type, commodity, weight
2. Pickup stop: facility name, address, contact info, appointment time/type
3. Delivery stop: same fields
4. Driver instructions displayed if present
5. Driver greeted by first name
6. **Edge cases:** load with multiple stops, load with no driver instructions, load with FCFS vs APPOINTMENT type

### Flow 3: Status Transitions
1. Driver on DISPATCHED load sees "En Route to Pickup" action button
2. Browser requests GPS permission → captures coordinates on transition
3. DISPATCHED → EN_ROUTE_PICKUP → AT_PICKUP → IN_TRANSIT → AT_DELIVERY → DELIVERED
4. Button label updates at each step
5. Terminal statuses (DELIVERED, CANCELED, TONU) show no action button
6. **Error paths:** GPS denied (should still allow transition), transition out of order (should reject), network failure mid-transition

### Flow 4: Check-In Submission
1. Driver taps "Check In" from load view
2. Enters notes (up to 2000 chars), location auto-captured
3. Submits → confirmation shown
4. Location-only share (quick GPS ping without notes)
5. **Edge cases:** empty notes, max-length notes, GPS unavailable

### Flow 5: Document Upload (BOL + POD)
1. BOL upload available after AT_PICKUP status
2. POD upload available at AT_DELIVERY / DELIVERED
3. Driver selects file (JPG/PNG/PDF, max 10MB)
4. Upload progress shown → success confirmation
5. Option to upload additional documents
6. **Error paths:** file too large (>10MB), unsupported file type, S3 presign failure, upload interrupted, camera capture on mobile

### Flow 6: SMS Deep-Link Check-In (Track 3 Integration)
1. Driver receives SMS prompt: "Load #LD-2026-XXXX: please check in. {url}"
2. Taps link → portal opens with load context pre-loaded
3. Driver can check in or advance status from the deep-linked page
4. **Verify:** DISPATCHED anchor SMS fires on dispatch, PRE_PICKUP fires ~1h before appointment, POST_PICKUP escalation fires if overdue, TRANSIT_INTERVAL fires mid-trip, DELIVERED/CANCELED cancels pending prompts

## Data Requirements

No new models. Audit operates against existing schema:
- `TrackingToken` — magic link tokens (type DRIVER, 7-day expiry)
- `SmsPromptSchedule` — SMS prompt records (anchors: DISPATCHED, PRE_PICKUP, POST_PICKUP, TRANSIT_INTERVAL, MANUAL)
- `Document` — upload records (types: BOL_SIGNED, POD)
- `CheckCall` — check-in records (notes, lat/lng, timestamp)
- `Load` + `Stop` — load details and stop info

## API/Interface Changes

No new endpoints. Audit exercises existing driver portal routes:

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/api/v1/driver-portal/portal/load` | Load summary |
| POST | `/api/v1/driver-portal/portal/load/status` | Advance status |
| POST | `/api/v1/driver-portal/portal/load/check-in` | Submit check-in |
| POST | `/api/v1/driver-portal/portal/load/documents/presign` | Get presigned upload URL |
| POST | `/api/v1/driver-portal/portal/load/documents/:id/confirm` | Confirm upload |
| POST | `/api/v1/driver-portal/loads/:loadId/send-driver-link` | Dispatcher sends SMS link |

Fixes may modify controllers, services, or frontend components but will not add new endpoints.

## Technical Context

### Existing Code to Reuse
- `authenticateDriverToken` middleware (`dispatch-api`) — already tested (8 tests), token validation logic
- `DriverPortalPage` (`dispatch-ui`) — main page component (~530 lines), handles all flows
- `DriverDocumentUpload` (`dispatch-ui`) — S3 presigned upload with progress tracking
- `DriverLocationButton` (`dispatch-ui`) — GPS capture component
- `driverPortalApi.ts` (`dispatch-ui`) — API client with token-in-query-param pattern
- `smsPromptSchedulerSubscriber` (`dispatch-api`) — seeds prompts on status change, cancels on terminal status
- `smsPromptWorker` (`dispatch-api`) — processes due prompts, sends SMS via Twilio port
- MSW mock handlers — existing dev mocks for driver portal API

### Key Decisions
- **Bug-hunt + fix only** — no backfilling unit/integration tests for working code. Only write tests as Playwright specs.
- **Reusable Playwright specs** — these become part of V.E2E.1, not throwaway scripts. Follow project Playwright conventions.
- **Mobile + desktop viewports** — test at 375px (iPhone SE) and 1280px (laptop). Drivers use phones in production.
- **Flow-based tasks** — each user flow is a self-contained task that writes the spec, runs it, and fixes bugs found. More parallelizable than audit-first-then-fix.
- **Screenshots at assertions** — every critical assertion captures a screenshot for V.E2E.2 evidence.

### Known Issues (from prior tracks)
- `s3Url` not yet renamed to `url` on Document model (Track 5 pending item) — audit should note but not fix (Track 5 scope)
- Pre-existing `ContextualAlert` bug: says "POD uploaded, all docs present" unconditionally on DELIVERED even when docs missing (Track 2 follow-up) — fix if encountered in driver portal context
- `invoiceReadiness` field update logic may be incomplete — note but don't fix (Track 8 scope)

## Acceptance Criteria

### Flow 1: Token Authentication
- [ ] Valid token loads portal with driver name greeting and load summary
- [ ] Expired token (>7 days) shows clear "link expired" message with instructions to contact dispatcher
- [ ] Revoked token shows appropriate error
- [ ] Invalid/malformed token returns 401, portal shows friendly error
- [ ] Missing token in URL shows friendly error (not blank page or crash)
- [ ] All above work at 375px and 1280px viewports

### Flow 2: Load Summary View
- [ ] Load number, status badge, equipment type, commodity, weight all render correctly
- [ ] Pickup stop shows facility, address, contact, appointment time and type
- [ ] Delivery stop shows same fields
- [ ] Driver instructions section appears when present, hidden when absent
- [ ] Multiple appointment types render correctly (APPOINTMENT, FCFS, NOTIFICATION, OPEN, DROP_HOOK)
- [ ] All above work at 375px and 1280px viewports

### Flow 3: Status Transitions
- [ ] Each transition (DISPATCHED through DELIVERED) succeeds with correct button label
- [ ] GPS coordinates captured and sent with each transition (when permission granted)
- [ ] Transition works when GPS permission denied (graceful degradation)
- [ ] Terminal statuses show no action button
- [ ] Out-of-order transition attempt shows error (not crash)
- [ ] Network failure during transition shows retry-able error
- [ ] All above work at 375px and 1280px viewports

### Flow 4: Check-In
- [ ] Check-in with notes + auto-location submits successfully
- [ ] Location-only quick share works
- [ ] Empty notes submission handled (either allowed or blocked with clear message)
- [ ] 2000-char notes accepted without truncation
- [ ] GPS unavailable doesn't block check-in
- [ ] Success confirmation shown after submit
- [ ] All above work at 375px and 1280px viewports

### Flow 5: Document Upload
- [ ] BOL upload available only after AT_PICKUP
- [ ] POD upload available only at AT_DELIVERY or DELIVERED
- [ ] JPEG, PNG, PDF files upload successfully with progress indicator
- [ ] File >10MB rejected with clear message before upload attempt
- [ ] Unsupported file type rejected with clear message
- [ ] Upload success shows confirmation with option to upload more
- [ ] Camera capture works on mobile (375px viewport)
- [ ] All above work at 375px and 1280px viewports

### Flow 6: SMS Deep-Link
- [ ] SMS-prompted portal link opens correct load with context
- [ ] Driver can check in from deep-linked page
- [ ] Driver can advance status from deep-linked page
- [ ] Token in SMS link is valid and authenticates correctly

### Cross-Cutting
- [ ] No console errors during any flow at either viewport
- [ ] No layout overflow or horizontal scroll at 375px
- [ ] Loading states shown during API calls (no blank flashes)
- [ ] All Playwright specs pass on second verification run with zero failures
