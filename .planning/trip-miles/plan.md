# Trip Miles vs Total Miles — RPM Split & Consistency Fix

> Generated by /prd-refine on 2026-04-06

## Problem

Miles are used inconsistently across the codebase. The backend `ratePerMile` divides `customerRate / loadedMiles`, but the frontend DriverEconomics divides `carrierPayout / totalMiles` — producing different RPM numbers for the same load when deadhead exists. There is no validation that `loadedMiles + deadheadMiles = totalMiles`, no UI for entering loaded or deadhead miles separately, and no automatic deadhead calculation when a driver is assigned. The existing `totalMiles` field (populated from the route API) actually represents trip miles (loaded miles), but is mislabeled and misused in financial calculations.

## Solution Overview

Introduce a clear **trip miles** (loaded) vs **total miles** (loaded + deadhead) distinction. Remap the route API result to populate `loadedMiles` (trip miles) as the primary field. Auto-calculate `deadheadMiles` when a driver is selected using route distance from the driver's location to the first pickup. Make `totalMiles` a computed read-only field (`loadedMiles + deadheadMiles`). Add a dual RPM display (trip RPM and total RPM) where appropriate, scoped by audience.

### Definitions

- **Trip Miles** = `loadedMiles` — miles driven with cargo (pickup → delivery route)
- **Deadhead Miles** = `deadheadMiles` — empty miles (driver location → first pickup)
- **Total Miles** = `loadedMiles + deadheadMiles` — always computed, never manually entered
- **Trip RPM** = `customerRate / loadedMiles` — revenue efficiency per cargo mile
- **Total RPM** = `customerRate / totalMiles` — true cost picture including deadhead

## Capabilities

### Must Have (P0)

- Route API result populates `loadedMiles` (trip miles) instead of `totalMiles`
- `totalMiles` is always computed as `loadedMiles + deadheadMiles`, read-only in the form
- CreateLoadForm displays **Trip Miles** as the primary visible miles field
- When deadhead miles are known, show **Total Miles** as a secondary read-only field
- Auto-calculate deadhead miles via route distance API when a driver with location is selected
- Backend financial calculations produce both `ratePerMile` (trip RPM) and `ratePerTotalMile` (total RPM)
- Enforce `totalMiles = loadedMiles + deadheadMiles` on the API (server-side computation, not client trust)
- Add `currentLatitude`/`currentLongitude` fields to Driver model for precise location tracking
- Geocode `currentCity`/`currentState` as fallback when driver has no lat/lng

### Nice to Have (P1)

- Settlement metrics show both trip RPM and total RPM for internal views
- DriverEconomics section shows "Rate/Trip Mile" alongside "Rate/Total Mile" when deadhead > 0
- Dashboard/reporting queries expose both mile types

## User Flows

### Create Load — Miles Population

1. Dispatcher enters stops (pickup, delivery, etc.) with addresses
2. Route API fires, returns route distance → populates **Trip Miles** (`loadedMiles`) form field in LoadDetailsSection
3. Trip Miles is the **only** miles form field (editable, with "Auto-calculated from route" helper text)
4. Summary bar header shows Trip Miles in the Route KPI group
5. Dispatcher selects a carrier → then selects a driver
6. If driver has location (lat/lng or city/state):
   - System geocodes city/state if no lat/lng available
   - Calls route distance API from driver location → first pickup stop
   - **Deadhead + Total Miles appear in the summary bar header only** (not as form fields)
   - Route KPI group expands: `+112 DH (959 tot)` line + `Tot RPM $3.34/mi`
7. If driver has no location data: no deadhead row in header, trip miles only
8. DriverEconomics section updates with both RPM values when deadhead is known

### Create Load — Manual Override

1. Dispatcher can manually edit Trip Miles in the form field (overrides route API value)
2. Deadhead and total miles are **not editable** — they are computed display values in the header only
3. Total Miles always recomputes: `tripMiles + deadheadMiles` (header display + server-side)

### Financial Calculation Flow

1. Load is saved with `loadedMiles`, `deadheadMiles`, and computed `totalMiles`
2. Backend `calculateLoadFinancials` produces:
   - `ratePerMile` = `customerRate / loadedMiles` (trip RPM)
   - `ratePerTotalMile` = `customerRate / totalMiles` (total RPM, only when totalMiles > loadedMiles)
3. API response includes both values
4. UI displays appropriate RPM based on audience context

## Data Requirements

### Driver Model (schema change)

- Add `currentLatitude Decimal(9,6)?` — driver's current latitude
- Add `currentLongitude Decimal(9,6)?` — driver's current longitude
- Existing `currentCity String?` and `currentState String?` remain as fallback

### Load Model (no schema change needed)

- `loadedMiles Int?` — already exists, will now be actively populated
- `deadheadMiles Int?` — already exists, will now be auto-calculated
- `totalMiles Int?` — already exists, becomes server-computed only
- `ratePerMile Decimal(6,2)?` — already exists (trip RPM)
- Add `ratePerTotalMile Decimal(6,2)?` — new field for total RPM

### Settlement Model

- Add `totalTripMiles Int` — sum of `loadedMiles` across settlement loads (for trip RPM metrics)

## API/Interface Changes

### Modified Endpoints

- `POST /loads` / `PATCH /loads/:id` — server computes `totalMiles` from `loadedMiles + deadheadMiles`; client-submitted `totalMiles` is ignored
- `GET /loads/:id` — response includes both `ratePerMile` and `ratePerTotalMile`
- Load list endpoints — include both RPM fields in response

### New Endpoint

- `GET /drivers/:id/deadhead-to?lat=X&lng=Y` — returns deadhead miles from driver's current location to a given coordinate. Uses driver lat/lng if available, falls back to geocoding city/state. Returns `{ deadheadMiles: number, isEstimated: boolean, source: 'coordinates' | 'geocoded' }`

### Frontend Components

- `LoadDetailsSection` — rename "Total Miles (auto from route)" field to "Trip Miles", maps to `loadedMiles`. Single editable miles field; deadhead/total are NOT form fields
- `CreateLoadPage` summary bar — restructure 7 flat KPIs into 3 grouped clusters (Revenue | Route | Carrier). Route group progressively shows deadhead + total miles when driver has location. See `designs/summary-bar.md`
- `DriverEconomicsSection` — label RPM correctly: `/tot mi` and `/trip mi` suffixes when deadhead > 0. See `designs/driver-economics-section.md`
- New hook: `useDeadheadDistance` — calls deadhead API when driver is selected and first stop has coordinates
- `FinancialSummary` type updated: `totalMiles` renamed to `tripMiles`, add `deadheadMiles`, `totalMiles` (computed), `ratePerTotalMile`

## Technical Context

### Existing Code to Reuse

- `calculateRouteDistance` (`dispatch-ui/src/utils/api/places/placeApi.ts`) — already accepts waypoints array, can be called with 2 points for deadhead
- `useRouteDistance` hook (`dispatch-ui/src/features/load/components/CreateLoadForm/sections/StopsSection/useRouteDistance.ts`) — pattern to follow for the new `useDeadheadDistance` hook
- `deadheadFeasibility.ts` (`dispatch-api/src/shared/utils/`) — haversine + road factor logic, can be used as estimation fallback
- `calculateLoadFinancials` (`dispatch-api/src/shared/financials.ts`) — add `ratePerTotalMile` alongside existing `ratePerMile`
- `geocodeAddress` or places API — for converting city/state to coordinates (check existing places service)

### Key Decisions

- **Route API result = trip miles (loadedMiles)**, not totalMiles. This is the correct semantic mapping since the route is pickup → delivery.
- **totalMiles is server-computed, never client-submitted.** The API ignores any client-sent `totalMiles` and always computes `loadedMiles + deadheadMiles`.
- **Geocode as fallback, lat/lng as primary.** Add lat/lng to Driver model for future accuracy; geocode city/state immediately so the feature works with existing data.
- **Deadhead endpoint is separate** from the route distance endpoint — it encapsulates the driver location lookup + geocode fallback logic on the server side.
- **Owner Operators see Total RPM as primary** (they care about all-in cost). Internal users see both. Company drivers see earnings, not RPM.
