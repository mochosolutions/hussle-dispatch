# Financial Pipeline (Tracks 8+9)

> Generated by /prd-refine on 2026-04-24
> Consolidates MVP plan Tracks 8 (Invoice) + 9 (Settlement) from `docs/tasks/mvp-plan.md`

## Problem

The dispatch loop ends with money: customer billed, carrier paid, driver paid. Today's pipeline has gaps that block the MVP demo:

- Dispatch fee is percentage-only; some deals are flat-fee.
- EXTERNAL_CARRIER dispatch fees are computed but never invoiced to the carrier as an A/R document.
- Driver pay types exist on the Driver model but don't flow through settlement generation.
- Settlement PDF is generated server-side but has no UI download affordance.
- Customer accessorials inflate revenue but the dispatch-fee base still reads from `customerRate` alone on most paths.

## Solution Overview

Extend the existing invoice + settlement modules so the full dispatch → money loop runs end-to-end for all three carrier types with a configurable dispatch fee (percentage or flat) and driver pay types flowing through settlement line items.

**Dispatcher commission (employee-earns-cut-of-fee) is out of MVP scope.** The Load schema fields `dispatcherUserId` and `dispatcherComm` remain in place but unused until a post-MVP payroll track tackles it properly. Persona is solo operator — owner is the dispatcher — so commission is 100% to self and doesn't need tracking yet.

## Dispatch fee semantics

Dispatch fee is **required on every carrier** (must have a value; 0 is allowed for COMPANY_ASSET/LEASED but not EXTERNAL). Behavior by carrier type:

| Carrier type | Fee minimum | Customer invoice | Fee invoice to carrier | Settlement deduction | Notes |
|---|---|---|---|---|---|
| EXTERNAL_CARRIER | > 0 (blocked if 0) | Yes | Yes — AR-style, emailed, mark-paid | Yes, on carrier settlement | Fee reduces carrier net |
| LEASED_CARRIER | ≥ 0 | Yes | No | Yes when fee > 0, on carrier settlement | Internal money flow; no self-invoice |
| COMPANY_ASSET | ≥ 0 | Yes | No | **No** — never on driver settlement | Fee tracked on Load as company-side expense (future dispatcher payroll). Driver net untouched. |

**Key rule:** the dispatch fee never reduces driver net. On COMPANY_ASSET the fee is a company-side number (think: future payable to a dispatcher/employee) with no MVP settlement line and no invoice.

## Capabilities

### Must Have (P0)

1. Dispatch fee configuration on Carrier supports type (PERCENTAGE | FLAT) + amount, with per-load override. Required on every carrier (not nullable). EXTERNAL_CARRIER blocked at API + UI when resolved fee = 0.
2. `feeIncludesAccessorials` defaults to `true` for new carriers. When true, dispatch fee base = `customerRate + sum(customer-billed accessorials)`.
3. EXTERNAL_CARRIER loads auto-generate a second invoice (type `DISPATCH_FEE`) billed to the carrier on delivery, emailed, and transitionable through DRAFT → SENT → PAID (manual mark-paid, consistent with current A/R).
4. LEASED_CARRIER loads with fee > 0 produce a DISPATCH_FEE settlement line on the carrier settlement. No fee invoice. Fee = 0 produces no line.
5. COMPANY_ASSET loads never generate a fee invoice and never produce a DISPATCH_FEE line on the driver settlement, regardless of the configured fee value. The fee stays tracked on the Load for future reporting/payroll.
6. Default customer notification settings on customer creation enable EMAIL for all triggers (prevents silent no-send).
7. Accessorial line items (preset + custom, billTo CUSTOMER/CARRIER/BOTH) flow correctly: CUSTOMER → customer invoice, CARRIER → carrier settlement deduction, BOTH → both.
8. Invoice detail page shows accessorial breakdown as distinct line items (not folded into a total).
9. Invoice list distinguishes customer invoices from dispatch-fee invoices (type badge or filter).
10. Settlement generation includes a new line-item type `DRIVER_PAY` on `SettlementItemType` (alongside existing `LOAD_REVENUE`, `DISPATCH_FEE`, `ACCESSORIAL`, `ADJUSTMENT`, `EXPENSE`).
11. Driver pay flows through settlement by `payType`: PERCENTAGE uses `carrierPayout`, PER_MILE uses `loadedMiles`, PER_HOUR uses `estimatedHours`, FLAT_RATE uses `payRate` directly.
12. PER_HOUR load missing `estimatedHours` blocks settlement generation with a 400 response listing affected load IDs; UI surfaces the block and links to each load.
13. Settlement PDF download button on `SettlementDetailPage` wired to `GET /settlements/:id/pdf`.
14. Settlement detail view itemizes line items grouped by type: LOAD_REVENUE, DISPATCH_FEE, DRIVER_PAY, ACCESSORIAL (by billTo), ADJUSTMENT, EXPENSE.

### Nice to Have (P1)

- Fee invoice auto-PAID on settlement approval (considered and rejected for MVP; revisit if manual mark-paid becomes noisy).

## User Flows

### F1 — Dispatch → Deliver → Invoice (EXTERNAL_CARRIER)

1. Dispatcher creates load with customer, carrier, customerRate $3,000, and one customer-billed accessorial ($200 detention).
2. Load progresses through dispatch → pickup → delivery.
3. On `load.delivered`, invoice readiness subscriber fires:
   - Customer invoice: $3,200 (rate + accessorial), auto-emailed per customer notification settings.
   - Carrier dispatch-fee invoice: (3,200 × 15%) = $480 (carrier has `dispatchFeeType=PERCENTAGE`, `dispatchFeePercent=15`, `feeIncludesAccessorials=true`). Status DRAFT → SENT, emailed to carrier primary contact.
4. Both invoices appear in invoice list with type badges.

### F2 — Generate carrier settlement (EXTERNAL)

1. Dispatcher opens settlements, selects carrier, picks date range, clicks Generate.
2. Settlement generator builds line items for each completed load:
   - LOAD_REVENUE +$3,000 (customerRate)
   - ACCESSORIAL +$200 (customer accessorial pass-through to carrier per billTo rules)
   - DISPATCH_FEE −$480
3. Net due to carrier = $2,720.
4. Settlement opens in DRAFT; dispatcher can add ADJUSTMENT line items, then approves.

### F3 — Generate driver settlement (COMPANY_ASSET)

1. Driver has `payType=PER_MILE`, `payRate=0.55`.
2. Load loadedMiles=500, customerRate=$3,200.
3. Settlement generator builds:
   - DRIVER_PAY +$275 (500 × 0.55)
   - No DISPATCH_FEE line (company-owned).
4. Generation blocks if any PER_HOUR load in range lacks `estimatedHours` — 400 response with load IDs.

### F4 — Download settlement PDF

1. Dispatcher opens `SettlementDetailPage`.
2. Clicks "Download PDF" → hits existing `GET /settlements/:id/pdf` endpoint → browser downloads.

## Data Requirements

### Carrier (schema additions)

- `dispatchFeeType DispatchFeeType @default(PERCENTAGE)` — new enum `PERCENTAGE | FLAT`. Required.
- `dispatchFeeAmount Decimal @default(0) @db.Decimal(10, 2)` — used when `dispatchFeeType = FLAT`. Required (non-null); 0 is a valid value.
- Existing `dispatchFeePercent` stays required with its current default (used when `dispatchFeeType = PERCENTAGE`).
- API + Yup validator: when carrier `type = EXTERNAL_CARRIER`, the resolved fee (percent or amount depending on type) must be > 0. COMPANY_ASSET and LEASED_CARRIER allow 0.
- Flip `feeIncludesAccessorials` default from `false` to `true`. No backfill for existing carriers (explicit out-of-scope).

### Load (schema additions)

- `dispatchFeeOverrideType DispatchFeeType?` + `dispatchFeeOverrideAmount Decimal?` for per-load overrides (nullable → inherit carrier).
- Existing `dispatcherUserId` and `dispatcherComm` stay in schema, **unused** in MVP. No new fields for commission. No new UI.

### Customer / CustomerNotificationSettings

- No schema change. On customer create, default settings row inserted with EMAIL enabled for all triggers (current code gap).

### Enums

- New enum `DispatchFeeType { PERCENTAGE, FLAT }`.
- Extend `SettlementItemType` with `DRIVER_PAY`. (`DISPATCH_FEE`, `ACCESSORIAL`, `ADJUSTMENT`, `EXPENSE`, `LOAD_REVENUE` already present.)

## API / Interface Changes

### API

- `POST /carriers` / `PATCH /carriers/:id` — accept `dispatchFeeType`, `dispatchFeeAmount` (in addition to existing `dispatchFeePercent`, `feeIncludesAccessorials`).
- `POST /loads` / `PATCH /loads/:id` — accept `dispatchFeeOverrideType`, `dispatchFeeOverrideAmount`.
- `POST /settlements` (generate) — returns 400 with `{ code: 'MISSING_ESTIMATED_HOURS', loadIds: [...] }` when PER_HOUR loads lack hours.
- `invoiceReadinessSubscriber` — on `load.delivered` for EXTERNAL_CARRIER only, create second invoice with `type=DISPATCH_FEE`, carrier as billTo, amount = resolved fee; kick off email.

### UI

- `CarrierFormDrawer` — fee type selector (Percentage / Flat) + amount input (conditional on type).
- Load form — per-load fee override (optional; collapsed section).
- `InvoiceDetailPage` — accessorial breakdown section.
- `InvoiceListPage` — type badge + type filter.
- `SettlementDetailPage` — "Download PDF" button + itemized line items grouped by type.

## Technical Context

### Existing code to reuse

- `invoices/services/invoiceReadinessSubscriber.ts` — already the sole invoice creator for `load.delivered`/`load.tonu`. Extend for second (fee) invoice when carrier type = EXTERNAL_CARRIER.
- `invoices/services/invoiceGenerationService.ts` + `invoiceBuilderService.ts` — already route LEASED to CUSTOMER, EXTERNAL to split (per 1.BE.2 fix). Verify no regression.
- `invoices/services/invoiceEmailService.ts` — reuse for carrier fee invoice; new recipient resolver reads carrier primary contact.
- `settlements/services/settlementService.generate` — already uses Decimal accumulation. Extend with DRIVER_PAY computation.
- `settlements/services/settlementPdfGenerationService.ts` + `settlementPdfDataBuilder.ts` — already render line items; update to group by type.
- `AccessorialCharge.billTo` — enum values are uppercase per Track 2 follow-up flag; existing `customer` default lowercase is a known drift. Include a data-normalization step in migration.
- `CustomerNotificationSettings` — insert default row in customer create service.

### Key decisions (from /prd-refine conversation)

- **Fee invoice lifecycle = AR-style** (emailed, mark-paid). Rejected "internal tracking only" and "deducted-from-settlement-only" to give the dispatcher a real A/R record they can chase.
- **LEASED ≠ EXTERNAL for fee invoicing.** LEASED carriers get their fee as a settlement deduction only, no second invoice. LEASED money flows through the dispatch org, so invoicing themselves is noise.
- **Dispatch fee is required on every carrier, but can be 0 for COMPANY_ASSET/LEASED.** EXTERNAL must be > 0 (validated at API + UI) — no free dispatch.
- **COMPANY_ASSET fee never touches driver settlement.** If set > 0, it's a company-side expense number tracked on the Load for future reporting and eventual dispatcher payroll. Driver net is unaffected. No fee invoice (self-invoicing is noise).
- **Schema: add type + amount, keep percent.** Non-breaking. Reads branch on `dispatchFeeType`. Avoids data migration churn.
- **`feeIncludesAccessorials` default flips to true.** New-carrier default aligns with the intent: accessorials are revenue and the dispatch fee should apply to revenue. Existing carriers retain their current value (no backfill).
- **PER_HOUR missing hours = block generation.** Chosen over "warn and use 0" to force the dispatcher to fix the data; prevents silent under-pay.
- **Accessorials always billable all three ways.** `billTo` kept as CUSTOMER / CARRIER / BOTH (not simplified) for pass-through scenarios.
- **Customer accessorials inflate dispatch-fee base.** When `feeIncludesAccessorials=true`, fee base = customerRate + sum(accessorials with billTo ∈ {CUSTOMER, BOTH}).
- **Dispatcher commission dropped from MVP.** Solo-operator persona = owner is the dispatcher, so a commission split is a no-op. Fields remain in schema for post-MVP payroll track. No defaults, no drawer, no settlement line items, no UI.

## Acceptance Criteria

All criteria must be testable (unit + integration + Playwright where appropriate).

1. Creating a carrier with `dispatchFeeType=PERCENTAGE, dispatchFeePercent=15` and a load with customerRate=$3,000 + $200 customer accessorial produces a carrier fee invoice of $480.
2. Creating a carrier with `dispatchFeeType=FLAT, dispatchFeeAmount=300` produces a carrier fee invoice of $300 regardless of customerRate.
3. Per-load `dispatchFeeOverrideType`/`dispatchFeeOverrideAmount` supersede carrier config for that load's fee invoice and settlement.
4. `feeIncludesAccessorials=false` on a carrier excludes accessorials from the fee base.
5. New carrier created without explicit value receives `feeIncludesAccessorials=true`.
6. EXTERNAL_CARRIER load delivery generates exactly two invoices: one CUSTOMER and one DISPATCH_FEE. Both are emailed. LEASED_CARRIER and COMPANY_ASSET deliveries generate exactly one CUSTOMER invoice.
7. COMPANY_ASSET driver settlement contains **no** DISPATCH_FEE line item under any configuration (even when the carrier has a non-zero fee configured).
7a. EXTERNAL_CARRIER create/update with resolved fee = 0 is rejected with 400 at API + blocked by form validation in UI.
7b. LEASED_CARRIER with fee = 0 generates a carrier settlement with no DISPATCH_FEE line. LEASED with fee > 0 produces a DISPATCH_FEE deduction line.
8. Customer accessorials (billTo=CUSTOMER or BOTH) appear on customer invoice; carrier-billed accessorials (billTo=CARRIER or BOTH) appear as carrier settlement deduction line items.
9. Invoice list UI shows distinct badges for CUSTOMER vs DISPATCH_FEE invoices and supports filtering by type.
10. Invoice detail renders each accessorial as a separate line item with type label and amount.
11. Settlement generation for a COMPANY_ASSET driver produces DRIVER_PAY line items matching payType: PERCENTAGE (against carrierPayout), PER_MILE (loadedMiles × payRate), PER_HOUR (estimatedHours × payRate), FLAT_RATE (payRate).
12. Settlement generation returns 400 with `{ code: 'MISSING_ESTIMATED_HOURS', loadIds: [...] }` when any PER_HOUR load in range lacks estimatedHours; no partial settlement is created.
13. Carrier settlement for EXTERNAL_CARRIER includes DISPATCH_FEE as a deduction; carrier's net payout = LOAD_REVENUE + passthrough ACCESSORIAL − DISPATCH_FEE − other deductions.
14. Settlement Decimal math matches existing pattern: accumulate raw Decimals, round once for line-item storage, compute net from raw values.
15. `SettlementDetailPage` renders a "Download PDF" button that returns a 200 PDF from `GET /settlements/:id/pdf`.
16. Customer created via API has a `CustomerNotificationSettings` row with EMAIL enabled for STATUS_CHANGE, CHECK_CALL, DOCUMENT_UPLOADED triggers.
17. Idempotency: invoking the invoice-readiness subscriber twice for the same `load.delivered` event does not create duplicate invoices (existing behavior preserved for both CUSTOMER and DISPATCH_FEE types).
18. Dispatch-fee invoice transitions DRAFT → SENT → PAID via existing invoice status endpoints.
19. Dispatcher commission is NOT computed, stored, or displayed anywhere in the settlement pipeline (MVP exclusion verified — no DISPATCHER_COMMISSION enum value added, no UI affordance present).
20. Playwright: full pipeline test passes:
    - EXTERNAL_CARRIER: both invoices generated + emailed, settlement has DISPATCH_FEE deduction, PDF downloads.
    - COMPANY_ASSET: one customer invoice, settlement has DRIVER_PAY only (all 4 pay types covered in separate scenarios), no DISPATCH_FEE.
    - LEASED_CARRIER: one customer invoice, settlement has DISPATCH_FEE deduction (when configured), no second invoice.
    - Flat vs percentage dispatch fee: both calculate correctly on invoice and settlement.
