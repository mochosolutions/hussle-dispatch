# API / Worker Role Split

> Generated by /prd-refine on 2026-05-29

## Problem

All background work — 12 event-bus subscriber groups and 4 cron jobs — currently runs **inside the HTTP process**. Worse, subscriber/cron startup is **entangled with module import**: `src/app.ts` imports each feature router (e.g. `import { loadsRouter } from './loads'`), which loads that module's `index.ts`, which calls `initializeSubscriber()` at module top-level. So merely mounting routes boots every consumer and cron.

Consequences:
- **Crons double-fire** the moment the API scales past one replica (settlement generation, watchdog, cleanups are not leader-elected).
- **HTTP replicas carry the wrong profile** — every API box loads Chromium/PDF + all consumers, so you can't scale HTTP on traffic without multiplying background work.
- **No isolation** — a misbehaving subscriber shares the event loop with request handling.

This is the keystone refactor for the deployment architecture (`docs/architecture/deployment-architecture.md`, Phase 0): it unblocks independent scaling, leader-elected crons, and workload isolation.

## Solution Overview

Run the **same image** in one of three modes selected by a `ROLE` env var:

- **`ROLE=api`** — mounts HTTP routers and `listen`s. Connects the event bus as a **publisher only**. Registers **no** subscribers, starts **no** crons.
- **`ROLE=worker`** — starts all subscribers + all crons, runs a **minimal `/health` HTTP server** (for Swarm/Dokploy healthchecks), no app routers. Connects the bus as consumer + publisher.
- **`ROLE=all`** (default) — today's behavior exactly: everything in one process. Preserves local dev and the current single-container Dokploy deploy until the split is flipped on.

The enabling change is **decoupling subscriber/cron startup from module import**: module `index.ts` files stop self-starting at import; a new `src/startBackground.ts` aggregator starts them explicitly, called only by the worker/all paths.

This phase also includes the **deploy wiring**: separate `api` and `worker` services from the same image in `docker-compose-prod.yml` + Dokploy, with `worker` desired-count = 1.

## Capabilities

### Must Have (P0)
- `ROLE` env var (`api` | `worker` | `all`, default `all`) gating which work the process runs.
- Subscriber/cron init removed from all import-time side effects; started explicitly via `src/startBackground.ts`.
- New `src/worker.ts` entrypoint: boot redis + bus, start subscribers + crons, `/health` server, graceful shutdown of all crons + `stopAgreements()` + `eventBus.close()` + `redisClient.quit()`.
- `ROLE=api` registers zero consumers and starts zero crons (verifiable).
- `ROLE=worker` runs all 12 subscriber groups + all 4 crons.
- Event-bus instance reconciled so `api` publishes and `worker` consumes on the same broker/topology (end-to-end event flow proven).
- dependency-cruiser rule: the api entrypoint / `app.ts` may not import `startBackground` (or any subscriber/cron aggregator).
- `docker-compose-prod.yml` + Dokploy define separate `api` and `worker` services from one image; `worker` count = 1.

### Nice to Have (P1)
- Structured boot log line per role naming the started subscribers/crons (aids the verification check).
- `ROLE=all` emits a warning in production env (nudges toward the split) — non-blocking.

## User Flows

### Boot — `ROLE=api`
1. Process starts, reads `ROLE=api`.
2. Connects Redis + constructs the publisher event bus.
3. `createApp(...)` mounts routers + `/health`; **no** subscriber/cron init runs.
4. `app.listen(PORT)`.

### Boot — `ROLE=worker`
1. Process starts, reads `ROLE=worker`.
2. Connects Redis + event bus (consumer + publisher).
3. `startBackground(deps)` → `startSubscribers()` (12 groups) + `startCrons()` (4 jobs); returns handles.
4. Starts a minimal `/health` express server (db + redis + bus readiness).
5. Registers SIGTERM/SIGINT → stop crons, `stopAgreements()`, `eventBus.close()`, `redisClient.quit()`.

### Boot — `ROLE=all` (default)
1. Does the api flow **and** the worker background flow in one process — byte-for-byte today's behavior.

### Event round-trip (verification)
1. An `api`-role process publishes a domain event (e.g. via a controller action).
2. RabbitMQ routes it to the durable queue.
3. A `worker`-role process consumes it and runs the handler. (Proves the bus reconciliation.)

## Technical Context

### Existing Code to Reuse
- `src/index.ts` (`dispatch-api`) — existing boot/shutdown entrypoint; the analog for `src/worker.ts` and the role dispatcher.
- `src/app.ts` `/health` route — analog for the worker's minimal health server.
- The composition-root pattern — each module already separates `controllers` from `initializeSubscriber`; the fix only moves *when* init is called (explicit, not import-time), not how it's wired.
- `src/shared/messaging/processedEventCleanup.ts` + `settlements/services/settlementCronJob.ts` — existing `node-cron` `start()/stop()` shape reused for the aggregator's shutdown handles.
- `src/carriers/services/__tests__/carrierSubscriber.test.ts` — analog for the role-bootstrap test.

### Key Decisions
- **Three roles incl. `ROLE=all` default** — preserves current behavior; the split is opt-in per environment, so zero dev/cutover regression risk.
- **Decouple init from import** — the only correct fix; gating a function call isn't enough while importing a router transitively calls `initializeSubscriber()`. Confirmed mechanism: `app.ts` router imports (`./loads`, `./drivers`, `./settlements`, `./agreements`, …) execute each module `index.ts`'s top-level init; plus explicit side-effect imports `./audit`, `./notifications`, `@/shared/fmcsa`.
- **Reconcile the event-bus instance** — today `index.ts` constructs a bus passed to `createApp` (controllers publish) while subscribers use the `sharedEventBus` singleton (`settlements/index.ts:56`). The split must make this explicit: `api` constructs/uses a publisher bus, `worker` uses the consuming bus, both pointed at the same broker/topology. Resolve to a single construction path per role.
- **4 crons, not 3** — `invitationCleanupJob` (auth) is now live alongside `processedEventCleanup`, `settlementCronJob`, `signedAgreementWatchdog`. All move to the worker/all path.
- **Leader-election is out of scope** — crons run on a single `worker` (count = 1) for now; multi-worker cron safety is a later phase.
- **dependency-cruiser guard** — makes "api accidentally imports a consumer" a CI failure, protecting the decoupling permanently.

## Acceptance Criteria

- With `ROLE=api`: process serves HTTP and `/health`; broker shows **no** consumers bound by this process; **no** cron timers scheduled (assert via logs/broker inspection / a test seam).
- With `ROLE=worker`: all **12** subscriber groups are consuming and all **4** crons are scheduled; `/health` returns ready (db+redis+bus); **no** app routes served.
- With `ROLE=all`: behavior is identical to the pre-change process (subscribers + crons + HTTP).
- An event published by an `api`-role process is consumed by a `worker`-role process end-to-end (bus reconciliation proven).
- No subscriber or cron initializes as a side effect of importing any module (verified: importing a router does not register a consumer).
- `npm run validate` passes in `dispatch-api`, including the new dependency-cruiser rule forbidding the api entrypoint from importing the background aggregator.
- `docker-compose-prod.yml` brings up distinct `api` and `worker` services from the same image; `worker` runs background work, `api` does not; `worker` healthcheck passes.
- Graceful shutdown on SIGTERM/SIGINT stops all 4 crons and closes the bus + redis in both `worker` and `all` modes.

## Out of Scope

- Leader-election / running more than one `worker` replica safely (later phase).
- Moving crons to EventBridge Scheduler or any cloud scheduler.
- Moving the SMS delay timing off the RabbitMQ delayed-message plugin (separate Phase 1).
- Any change to subscriber/handler business logic or to the HTTP API contract.
- Managed Postgres, multi-node Swarm, WebSocket gateway, telemetry plane (separate phases).
