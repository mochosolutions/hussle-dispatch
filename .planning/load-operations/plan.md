# Load Operations: Scheduling Enforcement, Dispatch Gates & Detention

> Generated by /prd-refine on 2026-04-12

## Problem

Dispatchers create loads with scheduling details (appointment times, notification windows) but there is no enforcement that the right fields are populated for each scheduling type. Drivers get dispatched to APPOINTMENT facilities without appointment numbers and get turned away. Detention charges — the #1 accessorial in the industry — are tracked manually and frequently missed, resulting in lost revenue. The system has the data model to support all of this (Stop scheduling fields, OrgSettings with detention config, AccessorialCharge with approval workflow) but the business logic connecting them doesn't exist.

## Solution Overview

Four capabilities, delivered in priority order:

1. **Scheduling type field enforcement at create/update time** — hard validation ensuring stops have the required fields for their scheduling type
2. **Dispatch gate validation** — warn-with-override when transitioning to DISPATCHED if APPOINTMENT stops are missing appointmentNumber
3. **Detention auto-detection** — automatically create PENDING detention accessorial charges when driver wait time exceeds org free hours, triggered by stop departure and status transitions
4. **Notification field enforcement** — require notificationHours on NOTIFICATION-type stops (automation deferred to future work)

## Capabilities

### Must Have (P0)

- Stops with `schedulingType: APPOINTMENT` require `appointmentStart` at create/update time
- Stops with `schedulingType: NOTIFICATION` require `notificationHours` at create/update time
- Stops with `schedulingType: FCFS` require `targetDate` at create/update time
- Stops with `schedulingType: OPEN` and `DROP_HOOK` have no additional field requirements
- Transitioning to DISPATCHED warns (with override) when any APPOINTMENT stop is missing `appointmentNumber`
- When a stop's `departureTime` is recorded and `arrivalTime` exists, calculate wait time against org `detentionFreeHours`; if exceeded, auto-create a DETENTION accessorial with `approvalStatus: PENDING`, `isAutoGenerated: true`, amount = ceil(excess hours) x `defaultDetentionRate`
- DROP_HOOK stops are exempt from detention calculation
- On status transitions (AT_PICKUP -> IN_TRANSIT, AT_DELIVERY -> DELIVERED), run detention check as a safety net for stops that may have had departure times set out of order
- Notify the dispatcher when an auto-generated detention charge is created

### Nice to Have (P1)

- ETA-based auto-notification for NOTIFICATION-type stops (when check-call ETA falls within `notificationHours` window, auto-notify facility)
- Detention calculation differentiated by scheduling type (APPOINTMENT uses window end instead of arrival)

## User Flows

### Scheduling Type Enforcement (Create/Update)

1. Dispatcher creates or updates a load with stops
2. `validateStops()` checks each stop's `schedulingType` against required fields:
   - APPOINTMENT: `appointmentStart` required
   - NOTIFICATION: `notificationHours` required
   - FCFS: `targetDate` required
   - OPEN: no requirements
   - DROP_HOOK: no requirements
3. If required fields are missing, return 400 with specific error message identifying the stop and missing field
4. Validation runs on both `createLoad` and `updateLoad` when stops are provided

### Dispatch Gate (Status Transition)

1. Dispatcher transitions load to DISPATCHED via `PATCH /:id/status`
2. System checks all APPOINTMENT-type stops on the load
3. If any APPOINTMENT stop is missing `appointmentNumber`:
   - Return 422 with warning: `"Stop {sequence}: APPOINTMENT stop is missing appointment number"`
   - Dispatcher can retry with `overrideWarnings: true` to proceed anyway
4. If all APPOINTMENT stops have `appointmentNumber`, transition proceeds normally

### Detention Auto-Detection

1. **Primary trigger:** Stop update sets `departureTime` (driver departs a stop)
   - System checks if `arrivalTime` is also set on the stop
   - If stop type is DROP_HOOK, skip detention check
   - Calculate wait hours: `(departureTime - arrivalTime) / 3600000`
   - Fetch org's `detentionFreeHours` (default: 2)
   - If wait hours > free hours:
     - Compute billable hours: `ceil(waitHours - freeHours)`
     - Fetch org's `defaultDetentionRate`
     - Create AccessorialCharge: `{ type: DETENTION, amount: billableHours * rate, billTo: 'customer', approvalStatus: PENDING, isAutoGenerated: true, description: 'Auto-detected: {waitHours}hr wait at {facilityName || city, state}' }`
     - Emit domain event `load.detention.detected` for notification dispatch
2. **Safety net trigger:** On status transitions AT_PICKUP -> IN_TRANSIT and AT_DELIVERY -> DELIVERED:
   - For each stop matching the transition (PICKUP stops for AT_PICKUP, DELIVERY stops for AT_DELIVERY), run the same detention check
   - Skip if a DETENTION accessorial already exists with `isAutoGenerated: true` for this stop (prevent duplicates)

### Detention Notification

1. Domain event `load.detention.detected` is emitted after auto-creation
2. Existing notification subscriber handles the event
3. Dispatcher receives notification: "Detention detected on Load {loadNumber} at {facilityName}: {waitHours}hr wait, {billableHours}hr billed at ${rate}/hr = ${amount}"

## Data Requirements

### No schema changes needed

All required fields already exist:

- **Stop model:** `schedulingType`, `appointmentStart`, `appointmentEnd`, `targetDate`, `notificationHours`, `appointmentNumber`, `arrivalTime`, `departureTime`, `type`
- **AccessorialCharge model:** `type` (DETENTION), `amount`, `billTo`, `approvalStatus` (PENDING), `isAutoGenerated`, `description`
- **OrgSettings model:** `detentionFreeHours` (default: 2), `defaultDetentionRate`
- **NotificationLog model:** existing infrastructure for load-level notifications

### New domain event

- `load.detention.detected` — payload: `{ loadId, organizationId, loadNumber, stopId, stopSequence, facilityName, waitHours, billableHours, rate, amount }`

### New field on AccessorialCharge (optional but recommended)

- `stopId: String?` — FK to Stop, to track which stop generated the detention charge and prevent duplicate auto-creation. Currently no way to link a charge to a specific stop.

## API/Interface Changes

### No new endpoints

All changes are internal business logic within existing endpoints:

- `POST /loads` and `PATCH /loads/:id` — enhanced stop validation in `validateStops()`
- `PATCH /loads/:id/status` — new warning for DISPATCHED transition
- `PATCH /loads/:loadId/stops/:stopId` — detention check when `departureTime` is set

### Modified response shapes

None — warnings already use the existing `StatusTransitionWarning` shape with `{ code, message }`.

## Technical Context

### Existing Code to Reuse

- `validateStops()` in `loadService.ts` — already validates APPOINTMENT requires appointmentStart and NOTIFICATION requires notificationHours. Extend with FCFS -> targetDate.
- `validateTransition()` in `shared/stateMachine.ts` — existing warning system for status transitions. Currently warns about missing signed BOL on DELIVERED. Add appointmentNumber check for DISPATCHED.
- `TRANSITION_SIDE_EFFECTS` map in `shared/stateMachine.ts` — existing side effect engine. Use for detention safety-net check on AT_PICKUP->IN_TRANSIT and AT_DELIVERY->DELIVERED.
- `AccessorialCharge` creation in `loadRepositoryPrisma.ts` — existing create pattern for charges.
- `OrgSettings` query via `settingsRepoPort` — already has `detentionFreeHours` and `defaultDetentionRate`.
- Domain event publishing in `loadStatusService.ts` — existing `publishEvent()` pattern for `load.status.changed`, `load.delivered`, etc.
- `NotificationLog` + notification subscriber infrastructure — existing pattern for dispatching notifications on domain events.

### Key Decisions

- **Create-time enforcement, not layered** — scheduling type field requirements are hard-validated at create/update. Simpler to understand than soft-at-create/hard-at-dispatch layering.
- **Warn with override at dispatch** — appointmentNumber warning at DISPATCHED transition uses the existing 422 + overrideWarnings pattern, not a hard block. Dispatchers sometimes book before appointment confirmation comes back.
- **Detention always from arrivalTime** — no scheduling type differentiation for detention calculation. Simpler model: wait time = departureTime - arrivalTime, excess = wait time - freeHours. Avoids complexity of APPOINTMENT-window-based calculation.
- **Round up to full hour** — billable detention hours are ceiled to the nearest full hour. Industry-standard conservative billing.
- **DROP_HOOK exempt** — driver doesn't wait at DROP_HOOK stops, no detention applies.
- **Notification automation deferred** — ETA-based auto-notification for NOTIFICATION stops is P1. For now, only enforce that `notificationHours` is a required field on NOTIFICATION stops.
- **stopId on AccessorialCharge** — optional FK to prevent duplicate auto-generated detention for the same stop. Without it, the safety-net trigger on status transitions would need to heuristically match existing charges.

## Acceptance Criteria

### Scheduling Type Enforcement

- Creating a stop with `schedulingType: APPOINTMENT` and no `appointmentStart` returns 400
- Creating a stop with `schedulingType: NOTIFICATION` and no `notificationHours` returns 400
- Creating a stop with `schedulingType: FCFS` and no `targetDate` returns 400
- Creating a stop with `schedulingType: OPEN` and no date fields succeeds
- Creating a stop with `schedulingType: DROP_HOOK` and no date fields succeeds
- Updating stops on an existing load applies the same validation rules
- Error message identifies the specific stop (by sequence) and the missing field

### Dispatch Gate

- Transitioning to DISPATCHED with an APPOINTMENT stop missing `appointmentNumber` returns 422 with a warning
- Retrying the same transition with `overrideWarnings: true` succeeds
- Transitioning to DISPATCHED with all APPOINTMENT stops having `appointmentNumber` succeeds without warnings
- Non-APPOINTMENT stops do not trigger the warning regardless of `appointmentNumber`
- Transitioning to statuses other than DISPATCHED does not check `appointmentNumber`

### Detention Auto-Detection

- Setting `departureTime` on a PICKUP stop where arrivalTime exists and wait time exceeds `detentionFreeHours` creates a DETENTION accessorial with `approvalStatus: PENDING` and `isAutoGenerated: true`
- Same behavior on DELIVERY stops
- DROP_HOOK stops with long wait times do not generate detention charges
- Billable hours are rounded up to the nearest full hour (e.g., 2hr 10min wait with 2hr free time = 1hr billed)
- Amount equals `ceil(excessHours) * defaultDetentionRate`
- Auto-generated charge description includes wait time and facility info
- Status transition AT_PICKUP -> IN_TRANSIT triggers detention check on pickup stops as safety net
- Status transition AT_DELIVERY -> DELIVERED triggers detention check on delivery stops as safety net
- Safety-net trigger does not create duplicate detention charges for the same stop
- Domain event `load.detention.detected` is emitted after auto-creation
- Dispatcher is notified when detention is auto-detected

### Notification Field Enforcement

- Creating a stop with `schedulingType: NOTIFICATION` and no `notificationHours` returns 400
- Creating a stop with `schedulingType: NOTIFICATION` and `notificationHours: 2` succeeds

## Out of Scope

- ETA-based auto-notification for NOTIFICATION stops (P1 — requires check-call ETA integration)
- Scheduling-type-differentiated detention (APPOINTMENT window-based vs arrival-based)
- Detention rate per facility or per customer (currently org-level only)
- Automatic detention billing (charges are always PENDING, require manual approval)
- Sub-hour detention billing increments (15-min or 30-min rounding)
- Driver-facing detention alerts or mobile notifications
- Historical detention reporting or analytics
