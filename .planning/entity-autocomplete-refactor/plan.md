# Unified Entity Autocomplete & Reusable Form Patterns

> Generated by /prd-refine on 2026-03-26

## Problem

The dispatch UI has 4 nearly-identical autocomplete implementations (Carrier, Customer, Contact, Place) each duplicating ~80% of their logic: debounced search, request cancellation, loading state, custom option rendering, and "create new" flows. They use inconsistent Formik integration and drawer-opening patterns.

Detail page drawers duplicate form field logic that already exists in Create Load components. The LoadRouteDrawer has its own bare-bones stop editing (EditableStopCard) instead of reusing the rich StopFormCard from Create Load. Drawer implementations are split between manual EditDrawer+Formik composition and the standardized FormDrawer wrapper.

This creates maintenance burden, inconsistent UX, and makes it harder to add new entity pages.

## Solution Overview

1. Create a shared `EntityAutocomplete` base component that all entity selection fields extend
2. Migrate all 4 autocomplete implementations to use it
3. Standardize all form drawers on `FormDrawer`
4. Rewrite `LoadRouteDrawer` to reuse `StopFormCard` with batch-save
5. Fix form field inconsistencies (raw MUI TextFields → @mocho/ui)

## Capabilities

### Must Have (P0)

- `EntityAutocomplete` base component with debounced search, request cancellation, Formik integration, configurable option rendering, and "Add New" action
- Configurable inline create form that expands within a drawer (for creating entities without opening a second drawer)
- All 4 autocompletes (Carrier, Customer, Contact, Place) migrated to EntityAutocomplete
- All eligible drawers migrated to FormDrawer
- LoadRouteDrawer rewritten to reuse StopFormCard with batch-save pattern
- DriverInfoDrawer and VehicleInfoDrawer use @mocho/ui form-field components

### Nice to Have (P1)

- Add `validateOnChange` / `validateOnBlur` props to FormDrawer for ManualEntryDrawer migration
- Drag-and-drop stop reordering in StopFormCard (currently up/down buttons)

## User Flows

### Entity Selection (autocomplete)
1. User focuses the field
2. Initial options load (debounced API call with optional scope filter)
3. User types → debounced search updates options
4. User selects an option → field value set, optional `onSelect` callback with full entity
5. If no match, user clicks "Add New [Entity]" in dropdown

### Inline Create (inside a drawer)
1. User clicks "Add New Contact" from the typeahead dropdown inside LoadContactDrawer
2. Inline form section expands below the search field (firstName, lastName, email, phone — configurable per entity)
3. User fills fields, clicks "Save"
4. API creates the entity → new entity auto-selects in the typeahead
5. Inline form collapses

### Inline Create (on a page form)
1. User clicks "Add New Contact" from the typeahead dropdown on Create Load page
2. A drawer opens (standard pattern — not inside another drawer)
3. User fills form, saves
4. Drawer closes → new entity auto-selects in the typeahead

### Route Editing (batch save)
1. User clicks Edit on Stops card → LoadRouteDrawer opens
2. Drawer shows all stops using StopFormCard (with address search, commodities, freight receiving)
3. User edits stops, adds/removes/reorders
4. User clicks Save → all changes submitted as a batch
5. Drawer closes

## Data Requirements

No new models. Existing entity types (Contact, Carrier, Customer, Place, Stop) are unchanged. The refactoring is purely UI-layer.

**EntityAutocomplete option shape (standardized):**
```typescript
interface EntityAutocompleteOption {
  value: string;          // entity ID
  label: string;          // display name
  description?: string;   // secondary text (email, location, etc.)
  metadata?: Record<string, unknown>; // entity-specific data for rendering
}
```

## Technical Context

### Existing Code to Reuse

- `TypeaheadField` (`@mocho/ui/components`) — EntityAutocomplete builds on top of this for Formik integration and option rendering
- `FormDrawer` (`mocho/components/FormDrawer/`) — standardized drawer wrapper, needs minor extension for validateOn* props
- `EditDrawer` (`components/EditDrawer/`) — still used by LoadRouteDrawer (multi-form container)
- `StopFormCard` (`features/load/components/StopFormCard/`) — reused in LoadRouteDrawer with added reorder UI
- `AddressSearchField` (`features/load/components/AddressSearchField/`) — used by StopFormCard, no changes needed
- `AddressTypeahead` (`components/AddressTypeahead/`) — used by AddressSearchField, no changes needed
- `getContacts` (`utils/api/fleet/contactApi`) — contact search API
- `getCarriers` (`utils/api/fleet/carrierApi`) — carrier search API
- `getCustomers` (`utils/api/fleet/customerApi`) — customer search API
- `typeaheadPlaces` (`utils/api/fleet/placeApi`) — place search API

### Key Decisions

- **EntityAutocomplete in `src/components/`** — shared across all features, not in mocho (entity-specific, not a generic form primitive)
- **Inline create form is configurable per entity** — EntityAutocomplete accepts a `renderInlineCreate` render prop. Each entity decides what fields to show for quick-create
- **Inline create vs drawer create is context-aware** — when EntityAutocomplete detects it's inside a drawer (via React context or prop), it uses inline create. On a page form, it opens a drawer
- **LoadRouteDrawer batch-save** — all stop changes saved together on "Save Changes" instead of per-stop. Uses Formik wrapping the stop list
- **LoadRouteDrawer stays on EditDrawer** — it's a multi-form container (Formik for stops + reorder controls), not a simple single-form drawer
- **FormDrawer extended** — add optional `validateOnChange` and `validateOnBlur` props (default: Formik defaults) for ManualEntryDrawer migration
- **StopFormCard gains reorder UI** — optional `canReorder` prop adds up/down buttons to the card header, used by LoadRouteDrawer

### Explicit Exclusions

- **AssignmentFieldGroup** — already properly shared between Create Load and LoadAssignmentDrawer. No changes needed
- **Drag-and-drop reordering** — deferred to P1. Up/down buttons are sufficient
- **API changes** — all existing endpoints work. Batch stop update uses existing `updateLoadRequest`

## Acceptance Criteria

### EntityAutocomplete
- Debounced search (300ms) with request cancellation via AbortController or ref tracking
- Formik-coupled via standard `formik` prop pattern
- Accepts `fetchOptions: (search: string) => Promise<Option[]>` for API integration
- Accepts `renderOption` for custom per-entity option display
- Accepts `scopeParams` for filtered queries (e.g., customerId, carrierId)
- "Add New" action button renders at bottom of dropdown
- `renderInlineCreate` render prop expands an inline form below the field when user clicks "Add New" inside a drawer
- Auto-selects newly created entity after inline create succeeds
- Loading spinner during search

### Autocomplete Migrations
- CarrierAutocomplete extends EntityAutocomplete with carrier-specific option rendering (name + type chip + driver/vehicle counts)
- CustomerAutocomplete extends EntityAutocomplete with customer-specific rendering (company name + status badge + city/state)
- BrokerAutocomplete extends EntityAutocomplete with contact-specific rendering (name + email + role) and optional `customerId` scope
- PlaceTypeahead extends EntityAutocomplete with place-specific rendering (name + facility type + city/state + contact)
- All existing usage sites (Create Load, detail drawers, entity pages) work without regression

### FormDrawer Migrations
- LoadContactDrawer, LoadCargoDrawer, LoadAssignmentDrawer, ContactInfoDrawer, PlaceInfoDrawer, ManualEntryDrawer, PaymentDrawer all use FormDrawer
- No visual or behavioral differences after migration (footer, dirty-state confirmation, submit flow identical)
- FormDrawer supports optional `validateOnChange` and `validateOnBlur` props

### Form Field Cleanup
- DriverInfoDrawer uses @mocho/ui TextField, SelectField instead of raw MUI components
- VehicleInfoDrawer uses @mocho/ui TextField, SelectField instead of raw MUI components
- No visual differences after migration

### LoadRouteDrawer Rewrite
- Uses StopFormCard for each stop (address search, commodities, freight receiving)
- Wrapped in Formik for batch-save on "Save Changes"
- StopFormCard shows up/down reorder buttons when `canReorder={true}`
- "Add Stop" button adds new stop via Formik FieldArray
- Delete stop with confirmation
- EditableStopCard deleted from codebase
