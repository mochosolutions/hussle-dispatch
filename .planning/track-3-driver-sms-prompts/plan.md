# Driver SMS Prompts (Track 3)

> Generated by /prd-refine on 2026-04-22

## Problem

Dispatchers need driver status visibility on active loads but don't have a scalable way to nudge drivers to check in. Today, check-ins are driver-initiated via the portal — which means silent drivers stay silent, and dispatchers chase them manually by phone or text. The driver portal works well when the driver opens it, but doesn't solve the "opened the portal never" problem.

We want a hybrid system: the portal remains the canonical data-entry surface (decision from MVP scope), and SMS acts as the nudge. Each active load gets a schedule of check-in prompts anchored to meaningful lifecycle events (dispatch, pickup window, transit). Drivers receive short texts with a portal deep-link; they tap, they check in, they're done.

## Solution Overview

A scheduler-driven SMS prompt system anchored to load lifecycle events. On key events (DISPATCHED, pre-pickup, post-pickup escalation, transit interval), the system enqueues future SMS sends via RabbitMQ delayed-message exchange. A worker consumer processes due messages, sends SMS via the existing Twilio port, logs the send in a `SmsPromptSchedule` table. Each message links to the driver portal via a single-use tracking token (reuses existing `trackingTokenService`).

When the driver checks in via the portal, the system cancels any **same-anchor** pending prompt for that load. All pending prompts are canceled on load DELIVERED, CANCELED, or TONU. Dispatchers can also manually fire an immediate prompt from the load detail page.

No per-load cap — exception loads (stuck trucks, dark drivers, detention escalations) may legitimately require sustained nudges. Rate control is enforced only by a 15-minute cooldown between any two prompts for the same load. This naturally bounds a single load to ~96 prompts per 24h if the driver never checks in or advances status.

## Capabilities

### Must Have (P0)

- **DISPATCHED anchor**: when load transitions to DISPATCHED, immediately send a "Load assigned" SMS with portal link
- **PRE_PICKUP anchor**: send SMS `smsPrePickupLeadMinutes` before the first stop's appointment start (default 60 min)
- **POST_PICKUP escalation anchor**: if the first stop's appointment has passed and load status is still DISPATCHED or EN_ROUTE_PICKUP (i.e., driver hasn't marked AT_PICKUP), send escalation SMS `smsPostPickupEscalationMinutes` after the appointment window (default 30 min)
- **TRANSIT_INTERVAL anchor**: while load is IN_TRANSIT, send periodic check-in prompts. Transit-duration-aware: if estimated transit <4h, fire one mid-transit prompt; else fire on `smsTransitIntervalMinutes` cadence
- **MANUAL anchor**: dispatcher-triggered immediate send from load detail
- **Cancel-on-progression**: same-anchor pending prompts are canceled when the corresponding portal check-in or status transition happens
- **Cancel-on-terminal**: all pending prompts are canceled when load reaches DELIVERED, CANCELED, or TONU
- **Rate limits**: 15 min cooldown between prompts per load (no per-load cap — exception loads need sustained attention)
- **SMS history**: dispatcher can see a chronological list of scheduled/sent/failed prompts on load detail
- **Org settings**: lead/interval/escalation minutes are org-configurable
- **Portal deep link**: SMS contains a single-use token URL that opens the driver portal scoped to the specific load

### Nice to Have (P1 — defer unless trivial)

- **Twilio delivery webhook** — capture delivery status callbacks, flag `SmsPromptSchedule` rows as DELIVERED/FAILED based on Twilio webhook (P1; MVP can ship without and treat send-success as delivered)

## User Flows

### Flow 1 — Dispatch triggers auto-prompts

1. Dispatcher dispatches a load (status → DISPATCHED)
2. `load.status.changed` event fires
3. SMS scheduler subscriber:
   - Enqueues DISPATCHED prompt (delay: 0 — fires immediately)
   - Enqueues PRE_PICKUP prompt (delay: `firstStop.appointmentStart - smsPrePickupLeadMinutes - now`)
   - Enqueues POST_PICKUP escalation (delay: `firstStop.appointmentEnd + smsPostPickupEscalationMinutes - now`, capped at something sane like 48h)
4. Worker processes each delayed message when due
5. Worker checks: does the prompt still apply? (re-reads `SmsPromptSchedule.status`; if CANCELED, drop)
6. Worker checks cooldown: skip if last sent for this load was <15 min ago
7. Worker generates portal tracking token + short SMS: `"Load #{loadNumber}: please check in. {url}"`
8. Worker sends via Twilio port → records `sentAt` + `twilioMessageSid` in `SmsPromptSchedule`

### Flow 2 — Transit interval

1. Load transitions to IN_TRANSIT (`load.status.changed`)
2. SMS scheduler subscriber:
   - Computes transit window (estimated deliveryAt - actualPickupAt, or appointment delta fallback)
   - If transit < 4h: schedule ONE TRANSIT_INTERVAL prompt at transit midpoint
   - Else: schedule first TRANSIT_INTERVAL at `now + smsTransitIntervalMinutes`
3. On each TRANSIT_INTERVAL worker execution, if load still IN_TRANSIT and no cancellation, re-enqueue the next TRANSIT_INTERVAL at `now + smsTransitIntervalMinutes`
4. All TRANSIT_INTERVAL prompts canceled when status leaves IN_TRANSIT

### Flow 3 — Driver check-in cancels same-anchor prompt

1. Driver opens portal via SMS deep link
2. Driver marks a status transition (e.g., "Arrived at Pickup") or submits a check-call
3. The portal action publishes `driver.checkin.logged` event (extend existing check-call event to include `anchor` field, or add a new event)
4. SMS scheduler subscriber maps the check-in to an anchor:
   - Status → AT_PICKUP cancels pending POST_PICKUP
   - Status → IN_TRANSIT cancels pending POST_PICKUP + next TRANSIT_INTERVAL
   - Check-call during transit cancels next TRANSIT_INTERVAL
   - Any portal token use cancels pending DISPATCHED
5. `SmsPromptSchedule.status` is flipped to CANCELED for matched rows

### Flow 4 — Dispatcher manual send

1. Dispatcher clicks "Send Check-in SMS" on load detail
2. UI dispatches `POST /loads/:id/sms-prompts`
3. API writes a `SmsPromptSchedule` row with anchor=MANUAL, scheduledAt=now, status=PENDING
4. API publishes an immediate `sms-prompt.due` delayed message with delay=0
5. Worker processes as normal (still respects rate limits)

### Flow 5 — Terminal status

1. Load transitions to DELIVERED / CANCELED / TONU
2. Subscriber finds all `SmsPromptSchedule` rows with status=PENDING for that load
3. Flips them to CANCELED
4. Worker skips them when delayed messages are consumed

## API/Interface Changes

### New endpoints

- `POST /loads/:id/sms-prompts` → dispatcher-triggered manual send. 201 with `SmsPromptSchedule` row. Throws 409 if rate limits exceeded, 400 if driver has no phone.
- `GET /loads/:id/sms-prompts` → history list. Returns `SmsPromptSchedule` rows for the load, newest first. Paginated.
- `POST /twilio/webhook/status` → Twilio delivery status callback (P1; skip for MVP unless trivial).

### Org settings endpoints (extend existing)

- Existing org settings endpoints extended to include the 5 new `sms*` fields. Validators accept positive integers. No new routes.

### New events on the event bus

Add to `eventMap.ts`:

- `sms.prompt.due` — delayed-message payload: `{ smsPromptScheduleId: string; loadId: string; organizationId: string; anchor: SmsPromptAnchor }`. This is what the RabbitMQ delayed-message exchange publishes and the worker consumes.
- `sms.prompt.canceled` — fired when a pending prompt is canceled (for audit/history UI updates): `{ smsPromptScheduleId: string; loadId: string; reason: string }`

Subscribers added to existing events:

- `load.status.changed` — scheduler subscriber: reacts to DISPATCHED (seed anchors), AT_PICKUP (cancel POST_PICKUP), IN_TRANSIT (seed TRANSIT_INTERVAL, cancel POST_PICKUP), DELIVERED/CANCELED/TONU (cancel all)
- `load.checkcall.logged` — scheduler subscriber: cancels next TRANSIT_INTERVAL
- Portal token consumption event (new or existing) — cancels pending DISPATCHED

**Refresh:** polling is saga-driven (project standard — no component-level `setInterval`). Component dispatches start/stop actions; a long-running saga handles the loop.

- Notifications tab mounts → dispatches `startSmsPromptPolling({ loadId })`
- Polling saga loop: `yield race({ stop: take(stopSmsPromptPolling.type), tick: delay(30_000) })`; on each tick, dispatches `fetchSmsPromptHistoryRequest({ loadId })`
- Tab unmounts → dispatches `stopSmsPromptPolling()` which wins the race and breaks the loop
- Also: `sendSmsPromptSuccess` forks a one-off `fetchSmsPromptHistoryRequest({ loadId })` so the history refreshes immediately after manual send, independent of the poll cadence
- Backoff: on N consecutive fetch failures, increase delay to 60s. Reset to 30s on first success. Keep backoff state in the page slice.

**Redux plumbing:**
- New entity slice `smsPromptHistory` (normalized by `id`) under `features/load/store`
- New page slice keys on `load:{loadId}` with `loading`/`errors` per operation plus `pollingDelayMs` and `consecutiveFailures` for backoff
- Sagas:
  - `fetchSmsPromptHistorySaga` — handles `fetchSmsPromptHistoryRequest` via `takeLatest` → `GET /loads/:id/sms-prompts` (paginated)
  - `smsPromptPollingSaga` — handles `startSmsPromptPolling`; runs the race/delay loop; forks `fetchSmsPromptHistoryRequest` each tick

## Technical Context

### Existing code to reuse

- **`trackingTokenService`** (`hussle-app-dispatch-api/src/notifications/services/trackingTokenService.ts`) — reuse its pattern (and possibly its table if scopes are extensible) for single-use portal deep-link tokens.
- **Twilio `sendSms` port** (`hussle-app-dispatch-api/src/shared/notifications/twilioSmsService.ts` + factory) — already wired, production-ready.
- **RabbitMQ event bus** (`hussle-app-dispatch-api/src/shared/messaging/rabbitMqEventBus.ts`) — extend to support delayed-message publishing. Requires the `rabbitmq_delayed_message_exchange` plugin and a new exchange.
- **`LoadStatusService` events** — already publishes `load.status.changed` and `load.delivered`. Scheduler subscribes to these, no changes needed to the publisher.
- **Driver portal tracking system** — portal routes + check-call recording are built. Likely need to emit a new event on portal check-ins that the SMS scheduler can listen to (`driver.portal.checkin`) OR extend existing events with an `anchor` hint. Decide during implementation.

### Key decisions (locked)

- **Scheduler infrastructure**: **RabbitMQ delayed messages** — reuses existing infra; adds the delayed-message exchange plugin. Alternative approaches (DB-polled worker, BullMQ) rejected to avoid new deps or polling overhead.
- **Termination on check-in**: **Cancel same-anchor only** — each anchor type cancels independently based on the check-in semantics. Preserves useful nudges (e.g., transit pings) even after pre-pickup confirmation.
- **Rate limits**: **15 min cooldown between prompts per load. No hard cap.** Exception loads (stuck trucks, dark drivers, detention escalations) may need sustained pinging, so a blanket cap would block legitimate ops. Cooldown alone bounds worst case to ~96 messages per 24h per load if the driver never responds.
- **Quiet hours**: **None** — send anytime while on active load (per MVP Round 3 decision).
- **SMS content**: **Short text + portal deep link** — `"Load #{loadNumber}: please check in. {url}"` (per MVP Round 2).
- **Transit-duration-aware interval**: if transit < 4h, one mid-transit ping; else `smsTransitIntervalMinutes` cadence.
- **Single-use token per prompt**: each SMS carries its own tracking token (reuse `trackingTokenService` with an `SMS_PROMPT` scope). Prevents token reuse/forwarding.

### Key decisions (open — flag for implementation)

- **How DISPATCHED anchor maps to portal check-in for cancellation** — simplest: first portal token consumption cancels pending DISPATCHED. Finalize during implementation.
- **Post-pickup escalation cap**: if the pickup appointment was yesterday, don't schedule an escalation forever. Cap lookup at `now + 48h` during scheduler seed.
- **Worker idempotency on Twilio failures**: if Twilio returns 5xx, retry once then mark FAILED. Don't re-queue indefinitely.

None (no web search needed; the architecture decisions come from existing repo patterns).

## Acceptance Criteria

1. Dispatching a load with a driver who has a phone number results in a DISPATCHED SMS delivered within 60 seconds of the status transition.
2. A PRE_PICKUP SMS is sent approximately `smsPrePickupLeadMinutes` (default 60) before the first stop's `appointmentStart`.
3. If the first-stop appointment window passes without the load reaching AT_PICKUP, a POST_PICKUP SMS is sent `smsPostPickupEscalationMinutes` (default 30) after `appointmentEnd`.
4. On load IN_TRANSIT, at least one TRANSIT_INTERVAL SMS fires: mid-trip for trips <4h, or on `smsTransitIntervalMinutes` cadence otherwise.
5. When a driver marks "Arrived at Pickup" in the portal, any PENDING `SmsPromptSchedule` rows with `anchor=POST_PICKUP` for that load are flipped to CANCELED and the worker drops them when their delayed message is consumed.
6. When a load transitions to DELIVERED / CANCELED / TONU, **all** PENDING `SmsPromptSchedule` rows for that load are flipped to CANCELED within the same event transaction.
7. Dispatcher can click "Send Check-in SMS" on the load detail page; a MANUAL `SmsPromptSchedule` row is created and an SMS is sent within 10 seconds (subject to cooldown).
8. If the last SMS for a load was sent <15 min ago, a new prompt (manual or automatic) is blocked (cooldown) — the row is created with status=FAILED and reason "cooldown not elapsed". There is no per-load message cap — exception loads may accumulate many prompts over time.
10. The SMS contains a URL of the form `{driverPortalUrl}/check-in?token={token}&loadId={loadId}`, and the token is a single-use token valid for the expected prompt window (e.g., until the next anchor fires or 24h).
11. The load detail page renders an SMS Prompt History panel showing all `SmsPromptSchedule` rows for the load, newest first, with columns: anchor, scheduledAt, sentAt, status, failureReason.
12. Org settings UI exposes `smsPrePickupLeadMinutes`, `smsTransitIntervalMinutes`, `smsPostPickupEscalationMinutes`, `smsCooldownMinutes` as integer inputs. Validation: positive integers, min 1, max 1440 (24h).
13. Attempting a MANUAL send for a driver without a phone number returns a 400 with a clear error message.
14. Integration test covers: dispatch → DISPATCHED SMS fires; simulated time skip → PRE_PICKUP fires; pickup-window-passed with no status advance → POST_PICKUP fires; IN_TRANSIT → TRANSIT_INTERVAL fires; DELIVERED → remaining pending prompts are all CANCELED.

## Out of Scope

- **Customer portal SMS** — different audience, separate feature
- **Inbound SMS / reply parsing** — driver can't reply and have the reply logged as a check-in. Portal-only data entry per MVP scope.
- **Quiet hours / timezone-aware muting** — per MVP decision, send anytime on active loads
- **Per-driver customization** — all drivers get the same schedule; org-level settings only
- **SMS templates / multi-language** — single hardcoded copy for MVP (`"Load #{loadNumber}: please check in. {url}"`)
- **Twilio delivery webhook processing** — P1 deferred unless trivial to add; MVP treats Twilio-accept as delivered
- **Analytics / delivery reports** — beyond the per-load history panel, no aggregate reporting for MVP
- **Retry policy tuning** — MVP: one retry on 5xx, then mark FAILED. Not configurable.
- **Per-load SMS cadence overrides** — org-level only for MVP
