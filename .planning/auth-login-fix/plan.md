# Auth Login & Session Refresh Fix

> Generated by /prd-refine on 2026-05-25

## Problem

Users are being logged out mid-day, and on hard-refresh they bounce to `/login` instead of resuming their session. In some cases the redirect never fires at all — the user is stuck on a broken page with failing API calls. Investigation surfaced four concrete defects in the auth strategy plus one dead UI feature:

1. **TTL mismatch.** Refresh cookie `maxAge` is **30 days** (`shared/utils/cookieUtils.ts:53`), but the Redis session row's TTL is **24 hours** (`auth/constants/index.ts:1`). After any 24h gap, the browser still presents a refresh cookie that the server cannot honor — refresh returns 401 → frontend hits `handleAuthFailure()` → redirect to `/login`.
2. **Destructive rotation, no grace window.** `rotateSessionRedis.ts:73–76` deletes the old refresh-token Redis row before writing the new one. Two browser tabs (or two parallel bootstrap requests) racing the same refresh cookie: one wins, the other reads a missing key and 401s → that tab logs the user out while the other stays signed in.
3. **Purely reactive, terminal-on-failure refresh.** `utils/axios.ts` only refreshes after a 401 returns. There is no proactive refresh and no retry on transient errors — a network blip during the once-per-hour refresh window logs the user out instantly. Compounded once drivers come online: mobile OS timer throttling and bursty cellular networks will make this far worse.
4. **Silent redirect failure on auth-failure.** `handleAuthFailure` in `utils/axios.ts:51–69` tries to call `navigate('/login')` via a deferred `getNavigate()` helper. The helper **throws** if `setNavigate(navigate)` (called from a `useEffect` in `App.tsx:22` and `routes/index.tsx:40`) hasn't run yet, and the call is wrapped in a bare `catch {}` that silently swallows the throw. On the main app this is rescued accidentally by `<AuthGuard>` re-rendering on Redux state change and emitting `<Navigate to="/login" />`. **But the carrier-portal and driver-portal routes (under `<PortalShell />`) have no `AuthGuard`**, so when their API calls 401 they:  (a) are still using the same shared axios instance and interceptor; (b) get no rescue from any router-level guard; (c) often see no navigation at all — the user is stranded on a broken page with no path forward. Also: redirecting an invite-token portal user to `/login` is the wrong destination — they don't have a password account.
5. **Dead "Remember Me" checkbox.** The checkbox at `features/auth/sections/AuthLogin/index.tsx:102` flows `rememberMe` through `loginRequest`, the login saga stores it in `localStorage`, and **nothing else reads it**. Backend ignores it. Has zero effect on session length.

## Solution Overview

Four coordinated fixes plus wiring the Remember Me toggle:

- **Align cookie maxAge with Redis TTL**, configurable per-session. Default 24h rolling; Remember Me extends both to 7 days. *(Final session lengths TBD pending driver-population decision — see Open Questions.)*
- **Add a 10-second read-through grace window** in `rotateSessionRedis` so the old refresh token continues to resolve to the **same new tokens** briefly after rotation. Concurrent tabs converge on the same session instead of one getting kicked or each ending up on a different session.
- **Add proactive refresh** — backend returns `accessTokenExpiresAt`; frontend schedules a refresh ~5 minutes before expiry **and also refreshes on `visibilitychange` / `focus` when the app returns from background** (essential for mobile drivers where `setTimeout` is unreliable). The 401-driven path becomes a safety net, not the primary mechanism.
- **Make refresh failure non-terminal for transient errors.** Retry with exponential backoff (e.g., 500ms / 1.5s / 4s, up to 3 attempts) on network errors or HTTP 5xx. Only treat HTTP 401 as a definitive failure.
- **Repair the auth-failure → redirect path.** Move navigation out of the axios interceptor (a layer that has no business knowing about routes); let Redux state changes drive routing via guards. Replace the bare `catch {}` with logging. Add a portal-specific session-expired flow so carrier-portal and driver-portal users get a portal-appropriate "session expired" screen instead of being silently stranded or wrongly punted to `/login`.

## Capabilities

### Must Have (P0)

- **Rolling 7-day session** by default — Redis TTL and refresh cookie maxAge both **7 days (604800 seconds)**, both reset on each rotation.
- **Remember Me = 30 days** — when checked at login, backend persists `rememberMe: true` on the session; all subsequent rotations use **30-day TTL** (2592000 seconds) for both Redis and cookie.
- **Driver login defaults Remember Me ON** — when the driver login flow ships, its login form defaults the Remember Me checkbox to checked (or hides it entirely and always sends `rememberMe: true`). Drivers on multi-day hauls don't have a workflow for "remember to re-check the box every Monday."
- **10-second read-through rotation grace** — after rotation, the OLD refresh-token Redis key is rewritten to a packet `{ newSessionKey, newRefreshToken }` with 10s expiry. A concurrent caller arriving with the old token reads this packet, receives the SAME new refresh token plus a freshly-signed access token, and returns successfully WITHOUT triggering a second rotation. Both tabs converge on the same session.
- **Proactive refresh (timer)** — backend includes `accessTokenExpiresAt` (ISO 8601) in login, refresh, and `/auth/me` JSON responses; frontend schedules `setTimeout` to fire refresh ~5 minutes before that timestamp.
- **Proactive refresh (visibility-aware)** — frontend also listens for `visibilitychange` and `focus`; when the app returns to foreground and the access token expires within (configurable) ~5 minutes, fire a refresh BEFORE any other API request. Essential for mobile drivers where `setTimeout` is throttled or killed while backgrounded.
- **Retry refresh on transient errors** — if `POST /auth/token/refresh` fails with no HTTP response (network error / timeout) or HTTP 5xx, retry with exponential backoff: 500ms, 1.5s, 4s (configurable, up to 3 retries). Surface a non-intrusive "Reconnecting…" toast during retries. Only HTTP 401 from the refresh endpoint is treated as a definitive failure (no retry).
- **Auth-failure path repair (Failure 4 fix)**:
  - `handleAuthFailure` in `utils/axios.ts` is reduced to dispatching Redux actions only (`logoutSuccess`, `resetPopups`, a new `sessionExpired({ context: 'main' | 'portal' })`); no imperative navigation.
  - A new `sessionExpiredSaga` watches the `sessionExpired` action and (a) calls `getNavigate('/login')` for `context: 'main'`, (b) dispatches a portal-specific action for `context: 'portal'`. Sagas run after the Redux store is initialized — no React-mount race.
  - Replace the bare `catch {}` with logging (console + future observability hook). Silent failure is never acceptable in the auth path.
  - Carrier-portal and driver-portal routes get a `PortalSessionGuard` that listens for the portal `sessionExpired` flag and renders a portal-appropriate "Your session has expired" screen with re-authentication guidance (e.g., "Request a new invite link" / "Sign in again to continue") instead of navigating to `/login`.
  - The axios interceptor decides `context` based on the request URL prefix (`/carrier-portal/*` or `/driver-portal/*` → portal context; everything else → main).
- **No regressions to login / signup / switch-org / accept-invite** — all six existing cookie-issuing controllers continue to work; the refresh-cookie maxAge change is centralized in `setRefreshTokenCookie`.

### Nice to Have (P1)

- Idle-timeout warning dialog (frontend reads `accessTokenExpiresAt` and warns N minutes before forced logout when refresh would also expire). **Out of scope for this fix.**
- Cross-tab BroadcastChannel coordination. With the 10s grace window we should not need it; deferred unless we see continued issues.

## User Flows

### Flow 1 — Active user, single tab, full day

1. User logs in at 9am, leaves Remember Me **unchecked**. Backend creates session with 7d TTL, cookie maxAge 7d.
2. Frontend reads `accessTokenExpiresAt` from the login response (~10am). Schedules proactive refresh for 9:55am.
3. At 9:55am the timer fires `POST /auth/token/refresh`. Backend rotates: writes new session + new refresh token (7d TTL), rewrites old refresh-token row to a grace packet `{ newSessionKey, newRefreshToken }` with **10s expiry**, sets new cookies, returns new `accessTokenExpiresAt`. Frontend schedules next refresh.
4. Cycle repeats hourly. User never sees a 401-induced refresh.
5. User logs out manually at 6pm → cookies cleared, Redis revoked.

### Flow 2 — Active user, two tabs open

1. Both tabs receive the same access + refresh cookies (browser-shared).
2. Tab A's proactive timer fires first at 9:55am, rotates successfully, browser receives new cookies.
3. Tab B's timer fires ~50ms later. It still has the **old** refresh token in memory's request, but the browser now sends the **new** cookie. Refresh succeeds normally.
4. Edge case — Tab B somehow sends the OLD refresh token (rare, only if cookie write hasn't propagated mid-flight): rotation grace window resolves it to the new session. Tab B's refresh succeeds with a fresh-but-equivalent session.

### Flow 3 — Returning user after a long gap (Remember Me off)

1. User logs in Monday without Remember Me → 7d session. Cookies and Redis both expire next Monday.
2. User comes back the following Wednesday (>7d gap). Cookies auto-purged by browser (maxAge passed) AND Redis session expired. Bootstrap fires `/auth/me` with no cookies → 401.
3. Interceptor sees no refresh cookie → skips refresh, dispatches `sessionExpired({ context: 'main' })` → user lands on `/login`. Correct behavior; they're past the rolling window.

### Flow 4 — Returning user after a long gap (Remember Me on)

1. User logs in Monday with **Remember Me checked** → 30d session.
2. User comes back two weeks later (14d gap). Access token expired, refresh cookie still valid (30d), Redis session still alive (rotated 14d ago → still within 30d window).
3. Bootstrap fires `/auth/me` → 401 → interceptor refreshes → succeeds → retries `/auth/me` → 200. User stays logged in. Redis TTL resets to a fresh 30d from this rotation.

### Flow 5 — Network blip during scheduled refresh

1. Proactive timer fires. `POST /auth/token/refresh` returns a network error (no HTTP response) or HTTP 5xx.
2. Interceptor retries with exponential backoff: 500ms → 1.5s → 4s (up to 3 retries). A non-intrusive "Reconnecting…" toast is shown while retries are in flight.
3. Any retry succeeds → toast clears, user resumes seamlessly.
4. All retries exhausted → `handleAuthFailure` dispatches `sessionExpired`; the saga and guards take over.
5. If any attempt returns HTTP 401 → `handleAuthFailure` immediately (session genuinely dead, no point retrying).

### Flow 6 — Driver on phone returns to the app after a 3-hour gap

1. Driver finishes a delivery, app has been backgrounded for 3 hours. iOS suspended the JS event loop; the proactive refresh timer never fired.
2. Driver taps the app icon, app becomes visible. `visibilitychange` listener fires.
3. Listener compares `Date.now()` to `accessTokenExpiresAt` from the last response. Token expired 2.5h ago.
4. Listener triggers an immediate proactive refresh BEFORE the UI fires any other requests.
5. Refresh succeeds against the still-valid 7d refresh token; new access token issued; next API requests proceed normally. Driver sees zero auth friction.

### Flow 7 — Auth failure on the carrier portal (Failure 4 fix)

1. Carrier portal user (invite-token authenticated) makes an API call. Token expired or session ended server-side.
2. Axios interceptor returns 401, exhausts retries, calls `handleAuthFailure`.
3. `handleAuthFailure` inspects the request URL → `/carrier-portal/...` → dispatches `sessionExpired({ context: 'portal' })`.
4. Redux state flips a portal session-expired flag.
5. `PortalSessionGuard` (wrapping `<PortalShell />`) sees the flag, renders a "Your session has expired" screen with a button to "Request a new invite link" or contact dispatch.
6. User is NOT punted to `/login` (which would be wrong — they have no password account).
7. Other queued API calls from the same portal context all see the same failure path; no broken page, no infinite retry loop.

## Technical Context

- `setSecureCookie(res, name, value, options)` at `cookieUtils.ts:6` — already accepts `options.maxAge`, no change needed downstream.
- `createSessionRedis` and `rotateSessionRedis` are the only two writers of session TTLs — single place to read `rememberMe` and pick TTL.
- `hashToken` / `verifyToken` from `tokenHelpers.ts` — unchanged.
- Frontend `axios.ts:23–166` interceptor — extend, don't replace. Existing `failedQueue` + `isRefreshing` logic stays.
- Frontend `notify` action (`features/ui/store/reducers/notificationSlice`) — surface "session refresh failed, retrying" toast on retry (optional — keep silent if it's annoying).

### Key Decisions

- **User populations driving design.** Four distinct populations use the auth system: (1) **internal dispatchers** — multi-tab, all-day desktop usage, hit the rotation race daily; (2) **carrier admins** — mixed desktop/mobile, variable networks; (3) **owner-operators** — intermittent usage, the population that actually benefits from Remember Me; (4) **drivers (forthcoming)** — phone-primary, multi-day hauls, OS-suspended backgrounding, flaky cell networks. Driver requirements push session lengths longer and force visibility-aware refresh into the design now (cheap to design for; expensive to retrofit).
- **7d base / 30d Remember Me, with Remember Me defaulted ON for drivers.** Driver-driven: a driver on a 3-day haul cannot tolerate a 24h base TTL. 7d is forgiving enough for owner-ops who skip a few days; 30d covers true intermittent users. The slight security loosening for dispatchers/carriers (vs. 24h base) is offset by rotation-on-each-use — an idle stolen cookie still rotates out within the window of the next active session. Driver login flow will default Remember Me on (or hide the checkbox) so multi-day hauls don't require explicit opt-in.
- **Read-through grace over destructive rotation.** After rotation, store `refresh:OLD → { newSessionKey, newRefreshToken }` for 10s. A concurrent caller in the grace window reads this packet, returns the SAME new refresh token plus a freshly-signed access token, and does NOT trigger a second rotation. Both racing tabs converge on the same session. This is the simplest implementation that delivers true convergence (not just "the second tab doesn't get a 401 anymore"). Migration is trivial — refresh tokens already rotate, so within one rolling-TTL window every Redis key takes the new shape.
- **Accept residual sub-millisecond parallel-rotation risk.** With read-through grace, the remaining race window is the time between `redisClient.get('refresh:R0')` and the grace-rewrite `redisClient.set('refresh:R0', ...)` on a single Redis instance — microseconds. Not worth adding a distributed lock primitive (SETNX + result-key polling) to the codebase to close. Revisit if observed in production.
- **`rememberMe: false` default for non-login token-issuing flows.** `signupOrg`, `acceptInvite`, `switchOrg`, `passwordChallenge` all create sessions with the base TTL. Simplest, secure default. None of the four user populations has an explicit need for these flows to inherit Remember Me; the only mild UX wart is `passwordChallenge` after a Remember-Me-checked login, which is a once-per-account first-time flow. Easy to upgrade later if users complain.
- **Server-side grace over client BroadcastChannel.** Single source of truth — server controls token lifecycle. Works for any client (web tab, mobile webview, future native). 10s is enough to swallow realistic races; short enough that a stolen old token can't be used long after rotation.
- **`accessTokenExpiresAt` over `expiresIn`.** Absolute timestamp avoids client-clock-skew issues for scheduling.
- **Visibility-aware refresh required for drivers.** `setTimeout` is unreliable on mobile (iOS suspends timers when backgrounded; Android Chrome throttles aggressively; PWAs can be force-killed). Adding `visibilitychange` / `focus` listeners that refresh on app-resume is non-negotiable if we want drivers to have smooth multi-day sessions.
- **Exponential backoff over single retry.** Drivers will hit transient network failures constantly on cellular. A single retry is not enough. 500ms / 1.5s / 4s (3 attempts) covers most realistic blips without being so long that the user notices a frozen UI. The "Reconnecting…" toast keeps the UX honest.
- **Move navigation out of the axios interceptor.** The HTTP layer has no business knowing about routes. Dispatching `sessionExpired({ context })` and letting sagas / guards drive navigation is architecturally correct AND eliminates the React-mount race in `getNavigate()`. Sagas start with the Redux store, before React mounts — no timing gap.
- **Portal session-expired flow ≠ main app session-expired flow.** Portal users (carrier-portal, driver-portal) authenticate via invite tokens, not passwords. Punting them to `/login` is the wrong destination. They need a portal-appropriate "session expired" screen with re-authentication guidance tailored to their context. This is also the only way to fix the "stuck on broken page" symptom for portal users.

### Future Hardening (out of scope for this fix)

- **Race-free rotation via Lua `EVAL`.** If we ever observe real sub-millisecond rotation races in production, the upgrade path is a Redis Lua script that performs the entire read-check-rewrite-rotate sequence atomically. Cleaner than a SETNX lock primitive (single round-trip, no lock-holder-crash failure mode, atomicity is a Redis guarantee). Note: under Redis Cluster topology, this requires hash-tagging auth keys with `{userId}` (and embedding userId in the refresh token format). Under single-Redis or Sentinel topology — both of which cover FleetCommand's scale for the foreseeable future — Lua works without modification.

### Explicit Exclusions

- **No BroadcastChannel / cross-tab JS coordination.** Server grace window covers the race.
- **No idle-timeout warning dialog.** Out of scope.
- **No change to JWT access-token TTL.** Stays 1h.
- **No change to access-token cookie maxAge** (already 1h, matches the JWT).
- **No CSRF changes.** The existing csrfToken cookie + header pattern remains.

## Acceptance Criteria

1. After login without Remember Me, the `accessToken` cookie has `maxAge: 3600s` and the `refreshToken` cookie has `maxAge: 604800s` (7 days). Redis `TTL session:refresh:<id>` returns ~604800. Verified via response Set-Cookie headers and `redis-cli`.
2. After login with Remember Me checked, the refresh cookie `maxAge` and Redis session TTL are both **30 days** (2592000 seconds). Verified the same way.
3. The login response JSON includes `accessTokenExpiresAt` as a valid ISO-8601 timestamp ~1h in the future. Same field present in `/auth/me` and `/auth/token/refresh` responses.
4. Calling `POST /auth/token/refresh` twice in rapid succession with the same starting refresh-token cookie returns 200 both times. The second call resolves to the same session as the first (verified by sessionId in Redis). After the 10s grace window expires, a third call with the original token returns 401.
5. Frontend bootstrap on a fresh page load schedules a `setTimeout` for ~55 minutes (= 1h minus 5min lead). Manually advancing time (or using a short access TTL in a local test) triggers the proactive refresh and the user never sees a 401.
6. Stubbing `POST /auth/token/refresh` to throw a network error (no response) causes the interceptor to retry exactly once after ~1s; if the retry succeeds, the user stays logged in with no visible disruption.
7. Stubbing `POST /auth/token/refresh` to return a real HTTP 401 (e.g. test with an expired refresh cookie) triggers `handleAuthFailure` immediately on the first response — no retry.
8. Unchecking Remember Me at login produces a **7d** session (verified in Redis); checking it produces a **30d** session.
9. The Remember Me checkbox value is included in the login request payload (no change — already present) and **observably affects** the resulting session length (new behavior).
10. After every successful refresh response, the frontend `refreshScheduler` reschedules its timer based on the new `accessTokenExpiresAt`. Verified via unit test on the scheduler module.
11. Returning the app to foreground (`document.visibilitychange` to `visible`) while the access token is within 5 minutes of expiry triggers an immediate refresh BEFORE any other API request fires. Verified via JSDOM unit test on the scheduler/listener and a manual mobile-browser observation.
12. Stubbing `POST /auth/token/refresh` to throw a network error (no response) causes the interceptor to retry with exponential backoff up to 3 times (500ms / 1.5s / 4s); a "Reconnecting…" toast is shown during retries and dismissed on success. If all retries fail, `sessionExpired` is dispatched.
13. Stubbing `POST /auth/token/refresh` to return HTTP 401 triggers `sessionExpired` immediately on the first response — no retry.
14. **Failure 4 — main app:** when `sessionExpired({ context: 'main' })` is dispatched and `getNavigate` IS available, `sessionExpiredSaga` calls `navigate('/login')` with `state.from` preserved.
15. **Failure 4 — `getNavigate` not yet set:** the saga logs a warning (instead of silent swallow) and `<AuthGuard>` rescues the redirect via `<Navigate to="/login" />`. End-to-end test: hard refresh on a protected route with no valid session → user lands on `/login`, no stranded broken-page state.
16. **Failure 4 — portal context:** when `sessionExpired({ context: 'portal' })` is dispatched while on `/carrier-portal/...` or `/driver-portal/...`, `PortalSessionGuard` renders the "Your session has expired" screen. The user is NOT redirected to `/login`. Re-authentication CTA is appropriate for the portal (e.g., "Request a new invite link").
17. The bare `catch {}` in `utils/axios.ts` is gone. Any caught error in the auth-failure path is logged.
18. All existing auth integration tests pass. New tests added: rotation grace window (read-through behavior + 10s expiry), TTL selection by `rememberMe`, `accessTokenExpiresAt` presence in responses, interceptor retry on transient error with exponential backoff, scheduler `visibilitychange` behavior, `sessionExpiredSaga` for both `main` and `portal` contexts, `PortalSessionGuard` rendering.
19. `npm run validate` passes in both `hussle-app-dispatch-api/` and `hussle-app-dispatch-ui/`.

## Out of Scope

- Idle-timeout warning UI (Phase 2 feature).

- Changing access-token TTL or rotation policy beyond what's described.
